## これは何か

- **一つの**数式（LaTeX サブセット / 論文記法 / MATLAB スタイル、お好みで）を書くと、同じ
  **次元付き IR** に降ろされ、名前付きの中間値とソースコメントを持つ Rust 関数にコンパイルされます。
- 次元（七つの基本量 kg·m·s·A·K·mol·cd）はコンパイル時に強制されます：`m + s` はそもそもコンパイルが通りません。
- 記号的微分、CSE、定数畳み込みを内蔵。解析的な偏微分は中心差分に対するテストで固定されています。
- **行列は一級市民**です：具体的な行列は完全に検査され、**パターン行列**（省略記号付き）は動的なサイズを表します——
  教科書の `[b c ⋯ 0; a b c ⋯; ⋯ a b c; 0 ⋯ a b]` は書かれたとおりにソースコードになります。

## 連邦と複数行の記法（2026-11-23 の第二裁定）

**一つのマクロブロックが、互いに参照し合う数式の一群を丸ごと抱えられます**（「連邦」）：

```rust
formula_matlab!{
    decl { F : force [N]; m : mass [kg]; r : radius [m]; }
    accel = F / m
    mech = ( accel * r )^(1/2)
}
// expands to a let chain: let accel = F / m; let mech = (accel * r).sqrt(); mech
```

- **項目の区切り** = セミコロンまたは**改行**で、これは**三つのレーンすべてで成り立ちます**（トークンレーンは
  proc-macro の span 行番号から改行を再構成し、その行番号はソースファイルに揃えられているので、診断は同じ行を指します）。
- **後ろの項目は前の項目を参照できます**：次元は名前と一緒に伝播します（accel の m/s² がシンボル表に加わる）。build.rs レーンは生成時に代入をインライン展開します。
- **名前が契約です**：数式が `decl` の名前を再利用するとき、その結果の次元はその宣言と一致しなければなりません
  （`a = F/m` はよく、`s : Pa; s = F/d` は拒否されます）。一つの数式セットまたは一つの生成ディレクトリ内での数式名の重複は常に拒否されます。
- **演算子の継続モデル**：演算子は**行末**に置かなければなりません（`x +⏎ y` ✓）。次行の先頭の `-`/`+` は新しい項目の符号であり、行継続の減算ではありません——それが曖昧性解消の裁定です。
- LaTeX 表面の暗黙の乗算（並置）は**一行に収めなければなりません**：行をまたいで並置すると、次の数式が乗算項として飲み込まれます。

**行列の複数行記法**（行ごとに物理的に一行。列の間隔は自由で、整列は不要）：

```text
[ 2*k, -k,    ...,   0 ;
  -k,  2*k,   -k,    ... ;
  ..., -k,    2*k,   -k ;
  0,   ...,   -k,    2*k ]
```

- 行区切り = `;` または改行（混在可、末尾は任意）。列区切り = カンマまたは空白（≥1、いくつでも）。
- セル内の省略記号 `...` / `⋯` / `…` は「その位置は省略」を意味します（書き戻し時に水平/垂直/対角を推論）。
- **`-` の前に空白がなければ符号、前に空白があれば新しい列の始まり**（MATLAB の意味論）：`[k-1]` は一列、`[k -1]` は二列。

## 複素数：値レイヤーからコード生成までエンドツーエンドで配管（2026-11-23）

- **`j` は予約された虚数単位**（常に無次元、決して宣言されず、**パラメータリストにも決して現れません**）。`Z = R_s + j*X` はそのまま書けます。
- 値レイヤーのバリアントはちょうど二つ：`Value::Scalar(C)` / `Value::Matrix(Vec<Vec<C>>)`、ここで `C = {re, im}`。
  実数は虚部がゼロの複素数 ⇒ **複素行列、転置、乗算、加算、減算がすべて
  要素ごとに無償で成り立ちます**。「実行列／複素行列」の象限分割は不要です。
- 超越関数は実数と複数で一つの表を共有します：`exp ln sqrt sin cos tan sinh cosh tanh` +
  `abs arg conj re im`（後ろの四つは常に実軸に戻ります）。複素べき乗は主枝上の `exp(w·ln z)` を通ります。
- **`eval` は複素数値に対して明示的なエラーを返します**（虚部を黙って捨てることはありません）。複素数値が欲しいときは常に `eval_value` を使ってください。
- **コード生成には独立した複素数レーンがあります**：数式に `j` が含まれると `-> (f64, f64)` =（実部, 虚部）として出力され、
  ブロックローカルの補助関数（`__c_mul` / `__c_sqrt` …）のうち**実際に使われたものだけが出力されます**（そうしないと clippy の `-D warnings` が赤になります）。
  バッチエントリは `out: &mut [(f64, f64)]` で、EIS の周波数掃引にそのまま使えます。
  マクロレーン（`formula!` など）も同じように選別します：`j` は呼び出し側で**自由変数に退化しません**。
  連邦 `let` チェーン内ですでに複素数になっている束縛は正しく継承されます（`emit_block_complex_with`）。
  複素数レーンは**解析的導関数を生成しません**：`abs/arg/conj/re/im` は複素解析的ではないため、連鎖律が成り立たないからです。
- **生成コードと値レイヤーは点ごとに一致しなければならない**というのが厳格な制約です：`__c_powf` は `C::pow_real` の整数選別をそのまま写し
  （負の実数の底の整数べきは正確に実軸に着地しなければならない）、`__c_sqrt` は大きな絶対値でのオーバーフローを避けるため値レイヤーと同じく `hypot` を使います。
  `__c_div` は IEEE に従う一方で値レイヤーはエラーにするのは意図的です——これらのそれぞれは fixture 内の演算子ごとの比較テストで守られています。
- 単位文字列は有理指数を受け付けます：`[V/A*s^(-1/2)]`（角括弧は必須——そうでないと指数の `/` と
  単位文字列の除算記号を見分けられません）。割り切れない指数（`m^(1/3)`）は明示的に拒否されます。無次元量には `[1]` と書きます
  （利得 / 個数 / モル分率はすべて宣言可能でなければならず、「単位を省略する」ことで紛れ込ませることはできません）。
- **`himari-fmt --diff <file>`**：読み取り専用のプレビューで、`--- current / +++ canonical`
  の unified diff を出力します（変更なし → 出力なしで終了コード 0、変更あり → 終了コード 1）。
- **実数と複素数の意味論的な境界**（意図的であり、見落としではありません）：`1/0` は以前 `inf` を返していましたが、今は**エラー**になります。
  `ln(0)` も同様です。`(-2)^0.5` は「結果は複素数です。`eval_value` を使ってください」と報告します。
  生成コードは代わりに IEEE の意味論に従います（ゼロ除算は inf/NaN）：ホットパスにエラーパスは載せず、
  数式レイヤーが静的に誤りと証明できるものは次元/形状のゲートが捕まえます。
- **`python3 scripts/fmt_check.py --fix`**：正規形に再レイアウトし、サイドカーを再生成するコマンド一つ。

## 単位：SI 接頭辞、換算、無次元群（2026-11-23）

- **接頭辞を分割する前に完全名を引く**：`m` はメートル（「ミリ何とか」ではない）、`mol` はモル、`cd` はカンデラ、
  `daN` はデカニュートン（最長の接頭辞が優先）。`nF` / `GHz` / `mm^2` / `mV/mm` / `µF` / `Ω` はすべて動きます。
  組立単位はエレクトロニクスが避けられない六つをカバーします：`F` `Ω`（または `ohm`）`S` `H` `Wb` `T`。
- **次元と換算係数は別々に保存されます**：`parse_unit` は次元だけを返し、`parse_unit_spec` はさらに →SI の換算係数を返します。
  `convert(v, "nF", "F") = 1e-9 F` で、次元の不一致はエラーになります。質量の基本単位は **kg** です：
  `g = 1e-3 kg`、`mg = 1e-6 kg`、`Mg = 1000 kg`。接頭辞はグラムを起点に数えます（回帰テストで固定）。
  **生成関数のパラメータは常に SI 基本単位**で、宣言内の接頭辞は可読性に影響するだけです——生成コードの doc comment は
  パラメータごとに換算係数を書き出します（実際の生成 doc comment からの逐語引用：
  `⚠ 参数 C_dl 声明为 µF：入参是 SI 基单位（1 µF = 0.000001 …）`）。
- **CGPM 2022 の接頭辞**も表にあります：`Q` (1e30)、`R` (1e27)、`r` (1e-27)、`q` (1e-30) を、既存の
  `da … Y / d … y` と並べて。
- **厳密な定義を持つ非 SI 単位**（`unit_base` が各係数を運ぶので `convert` は次元的に正直なままです）：`min`、`h`、`d`、`L`
  （または `l`。`mL` は `L` への接頭辞として分解されます）、`deg`、`arcmin`、`arcsec`、`bar`、`atm`、`eV`、`Wh`、`tonne`、`Da`（または `u`）、`nmi`、`knot`、`ha`、`acre`。
- **オフセット／対数単位は明示的に拒否されます**：`degC`（オフセット）と `dBm`（比）は接頭辞分割の前に止められ、
  「未知の単位」ではなく「真の原因」を報告します——これらを黙って K や無次元として扱うと**誤った値**を計算します。
  **曖昧な記号も推測せずに同じように拒否されます**：`cal` / `Cal` は熱化学カロリー（4.184 J）と IT カロリー（4.1868 J）で異なるため、どちらも
  `J` と書くよう促して拒否されます。`rpm` は角度軸を必要としますが（1 rpm = 2π/60 rad/s）、本機能は `rad` を無次元として扱うため、
  `2 * pi * f` を `[Hz]` 宣言と共に書くよう促して拒否されます。
- **無次元群（Buckingham Π）**：`dimensionless_groups` は**厳密な有理数**で消去し（`f64` はずれます）、
  「変数名 + 次元」から直接、基底の無次元な組合せを与えます。個数 =（変数の個数）− 階数（Π 定理がそのまま検査になります）。
  古典的な確認：`{rho, v, L, mu}` → 1 群 `rho·v·L·mu^-1`（レイノルズ数）。
  `dim_solve` は同じ連立方程式の非斉次な使い方です：`{kg, m/s²} → N` は指数 `[1, 1]` を与え、
  構成できない次元は「構成できない」と、あと何次元足りないかを報告します。

## 次元：半整数指数（2026-11-23）

`Dim` は内部で **1/2** 単位で保存されます（`[i16;7]` は真の指数の二倍を持つ）ので、分数べきと整数べきは
同じ整数演算を通ります：`√s = s^(1/2)`、`f^(-1/2)`、`Ω·s^(-1/2)` はすべて合法で、表示は `s^(-7/2)` のような
括弧形式を使います。したがって Warburg インピーダンスは `Z = σ·f^(-1/2)` という教科書の形に戻り、基準周波数による
無次元化は不要です。`dim_check` のべき指数は**先に定数を畳む**ので、自然な書き方 `f ^ (1/2)` は先に
`simplify` を呼ばずともゲートを通ります。

## 関数ファミリー：極値 / クランプ / 行列演算子（2026-11-23）

関数の引数個数（アリティ）の**唯一の真実の情報源**は `func_arity`（core 内）です。四つのレーン（アリティ検査 / 評価 / 次元 / 出力 / 書き戻し）は
すべてこれを参照します。以前は各レーンが独自の `match` を持っていて、それこそが「`arg` が実数レーンで存在しないメソッドとして出力される」問題が一つのリリースを生き延びた原因でした。

| ファミリー | 関数 | 注記 |
| --- | --- | --- |
| 単項スカラー | `exp ln log sqrt sin cos tan sinh cosh tanh` | 実数と複素で同じ表 |
| 複素数 | `abs arg conj re im` | `arg` は無次元。実数レーンでは re/im/conj は恒等 |
| 極値/クランプ | `min(a,b)` `max(a,b)` `clamp(v,lo,hi)` | Rust と同じ形：`v.max(lo).min(hi)`。三つの引数は同じ次元でなければならない |
| 行列演算子 | `det` `trace` `adjoint` `inv` | **具体的な行列リテラルだけを受け付けます**；`det`/`inv` は 4/3 次まで（2D と 3D のアイソパラメトリック要素の両方に十分）、`adjoint` = 共役転置 |

`det`/`inv` は**余因子の再帰**を使います（`det` ≤ 4、`inv` ≤ 3）：2D 三角形と 3D 四面体のアイソパラメトリック写像には十分で、
`J·J⁻¹ = I` と `det(J)=1` の数値チェック付きです。4×4 の逆行列は 16 個の 3×3 余因子
（約 100 項）を必要とし生成コードが膨れ上がるため、数値ライブラリへの誘導を添えて明示的に拒否されます。`det`/`trace` は `diff` で**微分の前に展開**されます——
展開結果はふつうの微分可能な式なので、FEM の `area = det(J)/2` は値と解析的導関数の両方を持ちます
（`∂area/∂x₂ = (y₃-y₁)/2`）。
`min/max/clamp` の区分選択は IR で表現できず（比較演算子がありません）、したがって**導関数は生成されません**。
生成コードにはその理由を説明するコメント行があります（もう panic しません）。極値とクランプは `f64::min/max` の NaN 規則に従います
（もう一方のオペランドを返すことがあります）。NaN の伝播を必要とする呼び出し側は境界で `is_finite` を確認してください。

## 組み込み形状の一覧

`identity` / `diag(d)` / `diag_v(d[i])` / `tridiag(a,b,c)` / `tridiag_v(b[i])` /
`bidiag_u(b,c)` / `bidiag_l(a,b)` / **`blockdiag2(p,q)` = diag(p·I₂, q·I₂)** /
**`banded(v, k)` = 半帯幅 k の対称帯行列**（k=2 は 5×5 以上でのみ一意。4×4 では密行列に退化します）。

これらの名前は**認識される IR の形状**を表すもので、数式から呼べる関数ではありません。入口は
省略記号付きの行列スケッチであり、認識できないものは明示的に拒否されます。

ブロック内のブロック対角の意味論 = スカラー × 単位行列（対角線上は p、ブロック内の非対角は空）、ブロックの外は空でなければなりません
（`0` と `...` は等価）。全体の次元が奇数なら中央のセルは右下のブロックへ回ります。

## 複素数レーンの性能：正直な側面（2026-11-23 実測）

`bin/bench.rs` は現在四つのレーンを測っています。複素数レーン Z_c（EIS 周波数掃引）は**手書きより遅い**ので、そのまま記録します：

| 形式 | ns/点 | 手書き比 |
| --- | --- | --- |
| 手書きの特殊化（`σ/√ω·e^{-jπ/4}`、分岐なし、ベクトル化可能） | 2.3 | 1× |
| 同形式の転写（生成コードの演算子列を一つのループへ写したもの） | 2.9 | 1.3× |
| 生成コード · スカラー直接呼び出し | 6.4 | 2.8× |
| 生成コード · バッチエントリ | 12.8 | 5.5× |

内訳：**汎用の複素 √/÷ は手書きの特殊化より約 2.2× 高く**（1 回の sqrt 対 3 回の sqrt + 除算一回）、
さらに**バッチラッパーで約 2.5× 余計にかかります**（タプルスライスへの書き込み + 分岐がループのベクトル化を妨げます）。

すでに行った最適化（どれも実際に差を詰めました）：

1. `__c_sqrt` を極形式（atan2+cos+sin、超越関数 4 個）から**代数的な閉形式**へ；
1. 純虚数の高速パス `√(iy) = √(|y|/2)(1+sign·j)`（sqrt わずか 1 回——EIS で日常的な形）；
1. `__c_div` は通常の大きさでは素直な形を使う（除算 1 回）；
1. 複素数の補助関数を**クロージャ**からブロックローカルの `#[inline(always)] fn` へ（15.5 → 11.9 ns/点）。

**結論（隠さず README に書く）**：複素数レーンは「正しく計算でき、十分速い」用途に向いており、
手書きの特殊化の限界を追う価値はありません。EIS 掃引の本当に熱いループでは特殊化を手書きし、数式は
`.formula` ファイルに**真実の情報源と次元検査**として残してください。実数レーンにはこの問題はありません（スカラー 1.11×、手書きと同等）。

## バッチエントリ：固定長が勝ち、スライスは負ける（実測）

ジェネレータは数式ごとに**二つ**のバッチエントリを出力します：

| 形式 | シグネチャ | 実測（BV、100k 点） |
| --- | --- | --- |
| スライス版 | `bv__batch(p0: &[f64], …, out: &mut [f64])` | 24.1 ns/点 = **スカラーの 0.82×（22% 遅い）** |
| 固定長版 | `bv__batch_n<const N: usize>(p: &[f64; N], …, out: &mut [f64; N])` | 19.3 ns/点 = **スカラーの 1.03×（3% 速い）** |

結論：**性能が欲しければ長さを型パラメータに入れる**ことです。スライス版の毎点八回の境界チェックはループ内にあり、
LLVM はそれらを完全には消せません。共通長を一度だけ計算する（`.min()` の連鎖）か zip イテレータに切り替えても 0.83× にしか届きません。
スライス版は便利な形（可変長データ）として残し、ホットパスでは固定長版を使ってください。
（ベンチのソース：`fixtures/three/src/bin/bench.rs`。私たちが踏んだ二つの方法論の罠——計時区間内でのベクトル構築と、
定数ベクトルによってスカラーパスが定数畳み込みされること——はソースコメントに記録されています。）

## 行列代数（形状 + 評価 + 生成）

次元と形状は**直交する二つの検査軸**です：次元は物理的な意味を、形状は代数的な合法性を司ります。

| 機能 | 挙動 |
| --- | --- |
| `shape_of` | 具体的な行列 → `(rows, cols)`；転置は交換；記号/パターン行列 → `None`（動的推論なし） |
| `shape_check` | 行列の加/減は同じ形状を要求し、行列積は `left cols = right rows` を要求、ギザギザ行列は拒否、行列の除算は明示的に拒否 |
| `eval_value` | スカラー/行列の統一的評価、行列積は `C_ij = Σ_k A_ik·B_kj` |
| `flatten_matrix_value` | **静的に展開可能な**行列式を行列 IR に畳み込む（転置/加/減/符号反転/スカラー放送/行列積） |
| 出力 | 畳み込まれた行列 → `vec![vec![…], …]` の定数リテラル。大きな行列はパターン行列 + ループのレーンへ |

```text
[1, 2; 3, 4] * [5, 6; 7, 8]  →  [[19.0, 22.0], [43.0, 50.0]]
[1, 2, 3]'                   →  3×1 column vector (emitted as vec![vec![1.0], vec![2.0], vec![3.0]])
A * [1, 2]                   →  scalar broadcast (a bare symbol is a scalar: matrices only come from literals/pattern generators)
[1, 2, 3] * [1, 2, 3]        →  compile-time rejection: matrix multiply impossible: (1, 3) × (1, 3)
```

> **汎用の実行時 `A,b` はやはりそのように宣言する必要があります**：`decl` の量が `_matrix`/`_vector` で終わる（または `matrix`/`vector` に等しい）
> 名前は行列/ベクトルのパラメータになり、下の実行時レーンはこれを使います。形状が宣言に含まれない行列への `A * x` は、リテラル、
> 静的に展開可能な式、またはパターンジェネレータで表現する必要があります。すべて*ほかの*裸の記号はスカラーです。
> 一般的な大規模 `Ax=b`、実行時のサイズ推論、悪条件の連立方程式には数値線形代数ライブラリを使ってください。

**非負整数の行列べき**：`[a, b; c, d] ^ 2` はジェネレータが明示的な行列積（0〜8 回）に畳み込みます。
`M ^ 0` は同じ次数の単位行列です（戻り値の型は依然として行列で、スカラーの `1` ではありません）。エンドツーエンドの数値検査は
`matrix_power.formula` にあります。畳み込みの失敗（負/分数べき、範囲外、非正方）は `compile_error!` を出します——
`vec![…] * vec![…]` のようなコンパイル上の事故にはしません。値レイヤー（`himari-eval`）は同じ形に対して同じ結果を与えます。

**二つの独立した実装が一致しなければなりません**：行列式のコード生成（`flatten_matrix_value` + リテラル出力）と
値レイヤーの評価（`eval_value`）は別々に書かれているため、**差分テスト**が両者を揃えています——
畳み込まれたリテラルの評価は、展開されていない式の評価とセルごとに一致しなければなりません（`mat-expr-fold`）。

**省略記号のない行列スケッチは具体的な行列です**：リテラルレーン（定数畳み込み、アロケーションループなし）を通り、
こちらがジェネレータより速いです。ジェネレータのレーン（`n` が実行時パラメータ）を使うには省略記号を書く必要があります。

## 実行時の行列/ベクトルレーン（2026-11-23）

上記はすべて静的です：形状は数式のコンパイル時に分かっています。実行時レーンは
**サイズが実行時にしか存在しないパラメータ**に対する別の答えです——ユーザーデータを消費するソルバ、FEM のアセンブリ、`A` と `b` を値として受け取るもの何でも。

- **宣言が唯一のスイッチ**：`decl` の量が `_matrix`/`_vector` で終わる（または `matrix`/`vector` に等しい）
  ものは行列/ベクトルのパラメータになります——`A : stiffness_matrix [N/m]` は `&[Vec<f64>]` として、`b : load_vector [N]` は `&[f64]` として渡されます。
  一度もオプトインしない名前はスカラーのままで、既存の数式には影響しません（`Decl::runtime_kind`）。
- **生成される関数は失敗可能です**：`Result<_, himari::runtime::NumericError>` を返し、構造化された単一のエラー型
  （`InvalidInput` / `ShapeError` / `NonFiniteValue` / `SingularMatrix` / `IllConditioned` / `UnstableResidual` / `NoRealRoots`）を使います。このレーンには
  **暗黙の NaN 契約はありません**。
- **`solve(A,b)`** は部分ピボット付き LU で、答えを返す前に二つの独立したゲートを通します：
  **rcond 推定**（`1/(‖A‖∞·‖A⁻¹‖∞)`、`rcond ≥ f64::EPSILON·64·n` を要求）と**相対残差検査**
  （`≤ 1e-9`）。逆行列は条件数推定のためにだけ作られ、`x` を得る手段として使われることは決してありません。特異なピボット、悪条件の行列、
  残差の大きい解は三つの別個のエラーであり、一つの「失敗」ではありません。
- **このレーンで他に使えるもの**：`inv`、`det`（リテラル引数のみ——実行時の `det` は次元に静的な行列次数が必要なため拒否されます）、
  `A*x`、`dot`、`norm`、および **1 始まり**の添字を使う `A(i, j)`（`[I,J]`。範囲外とゼロはパニックではなくエラーです）。
- **何を出力するか**：本体は生成関数内のスコープ内 `let` チェーンに対する検査付き式で、戻り値の型は
  値の種類に従います（`Result<f64, _>`、`Result<Vec<f64>, _>`、`Result<Vec<Vec<f64>>, _>`）。実行時レーンの数式は解析的ヤコビアンも、
  **`__f32` 変種も**、バッチエントリも出力しません（それらはスカラーでサイズのあるシグネチャを必要とするため）。
- **答えは独立した参照に対して検査されます**：`runtime_matrix.formula` は `solve(A,b)` を別のピボット付きガウス
  消去法に対して、`A*x` を `b` に対して、`A·inv(A)` を単位行列の列に対して、1 始まりの添字を、そしてピボットでしか正しく解けない
  意図的に極小の epsilon の連立方程式（`[[1e-17, 1], [1, 1]]`）を検証します——すべて 2e-12/2e-15 の許容差で。
- **マクロレーン**：`formula_matlab!` も実行時数式を受け付けますが、**一ブロックにつき一つの数式**だけです（実行時のチェーンは build.rs レーンに
  明示的なメッセージとともに留まります）。複素数の実行時行列パラメータは今のところ拒否されます。

## コード生成の品質（2026-11-23）

- **整数べきは `powi` を出力**：`x^3` → `(x).powi(3)`（以前は存在しない内部メソッドを出力していたため、
  どんな `x^3` も生成コードを指すエラーでコンパイルできませんでした）。fixture には `x^3` の**コンパイルゲート**があります。
- **未知の関数はコンパイル時に失敗**：実数レーンの関数はホワイトリストです。`arg(x)` は実数上で意味をなさないので →
  `compile_error!`。`re/im/conj` は実数上では恒等（近似ではなく厳密）です。
  複数引数の呼び出しは解析時に拒否されます（エミッタは `args[0]` しか見ておらず、残りを黙って捨てると誤った値を計算してしまうため）。
- **系のヤコビアン**：各 `.formula` ファイルはさらに `{filename}__jacobian(all params)` を生成し、
  行 = **微分に参加する実数スカラーの数式**（行列値 / 複素数 / 微分不可能な項目はスキップ）、列 = パラメータ（宣言順）、
  そしてパラメータに依存しない行はその列では一貫して **0** になります。これは陰的ソルバ / ニュートン反復 / FEM アセンブリが必要とする形です。
- **非有限の定数はハードに失敗**：`inf` / `NaN` を出力すると不正な識別子になるため、
  生成の前に発生源を名指ししてパニックします（`contains_nan_expr` が唯一の真実の情報源）。
- **べき乗の周りの括弧**：`(x^2)^3` と `x^(2^3)` は両方の表面で括弧が付きます——
  `x ^ 2 ^ 3` は `(x^2)^3` として再解析されるからです（x⁸ → x⁶、つまり正規の整形が**数学を変えてしまう**）。

## 整形（正規形）

`himari-fmt`：`cargo run -p himari-check --bin himari-fmt -- [--check|--write] <file>`。

- 複数行の decl（一行に一記号）；一行に一数式；**行列の列を整列**（各列 = 最も広い内容 + ≥1 空白、カンマが列の境界）。
- 独立したコメント行はすべてファイルの先頭に浮かびます（順序は保持）——コメントは人間のためのもので、IR には決して入りません。
- `--check` = ドリフトゲート（`just fmt-check` / CI に接続）；正規出力は往復で冪等です。
- **正規形はカンマを保ちます**：空白だけの区切りと二項減算は書き戻しで区別できないため（`-k` は減算項として飲み込まれます）、
  カンマが曖昧でない境界です。手でカンマなしで書くのは自由ですが、整形がカンマを戻します。

## レーン（2026-11-23 のユーザー裁定）

| レーン | 使い方 | 向いているもの |
| --- | --- | --- |
| **インラインマクロ** | `formula_matlab!{ decl { a : l [m]; b : l [m]; } a / b }` | 単純な数式 |
| **文字列マクロ** | `formula_latex!{ r"decl { … } \frac{a}{b}" }` | 単純な数式（LaTeX 表面） |
| **外部ファイルマクロ** | `formula_file!("formulas/bv.formula", matlab)` | 複雑な数式（方言を明示する必要あり） |
| **build.rs** | `packages/check/fixtures/three/` を参照 | リポジトリに入った生成コード + ドリフトゲート（正式レーン） |

マクロ内の `decl` は次元検査のための記号情報を提供するだけで、**Rust のローカル変数を作りません**：呼び出し側の `a/b` は
すでに呼び出し側が `let a = …; let b = …;` と書いていなければなりません。完全なコンパイル可能な例は
`inline_macro_example()`（`examples/common/src/main.rs` 内）を参照してください。

> ⚠️ 既知の制限：ファイルを読む proc-macro は **cargo に追跡されません**（`tracked_path` は依然 nightly）。
> そのため `.formula` を編集した後は再ビルドのトリガに `touch` が必要です。本番では build.rs レーン（`rerun-if-changed`）を使ってください。
> ⚠️ パターン行列/転置の**コンストラクタレーン**はファイル / build.rs にのみ存在します（ファイル名とジェネレータが必要）。
> インラインマクロがこれらに出会うと、誘導付きの明示的なエラーを報告し、決して黙って劣化しません。

## 表面言語（三つ、一つの IR）

| | 論文 | LaTeX | MATLAB スタイル |
| --- | --- | --- | --- |
| ギリシャ文字 | `α·x` | `\alpha \cdot x` | `alpha*x` |
| 省略記号 | `⋯ …` | `\cdots \vdots \ddots` | `...` |
| 行列 | `[a, ⋯, b; ⋮ ⋱ ⋮; c, ⋯, d]` | `\begin{bmatrix}…\end{bmatrix}` | `[a, ..., b; ...]` |
| 転置 | `A'`、`A′`、`A^T` | `A^T` | 左と同じ |
| 次元宣言 | `decl { v : velocity [m/s]; }` | 左と同じ | 左と同じ |

規則（拒否は機能です）：

- すべての記号はまず次元とともに宣言されなければなりません。未宣言 = コンパイルエラーで、字形的な推論はしません。
- `\sin^2 x`、`\left(\right)`、`$…$`、`x .* y` のような曖昧な、または純粋に組版的な記法は即座に拒否されます。
- 暗黙の乗算は LaTeX/論文の表面でのみ成り立ちます（単一文字の体系は構造上曖昧でないため）。MATLAB 表面は明示的な `*` を要求します。
- パターン行列は証明可能に正しい三つの形状のみをサポートします：`identity(n)`、`diag(d, n)`、
  `tridiag(a, b, c, n)`。認識できないもの = エラー + その三つの一覧。
- ソースは手書きでも構いません（結合文字など）。ただし **IR は正規化されていなければなりません**——結合文字は決して IR に入りません。

## ベクトル代数 / Horner / no_std（2026-11-23）

**`dot(a,b)` / `norm(v)`**：**具体的なリテラル**でのみ展開されます（形状はコンパイル時に既知）。
`dot` の次元は両辺の積、`norm` は要素と同じ次元です。`dot([x,y],[x,y])`（x=3,y=4）→ 25、
`norm` → 5。形状の不一致は即座に拒否されます。

**自動 Horner 変換**：ソースに `c₀ + c₁x + c₂x² + …` と書かれた**明示的な多項式**は、出力前に
`(…((cₙx + cₙ₋₁)x + …) + c₀)` へ変換されます——乗算回数は `2n-1` から `n` に減り、`x^n` のような大きなべきは消えます
（数値的により安定）。`a*x^3 + b*x` → `(a * x * x + b) * x`。
**コンパクトな形は展開されません**：`(u-1)^3` は書かれたままです（展開すると読みにくくなるだけ）。導関数も
**Horner 化前の元の式**に対して取られます（Horner 形を微分すると相殺する積の連鎖になるため）。

**`no_std` レーン**：`himari_buildhelper::generate_dir_libm` は `core` + `libm` だけを使うコードを生成します
（超越関数 → `libm::exp` など、整数べき → `libm::pow`。`f64::powi` は std のもの）。
これは**生成コード**が `no_std` で使えることを指し、2026-11-23 以降はコンパイル時のスタックも同様です：
`himari`、`himari-latex`、`himari-matlab` は `no_std + alloc` で、デフォルトの `std` feature の背後にあります（オフにしない限り `std` はオン）。
loader、buildhelper、macros、check の各クレート（ファイル IO、proc-macro ホスト、ツール）は `std` のままで、feature を明示的に有効にします。
生成コードは**自分自身の libm レーン**を保ち、ベアメタルの利用者が実際にリンクするのはそれです。
ゲート：`#![no_std]` の fixture クレート（`[lib] test = false`、テストハーネスが std を必要とするため）が生成コードをコンパイルし、**さらに**
std なしでパーサのチェーン（`himari_matlab::parse` → `dims_of_set` → `shapes_of_set` → `dim_check_runtime` → `format_set`）を演習します。
**`cargo build` の成功 = 生成コードとフロントエンドが密かに std に手を伸ばしていないこと。**
検証済みのベアメタルターゲット：`riscv32imc-unknown-none-elf`（core のみ——アトミクスは使えない）、`thumbv7em-none-eabi`、そして
`x86_64-unknown-none`（パーサのチェーン）。このレーンはヤコビアン（`alloc` が必要）も f32 変種も出力しません
（f32 の超越関数は libm の `*f` ファミリーで、私たちはレーンの半分だけを出荷することはしません）。偏微分には各数式の `__d_*` 関数を使ってください
（純粋なスカラーで、アロケーションゼロ）。

## ファイルをまたぐ数式ライブラリ：`use "..."`（2026-11-23）

```text
use "lib/atmosphere.formula"      % file header, may span several lines
decl { ... }
v_terminal = sqrt(2 * m * g / (rho * Cd * A))
```

- **解析は収集だけを行い、IO はローダーの仕事**：フロントエンドは純粋な文字列 API のままで（`FormulaSet.uses`）、
  ファイルの読み込み、再帰的インライン展開、循環検出、競合の解決は `himari-loader` が扱います。
- マージの意味論（単純で予測可能）：参照された decls/items は**先頭に置かれ** → 連邦はいつも通り機能します（後ろの項目は前の項目を参照できる）。
  同一の重複 decl は重複排除され、綴りが違えばエラー。項目名の重複は常にエラー（**「後勝ち」はなし**）。
  循環はエラーになり、循環の周りのファイル名の連鎖を出力します。
- **ライブラリは「呼ばれる」のではなく「置換される」**：`rho` が呼び出し側へ展開されると、パラメータリストには `rho_0 / h / H` が入ります。
  これは意図的です（隠れた状態がなく、静的に微分可能）。代償はパラメータリストが長くなることです。
- ディレクトリの慣習：`generate_dir` は**最上位**の `*.formula` だけを走査するので、`formulas/lib/*.formula` は
  自然にライブラリとしてのみ存在し、最上位の数式として二重に生成されることはありません。
- **方言はマクロから来るのであって、推測ではない**（2026-11-24 のユーザー裁定、「マクロが方言」）：数式を包むマクロが
  どの文法で読むかを決めます。

  | マクロ | 方言 |
  | --- | --- |
  | `formula!(…)` | **matex**（正規の表面。入口の名前は保たれ、意味論は決着済み） |
  | `formula_latex!(…)` | LaTeX |
  | `formula_matlab!(…)` | matex（`formula!` と同義だが、読んでいてより自明） |
  | `formula_file!("f.formula", latex)` | **必須の**第二引数で決まる |

  `formula_file!` は方言の引数を省略可能にしません：ファイルの中身をマクロ名から推論することはできず、マクロに推測させるのは
  曖昧さをどこか別の場所に隠すだけだからです。

  **これが単なる趣味でない理由**——これは実際の暗黙の誤った値を一つ取り除きます。`si` が宣言されているときの `si * x`：
  matex は `si·x` と読み、LaTeX は `s·i·x` と読みます。同じファイル、同じ入力（s=3, i=5, x=2, si=100）で実測：

  ```text
  old AUTO (try matex first, use if it succeeds)  →  200    without reporting any error
  explicit LaTeX                                  →  30
  ```

  両者は七倍近く違います。AUTO には作者がどちらを意図したかを知るすべがありませんでした——それが「推測」していたのは、単にどちらのパーサが先に成功したかだけです。
  だからこそマクロレーンの `Dialect` 列挙型には `Auto` のバリアントが**ありません**：型システムが推測の復活を保証で防ぎます。

```text
  src/generated.rs             % the checked-in generated code (reviewable, covered by the drift gate)
```

`cargo run -p himari-example-reentry` は速度→動圧→抗力の表を出力し、次を検証します：

- **物理的不変量**：`drag(v_terminal) == m·g`（相対差 1.6e-16——これは当てはめではなく定義です）
- **解析的導関数と差分商**：`∂drag/∂v` は二つの経路で 1.2e-8 の相対差で一致する
- **記号的求解**：`x_static` は `solve(k·x − F, x)` から得られ、`∂x/∂F = 1/k` が自動的に成り立つ
- **f32 変種**と**ライブラリをインライン展開した数式の系ヤコビアン**が同じ生成ファイルに含まれる

利用者は今や `himari-buildhelper::generate_dir(dir, out)` だけで済みます——build.rs レーン全体
（解析 / 連邦 / 次元 / 形状 / 導関数 / f32 / バッチエントリ / ヤコビアン / ソース LaTeX）が一つの関数に収まり、
プロジェクトごとに 300 行をコピーする必要はもうありません。

## 標準レーン：`himari-standards`（2026-11-23）

`packages/standards` は少数の**刊行された工学標準**を型付きの計算器にします。モジュール一つにつき条項レベルの関係が一つで、それぞれが
自分の `PROVENANCE`（標準 id、版、数式の出所の条項、そして*モデル化していない*もの）を持ちます。ここには標準の文章を引用する記述も、
標準への適合を主張する記述もありません——単に数式を普通の式として言い直しているだけです。単位換算は
意図的にありません：呼び出し側は SI 基本単位を渡します。

| モジュール | 標準 | 版 | 計算内容 |
| --- | --- | --- | --- |
| `iso_6506_1_2014` | ISO 6506-1 | 2014 | ブリネル硬さ `HBW`（および Pa 単位の平均圧痕圧力） |
| `iso_6892_1_2019` | ISO 6892-1 | 2019 | 引張強さ `Rm`、伸び率 `A`、弾性率 `E` |
| `iso_2533_1975` | ISO 2533 | 1975 | 対流圏の `T`、`p`、`rho` とジオポテンシャル変換（0 … 11 000 m。超えると外挿せず拒否します） |
| `gb_t_231_1_2018` | GB/T 231.1 | 2018 | ブリネル硬さ `HBW`；現行版で GB/T 231.1-2009 を置き換え、ISO 6506-1:2014 を修正して採用 |
| `gb_t_228_1_2021` | GB/T 228.1 | 2021 | 引張強さ `Rm`、伸び `A`、弾性率 `E`；現行版（2022-07-01 発効） |
| `gb_t_8170_2008` | GB/T 8170 | 2008 | 十進丸め、**銀行家丸め**（round-half-even）、十進文字列上で決定——`f64` は丸めの決定に一切関与しない |

二つの GB 機械試験モジュールは ISO の算術（同じ検証済みの評価）を再利用しますが、**独自の** id、版、出所を保つので、
応答に誤った標準のラベルが付くことは決してありません。`GB/T 228.1-2021` については、任意の ISO 文書の採用度を**独立に**
検証していないため、そのモジュールは同等性を明示的に主張しません——実装しているのは三つの定義だけです。版は
国家標準情報公共サービスプラットフォームに対して確認し、各モジュールはその確認を出所の注記に記録しています。

CLI `himari-standard` は一つのリクエストを評価し、形の安定した一つの応答文書（JSON）を出力します。リクエストは JSON または TOML として、
`--input <path>` から、または stdin から読み、`--format json|toml` でパーサを強制し、`--list` で正確な id と版を列挙します：

```bash
himari-standard --input packages/standards/examples/brinell.json
himari-standard --input packages/standards/examples/tensile.toml
himari-standard --list
```

`packages/standards/examples/` にあるこれら三つの例のリクエストはテストスイートが実際に実行するので、
文書に載った呼び出しが腐ることはありません。

未知のキーは無視ではなく拒否されます。すべての失敗は `values` を `null` にし原因を `errors` に入れた同じ文書を返します
（終了コード 1、stderr に一行の診断）。終了コード 2 はコマンドラインの誤用のために予約されています。小数が**丸めの決定**に関与する
リクエストはその数値を十進文字列として渡さなければなりません。二進浮動小数はクレートが見る前にすでに末尾の桁を失っているからです。

## 証明レーン：`himari-lean`（2026-11-23）

`packages/lean` は Lean 4 の**協調プロセス**です：自己完結した証明義務を生成し、stdin 経由で本物の `lean` 実行ファイルに渡し
（`lean --stdin --json -T <heartbeats> -M <MB>`）、起こったことを構造化文書で報告します。Lake プロジェクトもパッケージインデックスも
ネットワークもなく、生成されるファイルには import がありません。

- **動的データは*名前付きの例の定理文*のリテラル整数にしかならない**——データ定義、公理、識別子には決してならない。
- **カーネルで検査され、`decide` によって**：義務は `Int` 上で閉じ、`by decide` で解消されます。`native_decide`、`#eval`、
  `implemented_by`、`extern`、`partial`、`sorry`、ユーザー公理は出力されず、テストがその一覧に対して生成テキストを検査します。
- **公理ゲート**：`#print axioms` の出力を解析し、`propext`、`Classical.choice`、`Quot.sound` だけを許容します。読み取れない報告は
  違反であり、通過と見なすことはありません。報告がないことはきれいだという証拠ではありません。
- **独立したオラクル**：同じ行列式が Rust で*異なる*展開によって計算され、Lean が唯一の証人になることはありません。
- **`lean_missing` は一級の非成功**：ツールチェーンがなく、**何も検査されなかった**ことを意味します。これは「検証済み」として
  描かれることも、終了コード 0 で終わることも決してありません。ステータスと終了コード：`success` 0、`lean_missing` 3、`invalid_request` 4、`proof_failed` 5、
  `resource_exhausted` 6、`axiom_violation` 7、`oracle_mismatch` 8。

**本物のツールチェーンに対して検証済み（Lean 4.36.0、コミット `611c117b`）。** マイルストーンの義務はカーネルに受理され、公理を
一切報告しません：

```text
status = success            verified = true       exit = 0
lean_message: 'det3_example' does not depend on any axioms
oracle:       rust-i128-permutation det3([1,2,3,4,5,6,7,8,10]) = -3
```

負の対照は同じバイナリで設計どおりに振る舞います：`expected = -306` を主張するリクエストは `oracle_mismatch`（終了コード 8）を返し、
決して検証済みとして報告されません。スタブプロセスのテストスイートは `proof_failed` / `axiom_violation` / `resource_exhausted` の経路をカバーします。

プロビジョニングは本リポジトリの外にあり、一度きりです：`elan` を入れ、`leanprover/lean4:v4.36.0` を固定し、その後 `lean` を `PATH` に置くか
`HIMARI_LEAN_BIN` で指します。`just lean-verify` は義務を生成し、本物の Lean のテストを走らせます。**ツールチェーンがないとき、このレーンは
`lean_missing`（非成功）に縮退し、`--emit` はそれでもレビュー可能な `.lean` ファイルを書きます**——Lean の不在は検証として報告されることは決してありません。

## 堅牢性と敵対的入力（2026-11-23）

- **深さ制限 2048**：すべての解析出口が IR の深さを一度検査し（`check_depth`）、制限を超えるものは
  「formula nested too deeply (N levels > limit 2048)」と報告します。下流のどこかの再帰スタックが溢れる（SIGSEGV）のではなく。
  pest 自身のスタック制限も発火し、そのメッセージも平易な言葉に翻訳されます。**既知の境界**：長い鎖 `a + b + c + …` は
  IR で左結合の入れ子になるため、深さは項の数に等しくなります。したがって一つの数式の項数はおよそ 2048 に制限されます。
  別の決定的な括弧の入れ子ガード（256 段、`MAX_PARSE_NESTING`）が解析前に走ります。pest の
  オプションの `stack-guard` feature が使えない場所（`no_std`）でも成り立たなければならないからです。
- **不可視文字は常に拒否されます**：ゼロ幅スペース / 双方向制御文字 / ゼロ幅ジョイナ / BOM / NUL はすべて
  解析前に名指しで拒否されます（`scan_source`）——これらは数式を「レビュー時に見える姿と実際の姿を違える」ことができるからです。
- **Σ/∫ のステップ上限 10^7**：`Σ(i,1,1e9)` は「一晩走る」から一行のエラーになります。
- **引数が欠けた関数呼び出し**はもう `args[0]` の添字でパニックしません：三つのレーン（評価/出力/次元）がすべて明示的に拒否します。
- **構造化されたプロパティテスト**（ランダムな文字の寄せ集めではありません）：600 個のランダムな式がそれぞれ三つのゲートを通ります——
  正規形への書き戻しが**同じ木**に再解析されること、LaTeX への書き戻しが**同じ木**に再解析されること、そして `simplify` が**値を保つ**こと。
  三つとも現在までに不等価は 0 です（`prop-roundtrip`）。1500 項を合計する大きな入力も 100 ms 未満で完了します。

## 単精度（f32）レーン（2026-11-23）

すべての**実数スカラー**数式はさらに `{name}__f32(p: f32) -> f32` を生成します——同じ数式、
同じ出力規則で、リテラルだけが `f32` の接尾辞に変わります（`Fx::F32`、エミッタに通された唯一のスイッチ）。
実測 f32/f64 = **1.44×**（`SIMD` 8 レーン対 4 レーン + 帯域幅半分）で、
ゲームエンジン / オーディオ DSP / リアルタイム SDR が直接恩恵を受けます。

複素数と行列値の数式は f32 変種を**生成しません**：複素数レーンの `(f64, f64)` タプルと行列の
`Vec<Vec<f64>>` は単精度では別の型契約であり、それは後からでもできます（私たちはレーンの半分だけを出荷することはしません）。

三つの入口が一緒に出荷されます（すべて `himari-check` パッケージ内にあり、一つのパーサを共有）：

| 入口 | 目的 |
| --- | --- |
| `himari-fmt --diff` | 正規形と現行形の差分だけを表示（書き換えない） |

| `python3 scripts/fmt_check.py --fix` | 正規形への再レイアウト + サイドカーの再生成を一コマンドで |

**エラーはキャレットを伴います**：`FrontError::render_with_source` はソース行を出力し、問題の列の下に `^` を描きます
（三つのレーン——build.rs / fmt / eval——がすべてこれを通ります）——もう 17 列目まで自分で数える必要はありません。

**VS Code 拡張**（`packages/vscode`）には二つのチャネルがあります：

| チャネル | トリガ | データ源 |
| --- | --- | --- |
| CLI（既定、インストール不要） | 開く / 保存 | `himari-fmt --diagnose` + `--symbols` |

`himari-lsp` は手書きの最小サーバです（LSP フレームワークに依存しません）：`initialize` /

## LaTeX 表面：複数文字の名前には `\mathrm` が必要（2026-11-23）

LaTeX の数学モードでは、裸の `sigma` は**五つの掛け合わされた変数 s·i·g·m·a**（暗黙の乗算）なので、
この方言の複数文字の名前は `\mathrm{sigma_0}` と書かなければなりません——書き戻しも同じように出力します。
ギリシャ文字の名前（`sigma`、`omega`…）は**実際の字形** `\sigma` として書き戻され、下付きを保ちます
（`\sigma_0`）。実装はかつて部分文字列の置換だったので、`alphabet` が `\alphabet` に、`betamax` が `b\etamax` になり、
`sigma` が五つのイタリック体の文字として描画されていました——一度に三か所（ホバー / サイドカー / ドキュメントの真実の情報源）で誤りでした。修正済み（`latex_var`）。

## エラー：1 つの enum、9 言語

crate 内のあらゆる失敗は 1 つの enum `himari::Error` です。文字列の寄せ集めではなく、各失敗は
**データを伴う**バリアントなので、次の 3 つが同時に得られます。

- **安定したコード** —— `err.code()` は kebab-case の識別子（`dimension-mismatch`、
  `undeclared-symbol`、`no-real-roots` など）を返します。テストと利用者はコードを検証するので、
  文言の変更や翻訳で壊れることはありません。
- **言語ごとの描画** —— `err.render(locale)` と `Display`（英語）が
  [i18n.rs](packages/himari/src/i18n.rs) のカタログから文を生成します。CLI と LSP の境界では
  `HIMARI_LANG` / `LC_ALL` / `LANG` で選択でき、9 言語は組織の定めに従います
  （`en`、`zh-Hans`、`zh-Hant`、`ja`、`ko`、`fr`、`es`、`ru`、`ar`）。
- **`anyhow` 互換** —— `Error` は `core::error::Error`（`std` では `std::error::Error`）を実装し、
  `Send + Sync + 'static` でもあるため、ラッパーは不要です：

```rust
  use anyhow::Context as _;

  fn run() -> anyhow::Result<f64> {
      let dim = himari::parse_unit("N/m")?; // `?` converts automatically
      let e = himari::Error::NoRealRoots { discriminant: -4.0 };
      let err = anyhow::Error::from(e).context("solving the loop equation");
      let root = err.downcast_ref::<himari::Error>().expect("root cause kept");
      assert_eq!(root.code(), "no-real-roots");
      assert_eq!(dim, himari::parse_unit("kg/s^2")?);
      Ok(1.0)
  }

  fn main() {
      assert_eq!(run().unwrap(), 1.0);
  }
```

`tests/anyhow_compat.rs` がこれらをすべて固定します。`?` による伝播、`Send + Sync + 'static`
境界、`anyhow::Context` を経た後でも `downcast_ref::<himari::Error>()` でコードを取り戻せること、
そして「同じエラーが 9 言語で異なる描画になり、コードは常に同一」であること。

未登録のメッセージは `Error::Message(String)` に残ります。どの言語でもそのまま出力されるため、
段階的な移行が**型として**見えます（翻訳済みのふりをしません）。この負債は**文章ではなくゲート**で測ります：`python3 scripts/staging_budget.py` はワークスペースの全生産ツリー（`packages/`、`examples/`、`tools/`）内の未カタログ化プロデューサー（`Error::from(`、`Error::Message(`、フロントエンドの `FrontError::plain("…")` / `plain(format!(…))` / `FrontError::new(…, "…")`）を、テストとカタログ自身を除いて数え、記録された上限（現在 175）を超えると失敗します。ゲートは AST 走査（`tools/staging-budget`、`syn` 基于）で、行構成・空白・コメントに依存せず、`matches!(e, Error::Message(m) if …)` のような**パターン**が構築と誤判定されることはありません。上限は下がるだけで、それは強制されます：CI は `--against-git` でゲートを実行し、`HEAD` の `tools/staging-budget/src/ceiling.txt` を読み、作業ツリーの上限がより高ければ失敗します。全 38 変体は `catalogue_completeness_tests` が固定します——各変体を構築し 9 言語で描画します（空でない、`{n}` の漏れなし）。LSP のクイックフィックスの*タイトル*はまだ中国語です；診断はローカライズ済みです。

```text
python3 scripts/staging_budget.py                # counts + ceiling
python3 scripts/staging_budget.py --against-git  # also: the ceiling may only go down vs HEAD
```

### エディタ統合（LSP）

`himari-lsp` は手書きの LSP サービスです（プロトコル層は純粋関数で、単体テスト + エンドツーエンドの stdio テスト付き）：

| 機能 | 説明 |
| --- | --- |
| 診断 | `didOpen`/`didChange` の後で `publishDiagnostics` をプッシュ（未宣言の記号、次元の不一致、構文エラー） |
| 補完 | ファイルの `decl` 名 + 数式名 + 単項関数表（`det/inv/solve/roots/...`） |
| **クイックフィックス** | `textDocument/codeAction`：未宣言の記号 → ① 最も近い宣言済みの名前に綴りを直す ② decl ブロックに一行追加；関数名の綴り間違い → レジストリの名前 |
| 同期 | **インクリメンタル同期**（`textDocumentSync: 2`、範囲でスライス）；全体変更も受け付けるので古いクライアントも壊れない |

クイックフィックスは名前が**ちょうど一度だけ**現れるときにのみ置換を提案します（複数回現れるときは「宣言を追加する」だけを提案し、
どの出現かは決して推測しません）。範囲外の値は変更を捨てるのではなく常に**クランプ**されます（一つ捨てると
バッファがエディタと恒久的にずれてしまうからです）。

### 数式ライブラリの内容ロック：ライブラリが変わったら声をあげなければならない

`use "lib/…"` はライブラリファイルを**インライン展開**するので、ライブラリが変われば下流の生成コードも一緒に変わります——まさに
最も見落としやすい種類の回帰です。`--lock` は参照されるすべてのファイルの指紋を `<entry>.lock` に書き、以後**ロックはロードのたびに検証されます**：

```text
$ himari-fmt --lock formulas/entry.formula
已写入 formulas/entry.formula.lock（4 行）

$ himari-eval formulas/entry.formula         # someone quietly changed the library
himari-eval: 公式库与锁文件不一致（formulas/entry.formula.lock）：
  内容变了（声明版本 1.4.2 → 2.0.0）：lib/atmosphere.formula
              复核改动后运行 `himari-fmt --lock <入口>` 重新生成锁。
```

（CLI の出力は逐語引用です：ツールは依然として中国語で出力します。英語にすると、ライブラリとそのロックファイルが食い違っており——
`lib/atmosphere.formula` の宣言版が 1.4.2 → 2.0.0 に変わった——変更をレビューした後に
`himari-fmt --lock <entry>` を再実行する、という意味です。）

- **sha256 の内容ハッシュ**（semver の範囲ではない）：「インライン展開されたソース」のような依存の形では、内容ハッシュのほうが
  強い保証です——どんな変更も捕まえられ、バージョン解決のポリシーも事前リリースの規則も要りません。
- **プレーンテキスト、決定的、パスはエントリディレクトリからの相対**：git に入れられ、差分が読め、マシンをまたいで比較できます。
- **閉じたゲート**：`scripts/fmt_check.py` は `--lock-check` を `.lock` を持つファイルに実行します
  （`--fix` の下では自動的に再ロックもします）——古いロックは誰かがファイルをロードするのを待たずにゲートで赤になります。
- **オプトイン**：`.lock` がなければ何も検証されません（既存リポジトリへの影響はゼロ）。一度ロックがあれば、**新しい参照も失敗します**
  （ホワイトリストの意味論）。受け入れるには再ロックしてください。
- **読めないロックも失敗です**：UTF-8 でない（エディタが UTF-16 で保存した）、権限不足、ディレクトリのパスは
  すべてハードエラーです——これらを「ロックなし」と見なしては決してなりません。そうすると保護が黙ってオフになってしまいます。
- **`--fix` は三つの段階**（まず全部を整形 → 次に全部を再ロック → 最後にすべてのサイドカーを再生成）：
  サイドカーはロード時にロックを検証するので、ロックが先に確定していなければなりません。両方とも参照ライブラリの最終的な内容にも依存するので、
  それらを一つのループに混ぜると古い成果物が残ります。
- `%! version: 1.2.0` は人間が読むための列にすぎません（ロックされ、版が変われば報告されます）。意味論的な保証はハッシュにあります。
- semver の範囲を使わない理由：解決・固定・事前リリースのポリシー一式が必要になる一方、本リポジトリの依存の形は
  「インライン展開されたソース」です。「小さな漂流を許す」ことを表すには、再ロックがより直接的な表現です。

### 方言ディレクティブ：ファイルレーンにおける「マクロが方言」の対応物

ファイルにはそれを包むマクロがないので、対応する規則はこうです：**既定は matex、LaTeX は明示的に宣言する。** 両方のレーンは一つの原則を共有します——
推測はしない、意味論を決めるのは（パーサではなく）作者です。

```text
%! dialect: latex
decl {
    s : d;
    i : d;
    si : d;
    x : d;
}
q = si * x        % LaTeX semantics: s·i·x (not the declared si·x)
```

- `%! dialect: latex`（または `tex`）と `%! dialect: matex`（または `matlab`）をサポートします。
- **ディレクティブなし = matex**。かつてここには AUTO のフォールバック（matex の解析が失敗しソースに `\` があれば LaTeX を試す）があり、
  それがまさに上の 200 対 30 の暗黙の誤った値を作り出していました——削除済みです。
- 方言ディレクティブのない LaTeX 専用の記法 → 既定の matex として解析 → **エラー**（暗黙の誤った値には決してならない）。
  エラーは出口を示しますが（`%! dialect: latex` と書く）、**あなたの代わりに推測はしません**。
- **最初のコメントでない行より前**にのみ効きます（本文中のコメント内の `%!` は方言を変えません）。
- 認識できない値はエラーです。
- ディレクティブがあると、エラーはその方言で報告されます：LaTeX ディレクティブの下での構文エラーは LaTeX のエラーです。
- ちょうど一か所（`himari_loader::parse_source`）で実装されているので、build.rs レーン、`himari-fmt`、
  `himari-eval`、LSP の診断はすべて一致します。（LSP の診断は `HIMARI_LANG` が選んだ言語で描画されます。「エラー」の節を参照。）

### LaTeX 表面の除算（かつて欠けていたもの）

`a / b` と `a \div b` は本物の除算になり、`\frac{a}{b}` と同義で、乗算と同じ優先順位を持ち左結合です。
以前は LaTeX 表面に**除算演算子がまったくありませんでした**——`\frac{a}{b}` だけが受け付けられ、`a / b` は構文エラーでした。
それは赤ん坊を風呂の水と一緒に捨てるようなものでした：`/` は除算を書く最も普通の方法であり、それを拒否する理由はありませんでした。
（上の AUTO のフォールバックは実はこの欠陥を覆い隠していました：`a / b` を「たまたま動く」ようにしつつ、暗黙の誤った値を一緒に持ち込んでいたのです。
欠陥を直せば、フォールバックに存在する理由はありません。）

## 記号的線形求解 `solve`（2026-11-23）

単一変数の形 `solve(equation, variable)` は `equation = 0` を `variable = -b/a` として解きます（方程式はその変数について**線形**でなければなりません）。

```text
ES_ss = solve(k_on * E * S - (k_off + k_cat) * ES, ES)
      → ES_ss = k_on·E·S/(k_off + k_cat)          % Michaelis–Menten steady state
```

- 解は**依然として IR です**：したがって次元検査、評価、コード生成、解析的導関数、
  ヤコビアンを保ちます——二つ目の仕組みは要りません。`ES_ss` の偏微分とヤコビアンの行は自動的に出てきます。
- **パラメータリスト = 出力される式が実際に使う変数**：解かれた `ES` は `ES_ss` のパラメータに現れません
  （「求めているのに渡さねばならない」は修正済み）。サイドカー / ホバー / 補完は同じパラメータリストを読みます。
- **非線形性は明示的に拒否されます**：`x·x`、`1/x`、`x^2`、`sin(x)` は**解析の出口で**エラーとなり、関与する種類を名指しします。
  数値近似も、疑わしい答えもありません。化学的な定常状態を間違える代償は、数文字余計に打つよりもはるかに大きいからです。

### 連立方程式の形 `solve([equations…], [unknowns…])`

両方の引数がリストのとき、**線形連立方程式**のレーンに入り、解は**列ベクトル**になります（行列式の値レーンで、
`Vec<Vec<f64>>` を返します）：

```text
x = solve([(k1 + k2) * x1 - k2 * x2 - F1,
           -k2 * x1 + (k2 + k3) * x2 - F2], [x1, x2])
  → x = 2×1 column vector, dimension [m]           % two-mass spring statics
```

- **記号的消去**：ガウス–ジョルダン消去は**式の環**上で走ります（係数は数ではなく IR の部分式です）。
  各ステップで正規形に簡約されます。解かれた各成分は依然 IR で、いつも通り次元/評価/出力を通ります。
  **しかし連立方程式の解は行列値です**：行列値の数式は解析的導関数を生成せず（要素ごとの偏微分は行列ではなく、ヤコビアンのほうが行列です）、
  f32 変種も生成しません——それは `solve` 固有ではなく、行列値レーンに既存の制限です。
- **形状の慣習**：方程式と未知数のリストは行優先で**平坦化**されるので、`[e1, e2]` と `[e1; e2]` は等価です——
  利用者は向きを覚える必要がありません。未知数のリストの要素は裸の変数名でなければなりません。
- **未知数には宣言された次元が必要**：それで得られるのは**結果の次元の検査**（ばねの例は `m = N/(N/m)` を解きます）と、
  方程式そのものの**斉次性**の検査（`x1 − F1`、m を N に足すのは解析時に拒否されます）です。
  解かれた未知数はパラメータリストに入りません（生成関数は実際のパラメータだけを受け取ります）。
- **拒否は機能です**：劣決定（フルランクでない）、矛盾（消去後に `0 = nonzero`）、非線形（未知数が乗算の両辺に現れる /
  分母や指数の中 / 関数の引数の中）は**すべて解析の出口で報告されます**。
  次元に関する拒否は `dims_of_set` / 生成段階で起こります（パーサ自身は次元検査をしません）。
  冗長な方程式は「畳み込める意味で」取り除かれます：記号的な係数を持ちゼロに畳み込めない冗長行は、保守的に
  矛盾として報告されます——間違った解を返すより、断るほうがよい。
- **ピボットの非消滅と数値的な境界**：単一変数の `solve` と同じ慣習で、ゼロと証明できないものは非ゼロとして扱います
  （`a ≠ 0` を信頼します）。消去はコンパイル時に式の順序で起こり、**実行時に |ピボット| で行を並べ替えません**。
  極端なスケールでは閉形式が打ち消し、特異なパラメータは値レイヤーでゼロ除算を報告し、生成コードでは IEEE に従って `inf/NaN` になります
  ——それは例外ではありません。悪条件の系、またはピボット戦略が必要な系は数値ライブラリへ回してください。
- **境界（四つ。すべて解析の出口で、またはコンパイル時エラーとして拒否されます）**：

  1. **行列値**の係数または定数項（`solve(M*x - b, x)`、`solve([M*x - b], [x])`）→ `inv(A) * b` への誘導を添えて
     明示的に拒否されます——そうでないとスカラーレーンが `vec!` の除算を生成し、コンパイルが通りません。
  1. **方程式は異なる次元を持ってよい**（N の力の釣り合いと m の幾何拘束が一つの系に共存するのは合法）が、各方程式は
     それ自体で斉次でなければなりません。そして解の各成分は**一つの次元**を共有しなければなりません（電流と抵抗を同時に解くような
     混合次元の未知数はまだサポートされていません。それは行列値レーンの制限です）。
  1. 複素数レーン（`j` を含む）は**値レイヤー**と**出力レイヤー**で動きます（2026-11-23 に完成）：複素数の列ベクトルは
     `Vec<Vec<(f64, f64)>>` として出力され、要素は（実部, 虚部）です。交流回路の節点解析や EIS 風の「複素連立方程式」は
     したがって直接コードに生成できます。
  1. **冗長行のゼロ判定は十分条件です**：同類項のまとめで証明できるゼロ（`k−k`、`k·a−a·k`、`x·x²−x³`）は
     認識されます。ゼロと証明できない複雑な恒等式は非ゼロの係数として扱われます（保守的で、劣決定/矛盾を誤って報告することが
     ありますが、間違った解を返すことはありません）。

### 多項式の根 `roots(poly, x)`

`solve` は線形の閉形式を与え、`roots` は**多項式のすべての根**を与えます（列ベクトルとして）：

```text
roots_quad = roots(a * x ^ 2 + b * x + c, x)
% q = −(b + sign(b)·√(b²−4ac))/2; large root = q/a, small root = c/q
% Return order still matches the original formula (−b−√Δ first); it does not depend on sorting the roots by size.
```

- **1〜2 次だけ**：1 次は `solve` と同じ数学、2 次は閉形式の根の公式です。
  **3 次以上は明示的に拒否され**、実際の次数が報告されます——Cardano/Ferrari は浮動小数で条件数がひどく悪いので、
  本リポジトリは「精密に見える」近似を渡すことはしません。3 次以上の根は、まず係数を数値で計算してから
  数値ライブラリを使ってください。
- **重根は重複度の分だけ繰り返されます**（`x² − 2x + 1` は二つの 1 を返す）。代数学の基本定理と一致します。
  ゼロの根に対する `q=0` のフォールバックは `-b/(2a)` で、`0/0` を通りません。
- **二次公式での打ち消しの回避**：`(−b±√Δ)/(2a)` をそのまま使うと `b²≫4ac` のときに小さい根が失われます
  （`x²−10⁸x+1` はかつて `10⁻⁸` を約 `7.45×10⁻⁹` と計算しました）。今は安定な `q/a` と `c/q` を使い、生成コードにおける
  小さい根の相対誤差の合格ラインは `1e-12` です。両方の符号方向と複素数レーンに回帰テストがあります。
- **次元は自動的に出てきます**：方程式は次元的に斉次でなければならず、斉次性は直接「根の次元 = 変数の
  次元」を意味するので、余分な次元の導出は不要です（契約テストがこの推論を守っています）。
- **実数レーンでの負の判別式**：生成コードは型付きのエラーを返し、**NaN ではありません**——実数の二次 `roots` 入口は今
  `Result<_, himari::runtime::NumericError>` を返し、負の判別式は `NumericError::NoRealRoots { discriminant }` です。もう暗黙の
  NaN 契約はないので、`is_nan`/`is_finite` の確認はもはやこの状況を検出する方法ではありません。コンパイル時に負と証明できる
  定数の判別式は依然として即座に拒否されます。`eval_value` は汎用の複素数値レイヤーであり、複素数レーンにおける同じ式に対して
  **なお複素数の根を返します**。複素数レーンには明示的な `j` が必要です。
- **打ち消される高次の項は取り除かれます**：`x³ − x³ + x − 1` は 1 次として扱われます（「多項式に x³ が現れるから拒否」ではありません）。
- **非多項式は明示的に拒否されます**：`x` が関数の引数の中、分母の中、非整数のべきにある——それぞれ理由を添えて。
- **行列値の係数**は拒否されます（`solve` と同じ慣習で、そうでないとスカラーレーンが `vec!` の除算を生成します）。

### 係数ベクトル `poly_coeffs(poly, x)`

`roots` の補完：**係数**を（低次から高次へ）返し、`1×k` の行ベクトルを返します。

```text
coeffs = poly_coeffs(2 * s ^ 2 - 3 * s + 1, s)   → [[1, −3, 2]]
```

- **変数は無次元でなければなりません**。斉次多項式の k 次の係数の次元は `dim(poly)/dim(x)^k` で、それらは互いに異なります。
  しかし行列は**一つの次元の要素**を必要とします——したがって次元を持つ変数の係数を取ることは、その形では代数的に不可能です。
  この検査はそれを診断段階で直接説明し、出口を示します（特性量で割るか、`roots` を使う）。下流に
  「行列要素の次元が異なります」と報告させるのではなく。
- 高次のゼロ係数は取り除かれます（`x³ − x³ − 2x + 1` は 1 次）。ゼロ多項式は拒否されます。
- 非多項式（`sin(x)`、`1/x`、非整数のべき）は拒否されます。
- `poly_coeffs` という同じ抽出器を `roots` と共有します——係数の意味論の定義は一つ、利用者は二つ。

### 3 次より上の根：`himari-eval --roots`

言語で ≥ 3 次を拒否するのは避けられないトレードオフですが、**数値的**な根の探索はどの次数でも動くので、それはツール層に置かれます：

```text
$ himari-eval cubic.formula --roots
cubic = 1, 2, 3  [1] (degree 3, 3 roots)
cplx  = -1, 0.5-0.8660254037844387j, 0.5+0.8660254037844386j  [1] (degree 3, 3 roots)
```

- **Durand–Kerner 反復**（複素数の演算に core の `C` を再利用し、サードパーティの数値ライブラリは使わない）：初期値は
  `0.4 + 0.9j` のべき、半径は**根の大きさの幾何平均** `|c₀/cₙ|^(1/n)`（退化した場合のみ
  Cauchy 限界 `1+max|cᵢ|` に退避）。反復は最大 1000 回。DK の判定は `|Δz| ≤ 1e-10·radius`
  （1 ではなく根の大きさに対する相対値）。続いて**ニュートン研磨 60 ステップ**（相対停止判定 `1e-15·|z|`）。
- **非収束はエラー**であり、まだ収束していない近似を結果として返すことは決してありません。反復中の `inf`/`NaN` も即座のエラーです
  （`f64::max` は NaN に対して反対側を返すため、かつて NaN のステップが「収束した」ように見え、20 個の NaN を返しました）。
- **残差の受け入れ**：反復後、相対後方誤差 `|p(z)| / Σ|aₖ|·|z|ᵏ` が十分小さくなければなりません（しきい値 1e-8）。
  そうでなければエラーです——DK は根への収束を保証せず、判定は反復そのものから独立していなければなりません。
  分母は**`k=n` の項を含まなければなりません**：それがなければ定数 `|a_n|` は小さい `|z|` での分母になり、
  `x²−1e-100` が 4e25 倍も間違っているのに通ってしまいます（実際の回帰）。
- **ニュートン研磨**（相対判定）：単根は機械精度に達します。**重根は線形にしか収束しない**ので、`x²−2x+1` の類は
  `1e-9` 程度の相対誤差を持ち、エラーになりません——それはアルゴリズムの性質でありバグではありません。重根を
  単根として扱わないでください。
- **次数制限 16**（`poly_coeffs` の多項式展開の制限。`numeric_roots` 自体は最大 64 まで対応）。
- 反復の前に **monic 正規化**（最高次の係数で割る）を行い、大きさのオーバーフローを避けます。次数制限 64。`inf`/`NaN` の係数は拒否されます。
- **ノイズのゼロ化は虚部だけを消し、判定は相対的です**：実根は `1e-16` 規模の虚部の残りを持ちますが、それは
  反復の副産物です。判定は `|im| ≤ 1e-12·|z|`。**実部には決して触れません**（`x²−1e-50` の根は ±1e-25）し、
  **絶対的なしきい値もダメです**——大きさが 1e-12 未満の複素根では、虚部がその根の情報の全部です
  （`x³−1e-60` はかつてそれで三つの実根に潰され、相対誤差 0.87 で、エラーも出ませんでした）。
- 係数は `--set` で与えられたパラメータの下で数に評価されなければなりません。変数を省略したときは「数式内で宣言された唯一の
  記号」として推論され、候補が複数あるときは `--var` が必要です。
- 出力には次数と根の個数が付きます。複素根は `a+bj` と書かれます。

## 複素行列と複素連立方程式（2026-11-23）

複素性はスカラーだけのものではありません：行列の要素と解のベクトルも複素数になり得ますし、**値レイヤーと出力レイヤーは一致します**。
生成関数の戻り値の型は `Vec<Vec<(f64, f64)>>`（要素 =（実部, 虚部））：

```rust
// I = solve([Z*I1 - V, Z*I1 - R*I2], [I1, I2]) with Z = R + jωL
pub fn I(R: f64, w: f64, L: f64, V: f64) -> Vec<Vec<(f64, f64)>> { … }
```

- 典型的な用途は**交流回路の節点解析**と EIS のモデリング：未知数は複素数の電流/電位です。
- 転置は**単なる転置**（共役なし）——共役は別の `conj` 演算子です。混同しないでください。
- `adjoint` は共役転置で、形状がコンパイル時に分かるリテラルだけが展開できます。
- 複素数レーンでは `det/trace/adjoint/inv/solve/roots/dot/norm` も**同じように**出力前に IR 層で展開されます（歴史的な非対称：
  実数レーンは展開したのに、複素数レーンは `compile_error!` へ直行していました）。
- まだ未サポート：複素数数式の **no_std/libm レーン**（クロージャが std に依存）、複素数数式の**解析的導関数**
  （`abs/arg/conj/re/im` は複素解析的ではないので Wirtinger 微分が必要）、複素数数式の **f32 変種**。

## WGSL（GPU）レーン：サブセット + 検証の境界（2026-11-23）

`himari-fmt --wgsl <file.formula>` は実数スカラーの数式を f32 カーネルとして出力します：

```wgsl
// Generated by himari (f32 scalar lane; really compiled and validated by naga)
fn q(rho: f32, v: f32) -> f32 {
    return 0.5f * rho * (v * v);
}
```

**サポートされるサブセット（意図的に小さい）**：`+ - * /`、`sqrt`、`exp`/`log`（本リポジトリの `ln`）、`sin cos tan
sinh cosh tanh abs min max clamp`、それに 2/3 乗、平方根、-1 乗。
**明示的に拒否**：複素数（`j`）、行列、`det/inv/solve`、Σ/∫、記号演算子、その他のべき、
そして WGSL の予約語と衝突する記号——それぞれ理由付きで（コンパイルできないカーネルは出力しません）。

**検証は二層です**（2026-11-24 以降、WGSL レーンは**コンパイラレベル**の証拠を持ちます）：

1. **本物のコンパイルゲート**（権威）：`cargo test -p himari-check --features wgsl-compile`
   が fixture 内のすべての出力カーネルを **naga**（wgpu のシェーダコンパイラで、WGSL 仕様の権威ある実装の一つ）に渡し、
   本物の解析 + 本物の検証を行います。naga は純粋に CPU の dev-dependency で——**GPU は不要**、実行時の依存ツリーにも決して入りません。
1. **静的ゲート**（高速なふるい分け、`wgsl::validate_wgsl`）：括弧の対応、`-> f32` のシグネチャ、ちょうど一つの
   `return`、`f` を伴う浮動小数リテラル、`^`/`**` の不在、非有限定数の不在。その価値は「naga のない環境で粗い誤りを捕まえる
   + よりこのレーンに近いエラーメッセージ」で、**正しさの証明ではありません**。

**本物のコンパイルゲートが必須な理由——具体的な教訓**：この WGSL レーンのカーネルは、かつて一つ残らず**無効でした**。
WGSL には式本体の関数がなく、本体は `return expr;` でなければならないのに、エミッタは常に裸の式を出力していました。
さらに悪いことに、静的ゲートは `return` を**禁じて**いました——仕様のその部分を知らずに規則が書かれたため、誤解が
「規則」になってしまっていたのです。静的ゲートの構造的な盲点は「見落とす」ことではなく、「**何を見落としたかを知らず、
正しいコードを誤りと判定することさえある**」ことです。最初の naga の実行がそのクラス全体を露わにしました。
もう一つ訂正された信念：`return 2.5;` は naga では**合法です**（抽象浮動小数は文脈によって f32 に着地する）——したがって
「浮動小数は `f` を伴わなければならない」はこのレーンのスタイルの慣習であり、WGSL 仕様ではありません。

**検証の境界（正直に述べる）**：naga は**構文と型**だけを検証します。「カーネルが本物の GPU 上で正しい数を計算するか」はまだ
未検証です——それには wgpu のランタイム + GPU が必要です（node-3 に RTX 5880 があり、接続待ちです）。
また tint（Chrome/Dawn の実装）と naga は少数の境界規則で異なり、本リポジトリは naga にのみ責任を負います。

## 主張していないこと

これらはスコープの限界であり、もうすぐ終わる ToDo リストではありません。「主張していない」と書いてあるところでは「主張していない」と読んでください。

- **記号レーンに実行時のピボットはありません**：記号 `solve` は式の順序で消去し `a ≠ 0` を信頼します。ピボットの大きさで
  行を並べ替えることはしません。悪条件の系やピボットに敏感な系は実行時レーン（上の `solve(A,b)`）か数値ライブラリの領分です。
- **パターン行列はファイルレーン経由のみ**：パターン行列のコンストラクタレーンはファイル名とジェネレータを必要とするので、インラインマクロは
  誘導を添えて拒否します。任意のパターン行列の自動的な展開はありません（研究レベルで、内蔵の形状の外にあるものはサポート一覧を添えて
  明示的に拒否されます）。
- **WGSL の数値検証はまだ保留中**：naga は構文と型を証明しますが、カーネルが GPU 上で正しい数を計算することは証明しません。ここでは GPU での実行は一度も行われていません。
- **Lean の検証は成功していません**：このホストにはツールチェーンが入っていないので、走ったのはスタブプロセスのテストだけです。Lean が
  生成された証明義務を受け入れるという主張はありません。
- **`publish = false` は人手レビューのゲートです**：クレートは人手レビューが解除するまで意図的に公開できません。ステータスを参照。
- **`no_std` の範囲**：`himari`、`himari-latex`、`himari-matlab` は `no_std + alloc` です。loader/buildhelper/macros/check のクレートはそうではありません。
  生成コードは自分自身の libm レーンを保ち、複素数数式は `no_std` レーンに含まれません。
- **複素数の解析的導関数はなく、複素数や行列値の数式の f32 変種もなく、行列値の数式の解析的導関数もありません。**
- **`roots` は言語内では 1〜2 次だけ**です。より高次は `himari-eval --roots` で数値的にのみ可能です。
- 一般的な LaTeX（マクロ/catcode/組版）——意味論は決定不能で、組版は描画レイヤーの仕事です。
- 字形からの意味論の推論はせず、MATLAB 表面での `xy` の乗算もありません。`\sin^2 x` なし、`.*` なし、`$…$` なし（曖昧な、または純粋に
  組版的な記法：解析と描画は二つの異なる仕事で、一つのパーサが両方をすべきではありません）。
- リアルタイム/安全クリティカルな経路での実行時 JIT はなく、AGPL 依存は決して入れません（evalexpr ≥12 などは外です）。
- **`himari-standards`** のモジュールは条項レベルの計算器で、**適合性の主張ではありません**：試験片の形状、力の水準の選択、
  保持時間、不確かさの予算、標準自身の報告規則をモデル化しておらず、汎用の単位ライブラリでもありません。
- **`himari-lean`** レーンは一つの小さな閉じた整数の義務（3×3 行列式の例）を証明します。それは汎用の定理証明器ではなく、その公理
  ゲートは Lean 自身の出力を解析するパーサであって、健全性の議論ではありません。
