## Что это

- Вы пишете **одну** формулу (подмножество LaTeX / нотация из статьи / стиль MATLAB — на ваш выбор); она понижается в один и тот же
  **размерный IR**, а затем компилируется в функцию на Rust с именованными промежуточными значениями и комментариями в исходнике.
- Размерности (семь основных величин kg·m·s·A·K·mol·cd) проверяются на этапе компиляции: `m + s` просто не компилируется.
- Символьное дифференцирование, CSE и свёртка констант встроены; аналитические частные производные закреплены тестами против центральных разностей.
- **Матрицы — полноправные значения**: конкретные матрицы проверяются полностью; **матрицы-шаблоны** (с эллипсисами) выражают динамические размеры —
  хрестоматийная запись `[b c ⋯ 0; a b c ⋯; ⋯ a b c; 0 ⋯ a b]` является исходным кодом в том виде, как написана.

## Федерация и многострочная запись (второе решение от 2026-11-23)

**Один макроблок может содержать целую группу формул, которые ссылаются друг на друга** («федерация»):

```rust
formula_matlab!{
    decl { F : force [N]; m : mass [kg]; r : radius [m]; }
    accel = F / m
    mech = ( accel * r )^(1/2)
}
// expands to a let chain: let accel = F / m; let mech = (accel * r).sqrt(); mech
```

- **Разделитель элементов** = точка с запятой или **перевод строки**, и это **действует во всех трёх каналах** (токенный канал восстанавливает
  переводы строк по номерам строк span'ов proc-макроса, а эти номера выровнены на исходный файл, поэтому диагностика указывает на ту же строку).
- **Последующие элементы могут ссылаться на предыдущие**: размерность распространяется вместе с именем (м/с² у accel попадает в таблицу символов); канал build.rs подставляет замену ещё при генерации.
- **Имя — это контракт**: когда формула переиспользует имя из `decl`, размерность её результата должна совпадать с объявленной
  (`a = F/m` допустимо, `s : Pa; s = F/d` отклоняется); повторяющиеся имена формул внутри одного набора формул или одного каталога генерации отклоняются всегда.
- **Модель продолжения операторов**: оператор должен стоять **в конце строки** (`x +⏎ y` ✓); ведущий `-`/`+` на следующей строке открывает знак нового элемента, это не вычитание с продолжением строки — это и есть решение о снятии неоднозначности.
- Неявное умножение (приписывание) на поверхности LaTeX **должно оставаться в одной строке**: приписывание через границу строк поглощает следующую формулу как множитель.

**Многострочная запись матриц** (одна физическая строка на строку матрицы; расстояния между столбцами свободны, выравнивание не требуется):

```text
[ 2*k, -k,    ...,   0 ;
  -k,  2*k,   -k,    ... ;
  ..., -k,    2*k,   -k ;
  0,   ...,   -k,    2*k ]
```

- Разделитель строк = `;` или перевод строки (можно смешивать, завершающий необязателен); разделитель столбцов = запятая или пробел (≥1, в любом количестве).
- Эллипсис `...` / `⋯` / `…` в ячейке означает «здесь опущено» (горизонтальный/вертикальный/диагональный смысл выводится при обратной записи).
- **`-` без пробела перед ним — это знак, а предшествующий пробел начинает новый столбец** (семантика MATLAB): `[k-1]` — один столбец, `[k -1]` — два.

## Комплексные числа: сквозной канал от слоя значений до генерации кода (2026-11-23)

- **`j` — зарезервированная мнимая единица** (всегда безразмерная, никогда не объявляется, **никогда не попадает в список параметров**). `Z = R_s + j*X` можно писать напрямую.
- В слое значений ровно два варианта: `Value::Scalar(C)` / `Value::Matrix(Vec<Vec<C>>)`, где `C = {re, im}`.
  Вещественное число — это комплексное число с нулевой мнимой частью ⇒ **комплексные матрицы, транспонирование, умножение, сложение и вычитание
  поэлементно верны бесплатно**; разделение на квадранты «вещественная матрица / комплексная матрица» не нужно.
- Трансцендентные функции используют одну таблицу для вещественных и комплексных значений: `exp ln sqrt sin cos tan sinh cosh tanh` +
  `abs arg conj re im` (последние четыре всегда возвращаются на вещественную ось). Комплексные степени идут через `exp(w·ln z)` на главной ветви.
- **`eval` на комплексных значениях выдаёт явную ошибку** (он не отбрасывает мнимую часть молча); используйте `eval_value`, когда нужны комплексные значения.
- **У генерации кода есть отдельный комплексный канал**: если формула содержит `j`, она генерируется как `-> (f64, f64)` = (вещественная, мнимая),
  и из локальных для блока помощников (`__c_mul` / `__c_sqrt` …) **генерируются только реально использованные** (иначе clippy `-D warnings` становится красным).
  Пакетная точка входа — `out: &mut [(f64, f64)]`, напрямую пригодная для частотных свипов EIS.
  Макроканал (`formula!` и т. п.) разбирает так же: `j` **не** деградирует до свободной переменной в точке вызова;
  привязка, уже ставшая комплексной внутри федеративной цепочки `let`, наследуется корректно (`emit_block_complex_with`).
  Комплексный канал **не генерирует аналитических производных**: `abs/arg/conj/re/im` не комплексно-аналитичны, поэтому цепное правило не выполняется.
- **Сгенерированный код и слой значений должны совпадать поточечно** — это жёсткое ограничение: `__c_powf` повторяет целочисленный разбор `C::pow_real`
  (целая степень отрицательного вещественного основания должна попадать точно на вещественную ось), а `__c_sqrt` использует `hypot`, как слой значений, чтобы избежать переполнения при больших величинах;
  то, что `__c_div` следует IEEE, а слой значений выдаёт ошибку — намеренно: каждый из этих пунктов защищён в фикстурах тестом сравнения для своего оператора.
- Строки единиц принимают рациональные показатели: `[V/A*s^(-1/2)]` (скобки обязательны — иначе `/` в показателе нельзя отличить от
  знака деления в строке единицы); показатель, который не делится нацело (`m^(1/3)`), отклоняется явно. Для безразмерной величины пишите `[1]`
  (усиление / счёт / мольная доля должны быть объявляемыми; они не могут протащить себя внутрь через «опускание единицы»).
- **`himari-fmt --diff <file>`**: предпросмотр только для чтения, печатающий унифицированный diff
  `--- current / +++ canonical` (изменений нет → нет вывода и код выхода 0; изменения есть → код выхода 1).
- **Семантическая граница между вещественным и комплексным** (намеренная, а не недосмотр): `1/0` раньше давал `inf`, а теперь **выдаёт ошибку**;
  `ln(0)` так же; `(-2)^0.5` сообщает «результат комплексный, используйте `eval_value`».
  Сгенерированный код, напротив, следует семантике IEEE (деление на ноль даёт inf/NaN): горячий путь не несёт пути ошибки,
  а всё, что уровень формул может статически доказать как неверное, отсекается проверками размерности/формы.
- **`python3 scripts/fmt_check.py --fix`**: одна команда, чтобы переложить каноническую форму и перегенерировать сайдкары.

## Единицы: приставки СИ, преобразование, безразмерные группы (2026-11-23)

- **Прежде чем разбирать приставку, найдите полное имя**: `m` — это метр (а не «милли-ничто»), `mol` — моль, `cd` — кандела,
  `daN` — деканьютон (побеждает самая длинная приставка). `nF` / `GHz` / `mm^2` / `mV/mm` / `µF` / `Ω` работают все.
  Производные единицы покрывают те шесть, которых электроника не может избежать: `F` `Ω` (или `ohm`) `S` `H` `Wb` `T`.
- **Размерность и коэффициент преобразования хранятся отдельно**: `parse_unit` даёт только размерность; `parse_unit_spec` дополнительно даёт
  коэффициент перехода в СИ; `convert(v, "nF", "F") = 1e-9 F`, а несовпадение размерности выдаёт ошибку. Базовая единица массы — **kg**:
  `g = 1e-3 kg`, `mg = 1e-6 kg`, `Mg = 1000 kg`; приставки отсчитываются от грамма (закреплено регрессионным тестом).
  **Параметры сгенерированных функций всегда в основных единицах СИ**, приставка в объявлении влияет только на читаемость — doc-комментарий сгенерированного кода
  прописывает коэффициент преобразования для каждого параметра (цитата дословно из реального doc-комментария:
  `⚠ 参数 C_dl 声明为 µF：入参是 SI 基单位（1 µF = 0.000001 …）`).
- **Приставки CGPM 2022** есть в таблице: `Q` (1e30), `R` (1e27), `r` (1e-27), `q` (1e-30) наряду с уже имеющимися
  `da … Y / d … y`.
- **Внесистемные единицы с точными определениями** (`unit_base` несёт каждый коэффициент, чтобы `convert` оставался размерностно честным): `min`, `h`, `d`, `L`
  (или `l`; `mL` разбирается как приставка к `L`), `deg`, `arcmin`, `arcsec`, `bar`, `atm`, `eV`, `Wh`, `tonne`, `Da` (или `u`), `nmi`, `knot`, `ha`, `acre`.
- **Смещённые / логарифмические единицы отклоняются явно**: `degC` (смещение) и `dBm` (отношение) останавливаются до разбора приставки
  и сообщают «настоящую причину», а не «неизвестная единица» — молчаливая трактовка их как K или как безразмерных вычислила бы **неверное значение**.
  **Неоднозначные обозначения отклоняются так же, а не угадываются**: `cal` / `Cal` различаются между термохимической (4.184 J) и IT (4.1868 J) калориями, поэтому обе
  отвергаются с указанием писать `J`; `rpm` требует угловой оси (1 rpm = 2π/60 rad/s), а этот инструмент трактует `rad` как безразмерный, поэтому он отвергается
  с указанием писать `2 * pi * f` при объявлении `[Hz]`.
- **Безразмерные группы (Π-теорема Букингема)**: `dimensionless_groups` исключает методом Гаусса с **точными рациональными числами** (`f64` даёт дрейф)
  и выдаёт безразмерные комбинации базиса прямо из «имён переменных + размерностей»; количество = (число переменных) − ранг (Π-теорема как утверждение).
  Классическая проверка: `{rho, v, L, mu}` → 1 группа `rho·v·L·mu^-1` (число Рейнольдса).
  `dim_solve` — неоднородное использование той же системы: `{kg, m/s²} → N` даёт показатели `[1, 1]`,
  а невыразимая размерность сообщает «не удаётся составить» и сколько размерностей не хватает.

## Размерности: полуцелые показатели (2026-11-23)

`Dim` внутри хранит значения в единицах **1/2** (`[i16;7]` хранит удвоенный истинный показатель), поэтому дробные и целые степени
идут через одну и ту же целочисленную арифметику: `√s = s^(1/2)`, `f^(-1/2)`, `Ω·s^(-1/2)` — всё законно, а при выводе используется форма со скобками,
как `s^(-7/2)`. Импеданс Варбурга поэтому возвращается к хрестоматийной форме `Z = σ·f^(-1/2)`,
без необходимости приведения к безразмерному виду через опорную частоту. Показатель степени в `dim_check` **сначала сворачивает константы**,
поэтому естественная запись `f ^ (1/2)` проходит проверку без предварительного вызова `simplify`.

## Семейства функций: экстремум / ограничение / матричные операторы (2026-11-23)

**Единственный источник истины** для арности функций — `func_arity` (в core); все четыре канала (проверка арности / вычисление / размерность / генерация / обратная запись)
обращаются к нему — раньше каждый канал нёс свой `match`, и именно поэтому «`arg` генерировался как несуществующий метод в вещественном канале» пережил один релиз.

| семейство | функции | примечания |
| --- | --- | --- |
| унарные скалярные | `exp ln log sqrt sin cos tan sinh cosh tanh` | одна и та же таблица для вещественных и комплексных |
| комплексные | `abs arg conj re im` | `arg` безразмерен; в вещественном канале re/im/conj — тождество |
| экстремум/ограничение | `min(a,b)` `max(a,b)` `clamp(v,lo,hi)` | та же форма, что в Rust: `v.max(lo).min(hi)`; все три аргумента должны иметь одну размерность |
| матричные операторы | `det` `trace` `adjoint` `inv` | **принимают только конкретные матричные литералы**; `det`/`inv` до порядка 4/3 (достаточно и для 2D-, и для 3D-изопараметрических элементов), `adjoint` = сопряжённое транспонирование |

`det`/`inv` используют **рекурсию по алгебраическим дополнениям** (`det` ≤ 4, `inv` ≤ 3): этого достаточно для изопараметрических отображений 2D-треугольников и 3D-тетраэдров,
с численными проверками `J·J⁻¹ = I` и `det(J)=1`; обратная 4×4 потребовала бы 16 алгебраических дополнений 3×3
(≈100 слагаемых) и раздула бы сгенерированный код, поэтому она отклоняется явно с указанием на численную библиотеку. `det`/`trace` в `diff` **разворачиваются до дифференцирования** —
разложение является обычным дифференцируемым выражением, поэтому `area = det(J)/2` из МКЭ имеет и значение, и аналитическую производную
(`∂area/∂x₂ = (y₃-y₁)/2`).
Кусочный выбор в `min/max/clamp` невыразим в IR (оператора сравнения нет), поэтому **производные не генерируются**;
строка комментария в сгенерированном коде объясняет почему (паники больше нет). Экстремум и ограничение следуют правилу NaN у `f64::min/max`
(они могут вернуть второй операнд); вызывающий код, которому нужно протаскивание NaN, должен проверять `is_finite` на границе.

## Встроенные формы с первого взгляда

`identity` / `diag(d)` / `diag_v(d[i])` / `tridiag(a,b,c)` / `tridiag_v(b[i])` /
`bidiag_u(b,c)` / `bidiag_l(a,b)` / **`blockdiag2(p,q)` = diag(p·I₂, q·I₂)** /
**`banded(v, k)` = симметричная ленточная с полушириной k** (k=2 однозначна только начиная с 5×5; на 4×4 она вырождается в плотную матрицу).

Эти имена описывают **распознанную форму IR**; это не функции, которые можно вызвать из формулы. Точка входа —
матричный эскиз с эллипсисами, а всё нераспознанное отклоняется явно.

Семантика блочно-диагональной матрицы внутри блока = скаляр × единичная (p на диагонали, вне диагонали внутри блока пусто), вне блоков должно быть пусто
(`0` и `...` эквивалентны); при нечётной общей размерности центральная ячейка относится к правому нижнему блоку.

## Производительность комплексного канала: честная сторона (измерено 2026-11-23)

`bin/bench.rs` теперь измеряет четыре канала. Комплексный, Z_c (частотный свип EIS), **медленнее, чем написанный вручную**; записано как есть:

| форма | нс/точка | относительно написанной вручную |
| --- | --- | --- |
| ручная специализация (`σ/√ω·e^{-jπ/4}`, без ветвлений, векторизуемая) | 2.3 | 1× |
| транскрипция той же формы (последовательность операторов сгенерированного кода, скопированная в один цикл) | 2.9 | 1.3× |
| сгенерированный код · прямой скалярный вызов | 6.4 | 2.8× |
| сгенерированный код · пакетная точка входа | 12.8 | 5.5× |

Разбор: **общие комплексные √/÷ стоят примерно в 2.2 раза дороже ручной специализации** (1 sqrt против 3 sqrt + одно деление),
а **пакетная обёртка добавляет ещё примерно 2.5 раза** (запись в срез кортежей + ветвления не дают циклу векторизоваться).

Уже сделанные оптимизации (каждая действительно сузила разрыв):

1. `__c_sqrt` перешёл от полярной формы (atan2+cos+sin, 4 трансцендентные функции) к **алгебраической замкнутой форме**;
1. быстрый путь для чисто мнимых `√(iy) = √(|y|/2)(1+sign·j)` (всего 1 sqrt — повседневная форма в EIS);
1. `__c_div` при обычных величинах использует наивную форму (1 деление);
1. комплексные помощники переведены с **замыканий** на локальные для блока `#[inline(always)] fn` (15.5 → 11.9 нс/точка).

**Вывод (записан в README, а не спрятан)**: комплексный канал хорош для «считает верно + достаточно быстро», и гоняться за пределом
ручной специализации не стоит; для действительно горячего цикла свипа EIS напишите специализацию вручную, а формулу держите в
файле `.formula` как **источник истины и проверку размерности**. В вещественном канале этой проблемы нет (скаляр 1.11×, на уровне ручного кода).

## Пакетные точки входа: фиксированная длина побеждает, срезы проигрывают (измерено)

Генератор выдаёт **две** пакетные точки входа на формулу:

| форма | сигнатура | измерено (BV, 100k точек) |
| --- | --- | --- |
| вариант со срезом | `bv__batch(p0: &[f64], …, out: &mut [f64])` | 24.1 нс/точка = **0.82× от скалярного (на 22% медленнее)** |
| вариант с фиксированной длиной | `bv__batch_n<const N: usize>(p: &[f64; N], …, out: &mut [f64; N])` | 19.3 нс/точка = **1.03× от скалярного (на 3% быстрее)** |

## Матричная алгебра (форма + вычисление + генерация)

Размерности и формы — **две ортогональные оси проверки**: размерности ведают физическим смыслом, формы — алгебраической законностью.

| возможность | поведение |
| --- | --- |
| `shape_of` | конкретная матрица → `(rows, cols)`; транспонирование меняет местами; символьная/шаблонная матрица → `None` (динамического вывода нет) |
| `shape_check` | сложение/вычитание матриц требует равных форм, произведение требует `left cols = right rows`, «рваные» матрицы отклоняются, деление матриц отклоняется явно |
| `eval_value` | унифицированное вычисление скаляров/матриц, произведение матриц как `C_ij = Σ_k A_ik·B_kj` |
| `flatten_matrix_value` | сворачивает **статически разворачиваемое** матричное выражение в конкретный матричный IR (транспонирование/сложение/вычитание/отрицание/скалярное расширение/произведение матриц) |
| генерация | свёрнутая матрица → константный литерал `vec![vec![…], …]`; большие матрицы идут через канал «матрица-шаблон + цикл» |

```text
[1, 2; 3, 4] * [5, 6; 7, 8]  →  [[19.0, 22.0], [43.0, 50.0]]
[1, 2, 3]'                   →  3×1 column vector (emitted as vec![vec![1.0], vec![2.0], vec![3.0]])
A * [1, 2]                   →  scalar broadcast (a bare symbol is a scalar: matrices only come from literals/pattern generators)
[1, 2, 3] * [1, 2, 3]        →  compile-time rejection: matrix multiply impossible: (1, 3) × (1, 3)
```

> **Обобщённые `A,b` времени выполнения по-прежнему нужно объявлять именно так**: имена `decl` с величиной, оканчивающейся на `_matrix`/`_vector` (или равной `matrix`/`vector`),
> становятся матричными/векторными параметрами — именно это использует канал времени выполнения ниже. Любой *другой* «голый» символ — скаляр, поэтому `A * x` над
> матрицами, формы которых не входят в объявление, по-прежнему выражается литералами, статически разворачиваемыми выражениями или генераторами шаблонов.
> Для общих крупномасштабных `Ax=b`, вывода размера во время выполнения или плохо обусловленных систем используйте численную библиотеку линейной алгебры.

**Матричные степени с неотрицательным целым показателем**: `[a, b; c, d] ^ 2` сворачивается генератором в явные умножения матриц (0–8 раз),
`M ^ 0` — единичная матрица того же порядка (тип возврата всё равно матричный, а не скаляр `1`). Сквозная численная проверка — в
`matrix_power.formula`. Неудачная свёртка (отрицательный/дробный показатель, выход за диапазон, не квадратная) выдаёт `compile_error!`,
а не случайность компиляции вроде `vec![…] * vec![…]`; слой значений (`himari-eval`) даёт тот же результат для той же формы.

**Две независимые реализации должны совпадать**: генерация кода матричных выражений (`flatten_matrix_value` + выдача литерала)
и вычисление в слое значений (`eval_value`) написаны раздельно, поэтому **дифференциальный тест** держит обе стороны согласованными —
вычисление свёрнутого литерала должно совпадать с вычислением несвёрнутого выражения ячейка за ячейкой (`mat-expr-fold`).

**Матричный эскиз без эллипсисов — это конкретная матрица**: он идёт через канал литералов (константы сворачиваются, цикла выделения нет),
что лучше генератора; чтобы использовать канал генератора (где `n` — параметр времени выполнения), нужно написать эллипсисы.

## Канал матриц/векторов времени выполнения (2026-11-23)

Всё вышеописанное статично: формы известны при компиляции формулы. Канал времени выполнения — отдельный ответ для
**параметров, размеры которых существуют только во время выполнения** — решателя, потребляющего пользовательские данные, сборки МКЭ, всего, что получает `A` и `b` как значения.

- **Объявление — единственный переключатель**: `decl`, у которого величина оканчивается на `_matrix`/`_vector` (или равна `matrix`/`vector`), становится
  матричным/векторным параметром — `A : stiffness_matrix [N/m]` приходит как `&[Vec<f64>]`, `b : load_vector [N]` как `&[f64]`.
  Имена, которые не включаются явно, остаются скалярами, поэтому существующие формулы не затронуты (`Decl::runtime_kind`).
- **Сгенерированные функции могут завершаться ошибкой**: они возвращают `Result<_, himari::runtime::NumericError>`, один структурированный тип ошибки
  (`InvalidInput` / `ShapeError` / `NonFiniteValue` / `SingularMatrix` / `IllConditioned` / `UnstableResidual` / `NoRealRoots`). На этом канале
  **нет молчаливого контракта с NaN**.
- **`solve(A,b)`** — LU с частичным выбором ведущего элемента, затем две независимые проверки до выдачи любого ответа:
  **оценка rcond** (`1/(‖A‖∞·‖A⁻¹‖∞)`, требуется `rcond ≥ f64::EPSILON·64·n`) и **проверка относительной невязки**
  (`≤ 1e-9`). Обратная матрица строится только для оценки обусловленности и никогда не является способом получить `x`. Сингулярный ведущий элемент,
  плохо обусловленная матрица и решение с большой невязкой — три разные ошибки, а не одно «не получилось».
- **На этом канале также поддерживается**: `inv`, `det` (только литеральные аргументы — `det` времени выполнения отклоняется, потому что его размерности нужен статический
  порядок матрицы), `A*x`, `dot`, `norm`, а также индексация `A(i, j)` с **нумерацией с 1** (`[I,J]`; выход за диапазон и ноль — ошибки, а не паники).
- **Что он генерирует**: тело — проверяемое выражение над цепочками `let` в области видимости внутри сгенерированной функции, а тип возврата следует
  виду значения (`Result<f64, _>`, `Result<Vec<f64>, _>`, `Result<Vec<Vec<f64>>, _>`). Формулы канала времени выполнения **не** генерируют аналитического якобиана, **не**
  генерируют вариант `__f32` и **не** генерируют пакетных точек входа (им нужна скалярная сигнатура с известным размером).
- **Ответы проверяются против независимых эталонов**: `runtime_matrix.formula` проверяет `solve(A,b)` против отдельного исключения Гаусса
  с выбором ведущего элемента, `A*x` против `b`, `A·inv(A)` против столбцов единичной матрицы, индексацию с 1 и намеренно систему с крошечной
  эпсилон (`[[1e-17, 1], [1, 1]]`), которую правильно решает только выбор ведущего элемента — всё с допусками 2e-12/2e-15.
- **Макроканал**: `formula_matlab!` принимает и формулы времени выполнения, но только **одну формулу на блок** (цепочка времени выполнения остаётся на канале build.rs
  с явным сообщением); комплексные матричные параметры времени выполнения пока отвергаются.

## Качество генерации кода (2026-11-23)

- **Целые степени генерируют `powi`**: `x^3` → `(x).powi(3)` (раньше генерировался несуществующий внутренний метод,
  так что любой `x^3` не компилировался, а ошибка указывала внутрь сгенерированного кода). В фикстуре есть **компиляционная проверка** для `x^3`.
- **Неизвестные функции не проходят компиляцию**: функции вещественного канала — белый список; `arg(x)` над вещественными бессмыслен, поэтому выдаётся
  `compile_error!`; `re/im/conj` над вещественными — тождество (точное, не приближённое).
  Вызовы с несколькими аргументами отклоняются на этапе разбора (генератор смотрел только на `args[0]`, а молчаливое отбрасывание остальных вычисляло неверное значение).
- **Системный якобиан**: каждый файл `.formula` дополнительно порождает `{filename}__jacobian(all params)`,
  строки = **вещественные скалярные формулы, участвующие в дифференцировании** (матричнозначные / комплексные / недифференцируемые элементы пропускаются), столбцы = параметры (в порядке объявления),
  а строка, не зависящая от параметра, имеет **0** в этом столбце повсюду. Это та форма, которая нужна неявным решателям / итерациям Ньютона / сборке МКЭ.
- **Нефинитные константы падают жёстко**: генерация `inf` / `NaN` дала бы недопустимый идентификатор,
  поэтому перед генерацией срабатывает паника с указанием источника (`contains_nan_expr` — единственный источник истины).
- **Скобки вокруг степеней**: `(x^2)^3` и `x^(2^3)` получают скобки на обеих поверхностях —
  `x ^ 2 ^ 3` повторно разбирается как `(x^2)^3` (x⁸ → x⁶, то есть каноническое форматирование **изменило бы математику**).

## Форматирование (каноническое)

`himari-fmt`: `cargo run -p himari-check --bin himari-fmt -- [--check|--write] <file>`.

- Многострочные decl (один символ на строку); одна формула на строку; **столбцы матриц выровнены** (каждый столбец = шрина самого широкого содержимого + ≥1 пробел, запятая как граница столбца).
- Отдельные строки комментариев все поднимаются в начало файла (порядок сохраняется) — комментарии для людей и никогда не попадают в IR.
- `--check` = проверка дрейфа (подключена в `just fmt-check` / CI); канонический вывод идемпотентен относительно обратной записи.
- **Каноническая форма сохраняет запятые**: разделение только пробелами и бинарное вычитание неразличимы при обратной записи (`-k` был бы проглочен как терм вычитания),
  поэтому запятая — однозначная граница; писать вручную без запятых можно, форматирование их вернёт.

## Каналы (решение пользователя от 2026-11-23)

| канал | использование | подходит для |
| --- | --- | --- |
| **встроенный макрос** | `formula_matlab!{ decl { a : l [m]; b : l [m]; } a / b }` | простые формулы |
| **строковый макрос** | `formula_latex!{ r"decl { … } \frac{a}{b}" }` | простые формулы (поверхность LaTeX) |
| **макрос внешнего файла** | `formula_file!("formulas/bv.formula", matlab)` | сложные формулы (диалект нужно указывать явно) |
| **build.rs** | см. `packages/check/fixtures/three/` | сгенерированный код в репозитории + проверка дрейфа (формальный канал) |

`decl` внутри макроса лишь предоставляет информацию о символах для проверки размерности; он **не создаёт локальных переменных Rust**: `a/b` в
точке вызова должны уже быть `let a = …; let b = …;` у вызывающего кода. Полный компилируемый пример см. в
`inline_macro_example()` в `examples/common/src/main.rs`.

> ⚠️ Известное ограничение: proc-макрос, читающий файлы, **не отслеживается cargo** (`tracked_path` всё ещё только в nightly),
> поэтому после правки `.formula` нужен `touch`, чтобы вызвать пересборку; для продакшена используйте канал build.rs (`rerun-if-changed`).
> ⚠️ **Канал конструктора** для матриц-шаблонов/транспонирований существует только для файлов / build.rs (ему нужно имя файла и генератор);
> встроенные макросы при встрече с ними сообщают явную ошибку с указанием, никогда не деградируют молча.

## Языки поверхностей (три, один IR)

| | статья | LaTeX | стиль MATLAB |
| --- | --- | --- | --- |
| греческие буквы | `α·x` | `\alpha \cdot x` | `alpha*x` |
| эллипсис | `⋯ …` | `\cdots \vdots \ddots` | `...` |
| матрица | `[a, ⋯, b; ⋮ ⋱ ⋮; c, ⋯, d]` | `\begin{bmatrix}…\end{bmatrix}` | `[a, ..., b; ...]` |
| транспонирование | `A'`, `A′`, `A^T` | `A^T` | как слева |
| объявления размерностей | `decl { v : velocity [m/s]; }` | как слева | как слева |

Правила (отказ — это функция):

- Каждый символ должен быть сначала объявлен вместе со своей размерностью; необъявленный = ошибка компиляции, никакого вывода по начертанию.
- Неоднозначная или чисто типографская нотация, такая как `\sin^2 x`, `\left(\right)`, `$…$`, `x .* y`, отвергается сразу.
- Неявное умножение действует только на поверхностях LaTeX/статьи (однобуквенная система однозначна по построению); поверхность MATLAB требует явного `*`.
- Матрицы-шаблоны поддерживают только три доказуемо верные формы: `identity(n)`, `diag(d, n)`,
  `tridiag(a, b, c, n)`; всё нераспознанное = ошибка + список этих трёх.
- Исходники могут быть написаны от руки (комбинирующие знаки и т. п.), но **IR должен быть нормализован** — комбинирующие символы никогда не попадают в IR.

## Векторная алгебра / Горнер / no_std (2026-11-23)

**`dot(a,b)` / `norm(v)`**: разворачиваются только на **конкретных литералах** (форма известна на этапе компиляции);
размерность `dot` — произведение обеих сторон, `norm` имеет ту же размерность, что и её элементы. `dot([x,y],[x,y])` (x=3,y=4) → 25,
`norm` → 5. Несовпадающие формы отвергаются сразу.

**Автоматическое преобразование к схеме Горнера**: **явный многочлен**, записанный в исходнике как `c₀ + c₁x + c₂x² + …`, перед генерацией преобразуется в
`(…((cₙx + cₙ₋₁)x + …) + c₀)` — число умножений падает с `2n-1` до `n`, а большие степени вроде `x^n` исчезают
(численно устойчивее). `a*x^3 + b*x` → `(a * x * x + b) * x`.
**Компактные формы не разворачиваются**: `(u-1)^3` остаётся как написано (разворачивание только усложняет чтение); производные также берутся от
**исходной формы до Горнера** (дифференцирование формы Горнера даёт цепочку сокращающихся произведений).

**Канал `no_std`**: `himari_buildhelper::generate_dir_libm` генерирует код, использующий только `core` + `libm`
(трансцендентные → `libm::exp` и т. п., целые степени → `libm::pow`; `f64::powi` — это из std).
Это означает, что **сгенерированный код** пригоден для `no_std` — и с 2026-11-23 стек времени компиляции тоже:
`himari`, `himari-latex` и `himari-matlab` — это `no_std + alloc` за фичей `std`, включённой по умолчанию (`std` включена, если её не выключить).
Крейты loader, buildhelper, macros и check (файловый ввод-вывод, хост proc-макросов, инструментарий) остаются `std` и включают фичу явно.
Сгенерированный код сохраняет **свой канал libm**, с которым фактически линкуется потребитель на «голом железе».
Проверка: крейт-фикстура `#![no_std]` (`[lib] test = false`, поскольку тестовому харнессу нужен std), которая и компилирует
сгенерированный код, **и** прогоняет цепочку парсера (`himari_matlab::parse` → `dims_of_set` → `shapes_of_set` → `dim_check_runtime` → `format_set`)
без std. **Прошедший `cargo build` = сгенерированный код и фронтенд не тянут std втихую.**
Проверенные bare-metal цели: `riscv32imc-unknown-none-elf` (только core — атомики недоступны), `thumbv7em-none-eabi` и
`x86_64-unknown-none` (цепочка парсера). Этот канал не генерирует якобиан (ему нужен `alloc`) и не генерирует вариант f32
(трансцендентные функции f32 — это семейство `*f` из libm, а мы отказываемся выпускать половину канала); для частных производных используйте функции `__d_*` для каждой формулы
(чистый скаляр, нулевое выделение памяти).

## Межфайловые библиотеки формул: `use "..."` (2026-11-23)

```text
use "lib/atmosphere.formula"      % file header, may span several lines
decl { ... }
v_terminal = sqrt(2 * m * g / (rho * Cd * A))
```

- **Разбор только собирает, ввод-вывод — дело загрузчика**: фронтенд остаётся чистым строковым API (`FormulaSet.uses`),
  а `himari-loader` занимается чтением файлов, рекурсивной вставкой, обнаружением циклов и разрешением конфликтов.
- Семантика слияния (простая и предсказуемая): ссылки на decl/элементы **размещаются первыми** → федерация работает как обычно (последующие элементы могут ссылаться на предыдущие);
  одинаковые совпадающие decl дедуплицируются, различающиеся написания дают ошибку; повторяющиеся имена элементов дают ошибку всегда (**никакого «побеждает последняя запись»**);
  циклы дают ошибку и печатают цепочку имён файлов вокруг цикла.
- **Библиотека «подставляется», а не «вызывается»**: после раскрытия `rho` в вызывающий код список параметров содержит `rho_0 / h / H`.
  Это намеренно (никакого скрытого состояния, статически дифференцируемо); цена — более длинный список параметров.
- Соглашение о каталогах: `generate_dir` сканирует только **верхний уровень** `*.formula`, поэтому `formulas/lib/*.formula`
  естественно существует только как библиотеки и никогда не генерируется дважды как формула верхнего уровня.
- **Диалект задаётся макросом, а не угадывается** (решение пользователя от 2026-11-24, «макрос — это диалект»): какой макрос оборачивает формулу,
  тот и определяет, какая грамматика её читает.

  | макрос | диалект |
  | --- | --- |
  | `formula!(…)` | **matex** (каноническая поверхность; имя точки входа сохранено, семантика зафиксирована) |
  | `formula_latex!(…)` | LaTeX |
  | `formula_matlab!(…)` | matex (синоним `formula!`, читается понятнее) |
  | `formula_file!("f.formula", latex)` | определяется **обязательным** вторым аргументом |

  `formula_file!` не делает аргумент диалекта необязательным: по имени макроса нельзя вывести содержимое файла, а угадывание превратило бы
  макрос лишь в ещё одно место, где неоднозначность спрятана.

  **Почему это не просто вкусовщина стиля** — это устраняет реальное молчаливо неверное значение. Когда объявлен `si`, `si * x`:
  matex читает это как `si·x`, LaTeX читает как `s·i·x`. Измерено на одном и том же файле с одними и теми же входами (s=3, i=5, x=2, si=100):

  ```text
  old AUTO (try matex first, use if it succeeds)  →  200    without reporting any error
  explicit LaTeX                                  →  30
  ```

  Разница почти в семь раз. AUTO не мог знать, что имел в виду автор — «угадал» он лишь то, какой парсер сработал первым.
  Поэтому у перечисления `Dialect` в макроканале **нет** варианта `Auto`: система типов гарантирует, что угадывание не вернётся.

## Быстрый старт: `examples/reentry` (минимальный запускаемый проект)

```text
examples/reentry/
  formulas/entry.formula       % terminal velocity / dynamic pressure / drag (aerospace side)
  formulas/structures.formula  % static displacement = solve(k·x − F, x)
  build.rs                     % three lines: generate_dir("formulas", "src/generated.rs")
  src/main.rs                  % prints the table + physical invariant self-checks
  src/generated.rs             % the checked-in generated code (reviewable, covered by the drift gate)
```

`cargo run -p himari-example-reentry` печатает таблицу скорость→динамическое давление→лобовое сопротивление и проверяет:

- **Физический инвариант**: `drag(v_terminal) == m·g` (относительная разница 1.6e-16 — это не подгонка, это определение)
- **Аналитическая производная против разностного отношения**: `∂drag/∂v` согласуются с относительной разницей 1.2e-8 по обоим путям
- **Символьное решение**: `x_static` получается из `solve(k·x − F, x)`, и `∂x/∂F = 1/k` выполняется автоматически
- **Вариант f32** и **системный якобиан формулы с подставленной библиотекой** — оба в одном сгенерированном файле

Потребителю теперь нужен только `himari-buildhelper::generate_dir(dir, out)` — весь канал build.rs
(разбор / федерация / размерности / формы / производные / f32 / пакетные точки входа / якобиан / исходный LaTeX) сводится к одной функции,
так что каждому проекту больше не нужно копировать 300 строк.

## Общие примеры: `examples/common` (реальная генерация + независимые численные эталоны)

```bash
cargo run -p himari-example-common
cargo test -p himari-example-common
```

| файл формулы | пример | сгенерированная точка входа и проверка |
| --- | --- | --- |
| `matrices.formula` | поворот, транспонирование, `AᵀA`, обратная 2×2, `A·A⁻¹`, матрица на столбец | `rotation_orthogonality` / `N` / `stiffness_inverse` / `nodal_forces`; ячейка за ячейкой против ручного вычисления |
| `springs.formula` | система равновесия трёхузловых пружин `solve([…],[u₁,u₂,u₃])` | `displacements` против отдельного исключения Гаусса на Rust с частичным выбором ведущего элемента |
| `runtime_matrix.formula` | `A`/`b` времени выполнения: `solve(A,b)`, `A*x`, `inv(A)`, индексация с 1 | `runtime_displacements` / `runtime_traction` / `runtime_inverse` / `runtime_element`; каждый вызов может завершиться ошибкой (`Result`), выбор ведущего элемента доказан на `[[1e-17,1],[1,1]]` |
| `least_squares.formula` | нормальные уравнения для подгонки прямой | `line_fit` против прямой замкнутой формы метода наименьших квадратов, даёт `y=1.04+1.99x` |

Эти примеры доказывают, что **сейчас поддерживаемые формы** действительно проходят путь от `.formula` до исполняемого Rust; они не выдают

Сгенерированный `src/generated.rs` закоммичен и защищён проверкой дрейфа.

## Канал стандартов: `himari-standards` (2026-11-23)

`packages/standards` превращает горстку **опубликованных инженерных стандартов** в типизированные калькуляторы, одна связь уровня пункта на модуль, каждая
со своим `PROVENANCE` (идентификатор стандарта, редакция, пункт, из которого взята формула, и что *не* моделируется). Ничто здесь не цитирует
текст стандарта, и ничто не заявляет о соответствии стандарту — формула пересказывается как обычное выражение. Преобразование единиц
намеренно отсутствует: вызывающий код передаёт основные единицы СИ.

| модуль | стандарт | редакция | что вычисляется |
| --- | --- | --- | --- |
| `iso_6506_1_2014` | ISO 6506-1 | 2014 | твёрдость по Бринеллю `HBW` (плюс среднее давление отпечатка в Pa) |
| `iso_6892_1_2019` | ISO 6892-1 | 2019 | предел прочности `Rm`, относительное удлинение `A`, модуль `E` |
| `iso_2533_1975` | ISO 2533 | 1975 | тропосфера `T`, `p`, `rho` и пересчёт геопотенциала (0 … 11 000 m, а выше — отказ, а не экстраполяция) |
| `gb_t_231_1_2018` | GB/T 231.1 | 2018 | твёрдость по Бринеллю `HBW`; действующая редакция, заменяет GB/T 231.1-2009, модифицированно принимает ISO 6506-1:2014 |
| `gb_t_228_1_2021` | GB/T 228.1 | 2021 | предел прочности `Rm`, удлинение `A`, модуль `E`; действующая редакция (в силе с 2022-07-01) |
| `gb_t_8170_2008` | GB/T 8170 | 2008 | десятичное округление, **округление к чётному**, решается по десятичным строкам — `f64` никогда не участвует в решении об округлении |

Два модуля GB для механических испытаний переиспользуют арифметику ISO (то же проверенное вычисление), но сохраняют **свои** идентификатор, редакцию и происхождение, поэтому
ответ никогда не может быть помечен неверным стандартом. Для `GB/T 228.1-2021` степень принятия какого-либо документа ISO **не** была независимо
проверена, поэтому модуль явно не заявляет эквивалентности — реализованы только три определения. Редакции сверялись с
Национальной платформой публичных услуг в области информации о стандартах, и каждый модуль записывает проверку в своих заметках о происхождении.

CLI `himari-standard` вычисляет один запрос и печатает один документ ответа стабильной формы (JSON), читая запрос как JSON или TOML —
из `--input <path>` или stdin, с `--format json|toml` для принудительного выбора парсера и `--list` для точных идентификаторов и редакций:

```bash
himari-standard --input packages/standards/examples/brinell.json
himari-standard --input packages/standards/examples/tensile.toml
himari-standard --list
```

Эти три примера запросов в `packages/standards/examples/` прогоняются тестовым
набором, поэтому задокументированные вызовы не могут устареть.

Неизвестные ключи отвергаются, а не игнорируются; любая ошибка возвращает тот же документ с `values` = `null` и причиной в `errors`
(код выхода 1, с однострочной диагностикой в stderr); код 2 зарезервирован для неправильного использования командной строки. Запросы, чьи десятичные числа участвуют в **решении об
округлении**, должны нести эти числа как десятичные строки, потому что двоичное число с плавающей точкой уже потеряло последнюю цифру к моменту, когда крейт его видит.

## Канал доказательств: `himari-lean` (2026-11-23)

`packages/lean` — это Lean 4 **сопроцесс**: он генерирует самодостаточное обязательство доказательства, передаёт его настоящему исполняемому файлу `lean` через stdin
(`lean --stdin --json -T <heartbeats> -M <MB>`) и сообщает о результате структурированным документом. Никакого проекта Lake, никакого индекса пакетов,
никакой сети; в сгенерированном файле нет импортов.

- **Динамические данные превращаются только в литеральные целые** *именованного примера утверждения теоремы* — никогда в определение данных, аксиому или идентификатор.
- **Проверено ядром, через `decide`**: обязательство замкнуто над `Int` и закрывается `by decide`. Никакие `native_decide`, `#eval`,
  `implemented_by`, `extern`, `partial`, `sorry` или пользовательские аксиомы не генерируются, и тест сверяет сгенерированный текст с этим списком.
- **Проверка аксиом**: вывод `#print axioms` разбирается, и допускаются только `propext`, `Classical.choice` и `Quot.sound`; нечитаемый отчёт —
  это нарушение, а не прохождение. Отсутствие отчёта не является свидетельством чистоты.
- **Независимый оракул**: тот же определитель вычисляется в Rust с *другим* разложением, поэтому Lean никогда не является единственным свидетелем.
- **`lean_missing` — это полноценная неуспешность**: она означает, что тулчейна не было и **ничего не было проверено**. Она никогда не подаётся как
  «verified» и никогда не даёт код выхода 0. Статусы и коды выхода: `success` 0, `lean_missing` 3, `invalid_request` 4, `proof_failed` 5,
  `resource_exhausted` 6, `axiom_violation` 7, `oracle_mismatch` 8.

**Проверено на реальном тулчейне (Lean 4.36.0, коммит `611c117b`).** Обязательство вехи принимается ядром и вообще не сообщает ни о каких
аксиомах:

```text
status = success            verified = true       exit = 0
lean_message: 'det3_example' does not depend on any axioms
oracle:       rust-i128-permutation det3([1,2,3,4,5,6,7,8,10]) = -3
```

Негативные контроли ведут себя как задумано с тем же бинарником: запрос, утверждающий `expected = -306`, возвращает `oracle_mismatch` (код выхода 8) и
никогда не подаётся как verified, а набор тестов со stub-процессом покрывает пути `proof_failed` / `axiom_violation` / `resource_exhausted`.

Подготовка внешняя по отношению к этому репозиторию и остаётся разовой: установите `elan`, закрепите `leanprover/lean4:v4.36.0`, затем либо добавьте `lean` в `PATH`,
либо укажите на него `HIMARI_LEAN_BIN`. `just lean-verify` генерирует обязательство и запускает тест с настоящим Lean. **Без тулчейна канал деградирует до
`lean_missing` (неуспешность), а `--emit` по-прежнему записывает проверяемый файл `.lean`** — отсутствие Lean никогда не подаётся как верификация.

## Устойчивость к враждебному вводу (2026-11-23)

- **Предел глубины 2048**: каждый выход парсера один раз проверяет глубину IR (`check_depth`), и всё сверх предела сообщает
  «formula nested too deeply (N levels > limit 2048)» вместо того, чтобы позволить где-то ниже переполнить стек рекурсии (SIGSEGV).
  Ограничение стека самого pest тоже срабатывает, и его сообщение также переводится в понятные слова. **Известная граница**: длинная цепочка `a + b + c + …`
  в IR оказывается лево-вложенной, поэтому глубина равна числу термов; число термов в одной формуле поэтому ограничено примерно 2048.
  Отдельная детерминистическая защита от вложенности скобок (256 уровней, `MAX_PARSE_NESTING`) работает до разбора, потому что она должна действовать и там, где
  необязательная фича pest `stack-guard` недоступна (`no_std`).
- **Невидимые символы отвергаются всегда**: zero-width space / bidirectional override / zero-width joiner / BOM / NUL — все они
  называются и отвергаются до разбора (`scan_source`) — они могут сделать так, что формула «при проверке выглядит иначе, чем есть».
- **Предел шагов суммы/интеграла 10^7**: `Σ(i,1,1e9)` из «работает всю ночь» превращается в одну строку ошибки.
- **Вызов функции с отсутствующими аргументами** больше не паникует через индексацию `args[0]`: все три канала (вычисление/генерация/размерность) отклоняют его явно.
- **Структурированные property-тесты** (не случайный набор символов): 600 случайных выражений каждое проходит три проверки — обратная запись в канонической форме разбирается обратно в
  **то же дерево**, обратная запись LaTeX разбирается обратно в **то же дерево**, а `simplify` **сохраняет значение**.
  Все три сейчас показывают 0 неэквивалентностей (`prop-roundtrip`); большой ввод с суммой 1500 термов завершается менее чем за 100 мс.

## Канал одинарной точности (f32) (2026-11-23)

Каждая **вещественная скалярная** формула дополнительно порождает `{name}__f32(p: f32) -> f32` — ту же формулу,
те же правила генерации, изменились только литералы на суффикс `f32` (`Fx::F32`, единственный переключатель, протянутый через генератор).
Измерено f32/f64 = **1.44×** (`SIMD` 8 полос против 4 полос + половина пропускной способности),
от чего напрямую выигрывают игровые движки / аудио DSP / SDR в реальном времени.

Комплексные и матричнозначные формулы **не** порождают вариант f32: кортеж `(f64, f64)` комплексного канала и
`Vec<Vec<f64>>` матрицы — это другой типовой контракт в одинарной точности; это может появиться позже (мы отказываемся выпускать половину канала).

## Инструменты разработчика (2026-11-23)

Три точки входа поставляются вместе (все в пакете `himari-check`, делят один парсер):

| точка входа | назначение |
| --- | --- |
| `himari-fmt --diff` | показать только разницу между канонической и текущей формой (без перезаписи) |
| `himari-fmt --diagnose` | только диагностика разбора + размерности + формы (молчит с кодом 0, когда всё чисто) |
| `himari-fmt --symbols` | список имён `decl` и имён формул (источник данных для автодополнения в редакторе) |
| `himari-eval <file> --set k=v …` | **вычислить**: `Re = 200000 [1]`; `--groups` дополнительно печатает Π-группы Букингема; `--json` для машин |
| `python3 scripts/fmt_check.py --fix` | одна команда, чтобы переложить каноническую форму + перегенерировать сайдкары |

**Ошибки несут каретки**: `FrontError::render_with_source` печатает строку исходника и рисует `^` под offending-столбцом
(все три канала — build.rs / fmt / eval — идут через него) — больше не нужно самому считать до столбца 17.

**Расширение VS Code** (`packages/vscode`) имеет два канала:

| канал | триггер | источник данных |
| --- | --- | --- |
| CLI (по умолчанию, без установки) | открытие / сохранение | `himari-fmt --diagnose` + `--symbols` |
| **LSP** (необязательно) | **ошибки по мере набора** | `himari-lsp` (JSON-RPC через stdio) |

`himari-lsp` — написанный вручную минимальный сервер (без зависимости от LSP-фреймворка): `initialize` /
`didOpen` / `didChange` / `completion` / `codeAction` / `shutdown`, с **инкрементальной синхронизацией текста**.
Его диагностика несёт тот же `himari::Error`, что и библиотека, и выводится на языке, который выбирает `HIMARI_LANG` (с откатом к `LC_ALL`, `LANG`, затем к английскому); доступны все девять языков проекта.
Слой протокола обрабатывает состояние и параметры JSON-RPC как чистые функции, и есть сквозной тест, который действительно запускает процесс и действительно отправляет
кадры `Content-Length`. Задайте `himari.lspPath` в настройках, чтобы переключиться (оставить пустым = канал CLI).

Кандидаты автодополнения = имена `decl` файла + имена формул + таблица унарных функций (включая `det/inv/solve/dot/norm` и т. п.).

## Поверхность LaTeX: многосимвольные имена требуют `\mathrm` (2026-11-23)

В математическом режиме LaTeX «голый» `sigma` — это **пять перемножаемых переменных s·i·g·m·a** (неявное умножение),
поэтому многосимвольные имена в этом диалекте нужно писать `\mathrm{sigma_0}` — и обратная запись выдаёт их так же.
Имена греческих букв (`sigma`, `omega`…) записываются обратно **настоящими глифами** `\sigma` с сохранением подстрочного индекса
(`\sigma_0`). Реализация раньше была заменой подстрок, поэтому `alphabet` превращался в `\alphabet`, а
`betamax` в `b\etamax`, а `sigma` отображалась как пять курсивных букв — ошибка в трёх местах сразу (hover / сайдкар / источник истины документации). Исправлено (`latex_var`).

## Ошибки: один enum, девять языков

Каждый сбой в crate — это один enum, `himari::Error`. Это не набор строк: каждый сбой является
вариантом, **несущим свои данные**, и это сразу даёт три вещи.

- **Стабильный код** — `err.code()` возвращает идентификатор в kebab-case (`dimension-mismatch`,
  `undeclared-symbol`, `no-real-roots`, ...). Тесты и вызывающий код проверяют код, поэтому изменение
  формулировки или перевод никогда их не сломает.
- **Отрисовка на каждом языке** — `err.render(locale)` и `Display` (английский) строят предложение из
  каталога в [i18n.rs](packages/himari/src/i18n.rs). `HIMARI_LANG` / `LC_ALL` / `LANG` выбирают язык
  на границах CLI и LSP; девять локалей — это локали организации
  (`en`, `zh-Hans`, `zh-Hant`, `ja`, `ko`, `fr`, `es`, `ru`, `ar`).
- **Совместимость с `anyhow`** — `Error` реализует `core::error::Error` (то есть `std::error::Error`
  под `std`) и является `Send + Sync + 'static`, без каких-либо обёрток:

```rust
  use anyhow::Context as _;

  fn run() -> anyhow::Result<f64> {
      let dim = himari::parse_unit("N/m")?; // `?` converts automatically
      let e = himari::Error::NoRealRoots { discriminant: -4.0 };
      let err = anyhow::Error::from(e).context("solving the loop equation");
      let root = err.downcast_ref::<himari::Error>().expect("root cause kept");
      assert_eq!(root.code(), "no-real-roots");
      assert_eq!(dim, himari::parse_unit("kg/s^2")?);
      Ok(1.0)
  }

  fn main() {
      assert_eq!(run().unwrap(), 1.0);
  }
```

`tests/anyhow_compat.rs` закрепляет всё это: распространение через `?`, ограничение
`Send + Sync + 'static`, то, что `downcast_ref::<himari::Error>()` возвращает код после
`anyhow::Context`, и правило: одна и та же ошибка отрисовывается по-разному в девяти языках, а код
остаётся неизменным.

`Error::Message(String)` остаётся для ещё не каталогизированных сообщений. Он выводится дословно на
любом языке, поэтому поэтапная миграция видна **в типе**, а не выдаётся за переведённую; оставшиеся
места измеряются **гейтом, а не текстом**: `python3 scripts/staging_budget.py` считает всех некаталогизированных производителей во всех деревьях производства рабочего пространства (`packages/`, `examples/`, `tools/`) (`Error::from(`, `Error::Message(`, а во фронтендах `FrontError::plain("…")` / `plain(format!(…))` / `FrontError::new(…, "…")`), исключая тесты и сам каталог, и падает, если сумма превышает записанный потолок (потолок записан в `tools/staging-budget/src/ceiling.txt` и может только снижаться). Гейт — это обход AST (`tools/staging-budget` на `syn`): счёт не зависит от раскладки строк, пробелов и комментариев, а *шаблон* вроде `matches!(e, Error::Message(m) if …)` никогда не принимается за конструкцию. Потолок может только снижаться, и это применяется принудительно: CI запускает гейт с `--against-git`, читает `tools/staging-budget/src/ceiling.txt` из `HEAD` и падает, если потолок в рабочем дереве выше. Все 38 вариантов каталога закреплены тестом `catalogue_completeness_tests`: каждый конструируется и рендерится на девяти языках (непусто, без утечки `{n}`). *Заголовки* быстрых правок LSP пока остаются китайскими; его диагностика локализована.

```text
python3 scripts/staging_budget.py                # counts + ceiling
python3 scripts/staging_budget.py --against-git  # also: the ceiling may only go down vs HEAD
```

### Интеграция с редактором (LSP)

`himari-lsp` — написанный вручную LSP-сервис (слой протокола — чистые функции, с юнит-тестами + сквозным тестом через stdio):

| возможность | описание |
| --- | --- |
| диагностика | отправка `publishDiagnostics` после `didOpen`/`didChange` (необъявленные символы, несовпадения размерностей, синтаксические ошибки) |
| автодополнение | имена `decl` файла + имена формул + таблица унарных функций (`det/inv/solve/roots/...`) |
| **быстрое исправление** | `textDocument/codeAction`: необъявленный символ → ① переписать на ближайшее объявленное имя ② добавить строку в блок decl; опечатка в имени функции → имя из реестра |
| синхронизация | **инкрементальная синхронизация** (`textDocumentSync: 2`, по диапазонам); полные изменения тоже принимаются, поэтому старые клиенты не ломаются |

Быстрое исправление предлагает замену только тогда, когда имя встречается **ровно один раз** (если оно встречается несколько раз, предлагается только «добавить объявление»,
и никогда не угадывается, какое вхождение имелось в виду); значения вне диапазона всегда **ограничиваются**, а не отбрасываются (отбрасывание навсегда
рассинхронизировало бы буфер с редактором).

### Блокировки содержимого библиотек формул: когда библиотека меняется, она обязана заговорить

`use "lib/…"` **встраивает** файл библиотеки, поэтому когда библиотека меняется, сгенерированный код ниже по потоку меняется вместе с ней — именно тот вид
регрессии, который проще всего пропустить. `--lock` записывает отпечаток каждого файла, на который есть ссылка, в `<entry>.lock`, и с этого момента **блокировка проверяется при каждой загрузке**:

```text
$ himari-fmt --lock formulas/entry.formula
已写入 formulas/entry.formula.lock（4 行）

$ himari-eval formulas/entry.formula         # someone quietly changed the library
himari-eval: 公式库与锁文件不一致（formulas/entry.formula.lock）：
  内容变了（声明版本 1.4.2 → 2.0.0）：lib/atmosphere.formula
              复核改动后运行 `himari-fmt --lock <入口>` 重新生成锁。
```

(Вывод CLI цитируется дословно: инструмент всё ещё печатает по-китайски. По-английски: библиотека
и её файл блокировки расходятся — `lib/atmosphere.formula` изменил объявленную версию 1.4.2 → 2.0.0 — перезапустите
`himari-fmt --lock <entry>` после просмотра изменения.)

- **Содержательный хеш sha256** (а не диапазон semver): для зависимости вида «встроенный исходник» содержательный хеш —
  более сильная гарантия: ловится любое изменение, не нужна политика разрешения версий, не нужны правила предвыпусков.
- **Обычный текст, детерминистичный, пути относительно каталога точки входа**: его можно коммитить в git, diff читаем, и он сравним между машинами.
- **Замкнутая проверка**: `scripts/fmt_check.py` прогоняет `--lock-check` по файлам, у которых есть `.lock`
  (и автоматически перезапирает под `--fix`) — устаревшая блокировка краснеет в проверке, не дожидаясь, пока кто-то загрузит файл.
- **opt-in**: без `.lock` ничего не проверяется (нулевое влияние на существующие репозитории). Как только блокировка есть, **новая ссылка тоже даёт ошибку**
  (семантика белого списка); чтобы её принять, нужно перезапереть.
- **Нечитаемая блокировка — тоже ошибка**: не UTF-8 (сохранена редактором как UTF-16), недостаточные права или путь к каталогу
  — всё это жёсткие ошибки; они никогда не могут трактоваться как «блокировки нет», что молча отключило бы защиту.
- **У `--fix` три стадии** (сначала отформатировать всё → затем перезапереть всё → наконец перегенерировать каждый сайдкар):
  сайдкары проверяют блокировку при загрузке, поэтому блокировка должна быть окончательной сначала; и то и другое также зависит от окончательного содержимого библиотек, на которые есть ссылки,
  а смешивание в одном цикле оставляет устаревшие артефакты.
- `%! version: 1.2.0` — только колонка для человека (она запирается, и об изменённой версии сообщается); семантическая гарантия опирается на хеш.
- Почему нет диапазонов semver: это потребовало бы целой политики разрешения/закрепления/предвыпусков, тогда как форма зависимостей этого репозитория —
  «встроенный исходник». Выразить «разрешить незначительный дрейф» — это прямое утверждение через перезапирание.

### Директивы диалекта: аналог «макрос — это диалект» для файлового канала

Файл не обёрнут макросом, поэтому соответствующее правило таково: **по умолчанию matex; LaTeX объявляется явно.** Оба канала разделяют один принцип —
никакого угадывания, семантику решает автор, а не парсер.

```text
%! dialect: latex
decl {
    s : d;
    i : d;
    si : d;
    x : d;
}
q = si * x        % LaTeX semantics: s·i·x (not the declared si·x)
```

- Поддерживает `%! dialect: latex` (или `tex`) и `%! dialect: matex` (или `matlab`).
- **Нет директивы = matex**. Раньше здесь был запасной путь AUTO (если разбор matex не удался и исходник содержал `\`, пробовать LaTeX),
  и он давал ровно то молчаливое неверное значение 200 против 30 выше — он удалён.
- Нотация только для LaTeX без директивы диалекта → разбирается как matex по умолчанию → **ошибка** (никогда не молчаливо неверное значение);
  ошибка предлагает выход (написать `%! dialect: latex`), но **не угадывает за вас**.
- Действует только **до первой некомментированной строки** (директива `%!` внутри комментариев тела диалект не меняет).
- Нераспознанное значение — ошибка.
- С директивой ошибки сообщаются в этом диалекте: синтаксическая ошибка при директиве LaTeX — это ошибка LaTeX.
- Реализовано ровно в одном месте (`himari_loader::parse_source`), поэтому канал build.rs, `himari-fmt`,
  `himari-eval` и диагностика LSP согласованы. (диагностика LSP выводится на языке, который выбирает `HIMARI_LANG`; см. раздел «Ошибки».)

### Деление на поверхности LaTeX (когда-то отсутствовало)

`a / b` и `a \div b` теперь — настоящее деление, синонимичное `\frac{a}{b}`, с тем же приоритетом, что у умножения, и левоассоциативное.
Раньше на поверхности LaTeX **вообще не было оператора деления** — принимался только `\frac{a}{b}`, а `a / b` был синтаксической ошибкой.
Это выбрасывало ребёнка вместе с водой: `/` — самый обычный способ записать деление, и не было причин его отвергать.
(Запасной путь AUTO выше на деле прикрывал именно этот дефект: он заставлял `a / b` «случайно работать», принося с собой молчаливое неверное значение.
Исправьте дефект — и у запасного пути не останется причин существовать.)

## Символьное линейное решение `solve` (2026-11-23)

Однопеременная форма `solve(equation, variable)` решает `equation = 0` как `variable = -b/a` (уравнение должно быть **линейным** по этой переменной).

```text
ES_ss = solve(k_on * E * S - (k_off + k_cat) * ES, ES)
      → ES_ss = k_on·E·S/(k_off + k_cat)          % Michaelis–Menten steady state
```

- Решение **всё ещё IR**: поэтому оно сохраняет проверку размерности, вычисление, генерацию кода, аналитические производные и
  якобиан — второй механизм не нужен. Частные производные и строки якобиана для `ES_ss` получаются автоматически.
- **Список параметров = переменные, которые реально использует сгенерированное выражение**: переменная, для которой решали, `ES`, не появляется среди параметров `ES_ss`
  («её просят, но её всё равно надо передать» исправлено). Сайдкар / hover / автодополнение читают тот же список параметров.
- **Нелинейность отклоняется явно**: `x·x`, `1/x`, `x^2`, `sin(x)` дают ошибку **на выходе парсера** и называют задействованный вид;
  никакого численного приближения, никакого сомнительного ответа. Ошибка в химическом стационарном состоянии стоит гораздо дороже, чем набрать несколько лишних символов.

### Системная форма `solve([equations…], [unknowns…])`

Когда оба аргумента — списки, включается канал **линейных систем**, а решение — **вектор-столбец** (канал значений матричных выражений,
возвращающий `Vec<Vec<f64>>`):

```text
x = solve([(k1 + k2) * x1 - k2 * x2 - F1,
           -k2 * x1 + (k2 + k3) * x2 - F2], [x1, x2])
  → x = 2×1 column vector, dimension [m]           % two-mass spring statics
```

- **Символьное исключение**: исключение Гаусса–Жордана выполняется над **кольцом выражений** (коэффициенты — это подвыражения IR, а не числа),
  с приведением к нормальной форме на каждом шаге. Каждая решённая компонента всё ещё IR и проходит размерности/вычисление/генерацию как обычно.
  **Но системное решение матричнозначно**: матричнозначные формулы не генерируют аналитических производных (поэлементные частные производные — не матрица; матрица — это якобиан)
  и не генерируют вариант f32 — это существующее ограничение матричнозначного канала, а не особенность `solve`.
- **Соглашение о форме**: списки уравнений и неизвестных **выравниваются в строку** (flatten, row-major), поэтому `[e1, e2]` и `[e1; e2]` эквивалентны —
  пользователю не нужно помнить ориентацию. Элементы списка неизвестных должны быть «голыми» именами переменных.
- **Неизвестным нужны объявленные размерности**: это покупает **проверку размерности результата** (пример с пружинами решает `m = N/(N/m)`)
  а также проверку **однородности** самих уравнений (`x1 − F1`, сложение m с N, отклоняется на этапе разбора).
  Решённые неизвестные не попадают в список параметров (сгенерированная функция принимает только настоящие параметры).
- **Отказ — это функция**: недоопределённая (не полного ранга), противоречивая (после исключения `0 = ненулевое`), нелинейная (неизвестная встречается по обе стороны от
  умножения / в знаменателе или показателе / внутри аргумента функции) — **все сообщаются на выходе парсера**.
  Отказы, связанные с размерностями, происходят в `dims_of_set` / на стадии генерации (сам парсер не проверяет размерности).
  Избыточные уравнения удаляются «в сворачиваемом смысле»: избыточная строка с символьными коэффициентами, которая не сворачивается в ноль, консервативно
  сообщается как противоречивая — лучше отказать, чем вернуть неверное решение.
- **Ненулевой ведущий элемент и численная граница**: то же соглашение, что у однопеременного `solve`, — то, что нельзя доказать нулевым, считается
  ненулевым (мы доверяем `a ≠ 0`). Исключение происходит на этапе компиляции в порядке выражений и **не переставляет строки по |ведущему элементу| во время выполнения**;
  при экстремальных масштабах замкнутая форма сокращается, сингулярный параметр сообщает деление на ноль в слое значений и даёт `inf/NaN` по IEEE в
  сгенерированном коде — это не исключение. Плохо обусловленные системы или системы, которым нужна стратегия выбора ведущего элемента, должны идти в численную библиотеку.
- **Границы (четыре, все отклоняются на выходе парсера или как ошибки компиляции)**:

  1. Коэффициент или постоянный член **матричнозначный** (`solve(M*x - b, x)`, `solve([M*x - b], [x])`) → отклоняется явно с
     указанием на `inv(A) * b` — иначе скалярный канал сгенерировал бы деление `vec!`, которое не компилируется.
  1. **Уравнения могут иметь разные размерности** (баланс сил в N плюс геометрическое ограничение в m — законная система), но каждое уравнение должно быть
     однородным само по себе; и каждая компонента решения должна иметь **одну размерность** (неизвестные разных размерностей — решение одновременно для тока и
     сопротивления — пока не поддерживаются; это ограничение матричнозначного канала).
  1. Комплексный канал (с `j`) работает **в слое значений** и **в слое генерации** (завершено 2026-11-23): комплексный вектор-столбец
     генерируется как `Vec<Vec<(f64, f64)>>`, элементы — (вещественная, мнимая). Узловой анализ цепей переменного тока и «системы комплексных уравнений»
     в стиле EIS поэтому могут генерироваться прямо в код.
  1. **Проверка на ноль у избыточных строк — достаточное условие**: нули, которые доказывает приведение подобных (`k−k`, `k·a−a·k`, `x·x²−x³`),
     распознаются; сложное тождество, которое нельзя доказать нулевым, трактуется как ненулевой коэффициент (консервативно — оно может ложно сообщить
     о недоопределённости/противоречивости, но неверного решения не вернёт).

### Корни многочленов `roots(poly, x)`

`solve` даёт линейную замкнутую форму; `roots` даёт **все корни многочлена** (как вектор-столбец):

```text
roots_quad = roots(a * x ^ 2 + b * x + c, x)
% q = −(b + sign(b)·√(b²−4ac))/2; large root = q/a, small root = c/q
% Return order still matches the original formula (−b−√Δ first); it does not depend on sorting the roots by size.
```

- **Только степени 1–2**: степень 1 — та же математика, что у `solve`; степень 2 — формула корней в замкнутом виде.
  **Степень 3 и выше отклоняется явно** с сообщением фактической степени — Кардано/Феррари ужасно обусловлены в плавающей точке,
  и этот репозиторий не будет выдавать «выглядящее точным» приближение. Для корней степени три и выше сначала вычислите коэффициенты численно,
  а затем используйте численную библиотеку.
- **Кратные корни повторяются с кратностью** (`x² − 2x + 1` даёт две единицы), в согласии с основной теоремой алгебры;
  запасной путь `q=0` для нулевого корня — `-b/(2a)`, и он не проходит через `0/0`.
- **Избегание сокращения в формуле квадратного уравнения**: прямое использование `(−b±√Δ)/(2a)` теряет малый корень при `b²≫4ac`
  (`x²−10⁸x+1` однажды вычислил `10⁻⁸` примерно как `7.45×10⁻⁹`). Теперь используются устойчивые `q/a` и `c/q`, а порог приёмки для
  относительной ошибки малого корня в сгенерированном коде — `1e-12`; есть регрессии для обоих направлений знака и для комплексного канала.
- **Размерности получаются автоматически**: уравнение должно быть размерностно однородным, а однородность прямо влечёт «размерность корня = размерность
  переменной», поэтому дополнительный вывод размерности не нужен (это рассуждение охраняется контрактным тестом).
- **Отрицательный дискриминант в вещественном канале**: сгенерированный код возвращает типизированную ошибку, **а не NaN** — вещественная точка входа `roots` для квадратного уравнения теперь возвращает
  `Result<_, himari::runtime::NumericError>`, а отрицательный дискриминант — это `NumericError::NoRealRoots { discriminant }`. Молчаливого
  контракта с NaN больше нет, поэтому проверки `is_nan`/`is_finite` больше не являются способом обнаружить этот случай; константный дискриминант,
  доказуемо отрицательный на этапе компиляции, всё равно отвергается сразу. `eval_value` — это общий комплексный слой значений, и он **по-прежнему возвращает комплексные корни**
  для того же выражения в комплексном канале; комплексному каналу нужен явный `j`.
- **Сокращающиеся члены высших порядков удаляются**: `x³ − x³ + x − 1` трактуется как степень 1 (а не «отвергается, потому что в многочлене есть x³»).
- **Немногочлены отклоняются явно**: `x` внутри аргумента функции, в знаменателе или в нецелой степени — каждый со своей причиной.
- **Матричнозначные коэффициенты** отклоняются (то же соглашение, что у `solve`, иначе скалярный канал сгенерировал бы деление `vec!`).

### Вектор коэффициентов `poly_coeffs(poly, x)`

Дополнение к `roots`: он даёт **коэффициенты** (от младших к старшим), возвращая вектор-строку `1×k`.

```text
coeffs = poly_coeffs(2 * s ^ 2 - 3 * s + 1, s)   → [[1, −3, 2]]
```

- **Переменная должна быть безразмерной**. Размерность коэффициента при степени k однородного многочлена — `dim(poly)/dim(x)^k`, и они различаются;
  но матрица требует **элементов одной размерности** — поэтому взятие коэффициентов у размерной переменной алгебраически невозможно в такой форме.
  Эта проверка объясняет это прямо на стадии диагностики и предлагает выход (разделить на характерную величину или использовать `roots`), вместо того чтобы дать
  ниже по потоку сообщить «размерности элементов матрицы различаются».
- Нулевые коэффициенты старших степеней удаляются (`x³ − x³ − 2x + 1` — степень 1); нулевой многочлен отклоняется.
- Немногочлены (`sin(x)`, `1/x`, нецелые степени) отклоняются.
- Он использует тот же извлекатель `poly_coeffs`, что и `roots` — одно определение семантики коэффициентов, два потребителя.

### Корни выше третьей степени: `himari-eval --roots`

Отклонять степень ≥ 3 в языке — вынужденный компромисс, но **численный** поиск корней работает для любой степени, поэтому он живёт в слое инструментов:

```text
$ himari-eval cubic.formula --roots
cubic = 1, 2, 3  [1] (degree 3, 3 roots)
cplx  = -1, 0.5-0.8660254037844387j, 0.5+0.8660254037844386j  [1] (degree 3, 3 roots)
```

- **Итерация Дуранда–Кернера** (переиспользуя `C` из core для комплексной арифметики, без сторонней численной библиотеки): начальные значения — степени
  `0.4 + 0.9j`, радиус — **геометрическое среднее модулей корней** `|c₀/cₙ|^(1/n)` (с откатом к границе
  Коши `1+max|cᵢ|` только в вырожденных случаях); не более 1000 итераций; критерий DK — `|Δz| ≤ 1e-10·radius` (относительно модуля корней,
  а не относительно 1); затем **60 шагов полировки Ньютоном** (относительный критерий остановки `1e-15·|z|`).
- **Невыход на сходимость — это ошибка**, а не ещё-не-сошедшееся приближение, возвращённое как результат; `inf`/`NaN` во время итерации тоже немедленная ошибка
  (`f64::max` для NaN возвращает другую сторону, что однажды заставило шаг с NaN выглядеть «сошедшимся» и вернуло 20 NaN).
- **Приёмка по невязке**: после итерации относительная обратная ошибка `|p(z)| / Σ|aₖ|·|z|ᵏ` должна быть достаточно мала (порог 1e-8),
  иначе ошибка — DK не гарантирует сходимости к корню, и критерий должен быть независим от самой итерации.
  Знаменатель **должен включать член `k=n`**: без него знаменатель при малых `|z|` вырождается в константу `|a_n|`,
  и `x²−1e-100` прошёл бы, будучи неверным в 4e25 раз (реальная регрессия).
- **Полировка Ньютоном** (относительный критерий): простой корень достигает машинной точности; **кратный корень сходится лишь линейно**, поэтому `x²−2x+1` и
  подобные имеют относительную ошибку порядка `1e-9` и ошибки не дают — это свойство алгоритма, а не баг; не считайте кратный корень
  простым.
- **Предел степени 16** (предел разложения многочлена у `poly_coeffs`; сам `numeric_roots` поддерживает до 64).
- **Моническая нормализация** перед итерацией (деление на старший коэффициент), чтобы избежать переполнения величины; предел степени 64; коэффициенты `inf`/`NaN` отклоняются.
- **Обнуление шума очищает только мнимую часть, и критерий относительный**: вещественный корень несёт мнимый остаток порядка `1e-16`, что является
  артефактом итерации; критерий — `|im| ≤ 1e-12·|z|`. **Вещественная часть не трогается никогда** (корни `x²−1e-50` — ±1e-25),
  и **абсолютный порог тоже не годится** — для комплексного корня с модулем ниже 1e-12 мнимая часть — это вся информация в корне
  (`x³−1e-60` однажды был размазан в три вещественных корня на этом основании, относительная ошибка 0.87, без ошибки).
- Коэффициенты должны вычисляться в числа при параметрах, заданных `--set`; когда переменная опущена, она выводится как «единственный объявленный символ в
  формуле», а несколько кандидатов требуют `--var`.
- В выводе есть степень и число корней; комплексные корни записываются как `a+bj`.

## Комплексные матрицы и системы комплексных уравнений (2026-11-23)

Комплексность не только скалярна: элементы матриц и векторы решений тоже могут быть комплексными, и **слой значений и слой генерации согласованы**.
Тип возврата сгенерированной функции — `Vec<Vec<(f64, f64)>>` (элемент = (вещественная, мнимая)):

```rust
// I = solve([Z*I1 - V, Z*I1 - R*I2], [I1, I2]) with Z = R + jωL
pub fn I(R: f64, w: f64, L: f64, V: f64) -> Vec<Vec<(f64, f64)>> { … }
```

- Типичные применения — **узловой анализ цепей переменного тока** и моделирование EIS: неизвестные — это комплексные токи/потенциалы.
- Транспонирование — **обычное транспонирование** (без сопряжения) — сопряжение это отдельный оператор `conj`; не путайте их.
- `adjoint` — сопряжённое транспонирование; разворачиваться могут только литералы, форма которых известна на этапе компиляции.
- В комплексном канале `det/trace/adjoint/inv/solve/roots/dot/norm` **также** разворачиваются на уровне IR перед генерацией (историческая асимметрия:
  вещественный канал разворачивал, а комплексный сразу шёл к `compile_error!`).
- По-прежнему не поддерживается: **канал no_std/libm** для комплексных формул (замыкания зависят от std), **аналитические производные** для комплексных формул
  (`abs/arg/conj/re/im` не комплексно-аналитичны, для этого нужны вычисления Виртингера) и **вариант f32** для комплексных формул.

## Канал WGSL (GPU): подмножество + граница валидации (2026-11-23)

`himari-fmt --wgsl <file.formula>` генерирует вещественную скалярную формулу как ядро f32:

```wgsl
// Generated by himari (f32 scalar lane; really compiled and validated by naga)
fn q(rho: f32, v: f32) -> f32 {
    return 0.5f * rho * (v * v);
}
```

**Поддерживаемое подмножество (намеренно маленькое)**: `+ - * /`, `sqrt`, `exp`/`log` (здесь `ln`) `sin cos tan
sinh cosh tanh abs min max clamp`, плюс степени 2/3, квадратный корень и степень -1.
**Явно отклоняется**: комплексные (`j`), матрицы, `det/inv/solve`, Σ/∫, символьные операторы, другие степени
и символы, совпадающие с зарезервированными словами WGSL — каждый с причиной (мы не генерируем ядро, которое не компилируется).

**Валидация в два слоя** (с 2026-11-24 у канала WGSL есть доказательство **на уровне компилятора**):

1. **Настоящая компиляционная проверка** (авторитетная): `cargo test -p himari-check --features wgsl-compile`
   передаёт каждое сгенерированное ядро в фикстурах **naga** (компилятору шейдеров от wgpu, одной из авторитетных реализаций спецификации WGSL) для
   настоящего разбора + настоящей валидации. naga — чисто CPU-зависимость для разработки — **GPU не нужен**, и он никогда не попадает в дерево рантайм-зависимостей.
1. **Статическая проверка** (быстрый скрининг, `wgsl::validate_wgsl`): баланс скобок, сигнатура `-> f32`, ровно один
   `return`, литералы с плавающей точкой с `f`, без `^`/`**`, без нефинитных констант. Её ценность — «ловля грубых ошибок в окружениях без naga
   + сообщения об ошибках ближе к этому каналу»; **это не доказательство корректности**.

**Почему настоящая компиляционная проверка обязательна — конкретный урок**: каждое ядро этого канала WGSL раньше было **невалидным**.
В WGSL нет функций с телом-выражением; тело должно быть `return expr;`, а генератор всегда выдавал голое выражение;
хуже того, статическая проверка **запрещала `return`** — потому что правило было написано без знания этой части спецификации, превратив
непонимание в «правило». Слепое пятно статической проверки — не «оно что-то пропустит», а «**оно не знает, что пропустило,
и может даже признать корректный код неверным**». Первый прогон naga вскрыл весь класс.
Ещё одно исправленное убеждение: `return 2.5;` **законен** в naga (абстрактный float по контексту становится f32) — поэтому «float'ы должны нести `f`» — это стилистическое
соглашение этого канала, а не спецификация WGSL.

**Граница валидации (сказано честно)**: naga проверяет только **синтаксис и типы**. «Вычисляет ли ядро правильные числа на реальной GPU» по-прежнему
не проверено — для этого нужен рантайм wgpu + GPU (на node-3 есть RTX 5880, подключение ожидается).
Также tint (реализация Chrome/Dawn) и naga различаются в нескольких пограничных правилах; этот репозиторий отвечает только перед naga.

## Что не заявляется

Это ограничения области, а не почти готовый список дел. Говорите «не заявлено» там, где написано «не заявлено».

- **Нет выбора ведущего элемента во время выполнения в символьном канале**: символьный `solve` исключает в порядке выражений и доверяет `a ≠ 0`; он не переставляет строки по
  величине ведущего элемента. Плохо обусловленные системы или системы, чувствительные к выбору ведущего элемента, относятся к каналу времени выполнения (`solve(A,b)` выше) или к численной библиотеке.
- **Матрицы-шаблоны только через файловый канал**: канал конструктора для матриц-шаблонов требует имени файла и генератора, поэтому встроенные макросы отклоняют их
  с указанием; нет автоматического разворачивания произвольных матриц-шаблонов (исследовательский уровень — всё вне встроенных форм отклоняется явно
  со списком поддерживаемых).
- **Численная валидация WGSL всё ещё ожидается**: naga доказывает синтаксис и типы, а не то, что ядро вычисляет правильные числа на GPU. Запуска на GPU здесь не было.
- **Проверка Lean не удалась**: на этом хосте не установлен тулчейн, поэтому прогонялись только тесты со stub-процессом. Нет утверждения, что Lean принимает
  сгенерированные обязательства доказательств.
- **`publish = false` — это шлюз человеческой проверки**: крейты намеренно непубликуемы, пока проверку не снимет человек; см. «Статус».
- **Область `no_std`**: `himari`, `himari-latex` и `himari-matlab` — это `no_std + alloc`; крейты loader/buildhelper/macros/check — нет.
  Сгенерированный код сохраняет свой канал libm, а комплексные формулы не входят в канал `no_std`.
- **Нет комплексных аналитических производных, нет варианта f32 для комплексных или матричнозначных формул, нет аналитической производной для матричнозначных формул.**
- **`roots` покрывает в языке только степени 1–2**; высшие степени — только численно через `himari-eval --roots`.
- Общий LaTeX (макросы/catcode/вёрстка) — неразрешимая семантика; вёрстка относится к слою рендеринга.
- Нет вывода семантики по начертанию и нет умножения `xy` на поверхности MATLAB. Нет `\sin^2 x`, нет `.*`, нет `$…$` (неоднозначная или чисто
  типографская нотация: разбор и рендеринг — две разные задачи, и один парсер не должен делать и то и другое).
- Нет JIT во время выполнения на путях реального времени/критичных для безопасности; никаких AGPL-зависимостей, никогда (evalexpr ≥12 и подобные исключены).
- Модули **`himari-standards`** — калькуляторы уровня пункта, **а не заявления о соответствии**: они не моделируют геометрию образца, выбор уровня нагрузки,
  время выдержки, бюджеты неопределённости или собственные правила отчётности стандартов, и они не являются универсальной библиотекой единиц.
- Канал **`himari-lean`** доказывает одно небольшое замкнутое целочисленное обязательство (пример определителя 3×3); это не универсальный доказатель теорем, а его
  проверка аксиом — это парсер по собственному выводу Lean, а не аргумент о корректности.
