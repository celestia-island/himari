## 이 문서가 다루는 것

- 수식을 **하나만** 작성하면 됩니다(LaTeX 부분집합 / 논문 표기법 / MATLAB 스타일, 원하는 것을 선택). 그것이 동일한
  **차원 IR**로 내려간 뒤, 이름이 붙은 중간값과 소스 주석을 갖는 Rust 함수로 컴파일됩니다.
- 차원(일곱 개의 기본량 kg·m·s·A·K·mol·cd)은 컴파일 시점에 강제됩니다: `m + s`는 그냥 컴파일되지 않습니다.
- 기호 미분, CSE, 상수 폴딩이 기본으로 들어 있으며, 해석적 편미분은 중심 차분에 대조하는 테스트로 고정됩니다.
- **행렬은 일급 시민입니다**: 구체 행렬은 완전히 검사되며, **패턴 행렬**(줄임표 포함)은 동적 크기를 표현합니다.
  교과서의 `[b c ⋯ 0; a b c ⋯; ⋯ a b c; 0 ⋯ a b]`는 쓴 그대로가 소스 코드입니다.

## 페더레이션과 여러 줄 작성 (2026-11-23 두 번째 결정)

**하나의 매크로 블록이 서로를 참조하는 수식 그룹 전체를 담을 수 있습니다**("페더레이션"):

```rust
formula_matlab!{
    decl { F : force [N]; m : mass [kg]; r : radius [m]; }
    accel = F / m
    mech = ( accel * r )^(1/2)
}
// expands to a let chain: let accel = F / m; let mech = (accel * r).sqrt(); mech
```

- **항목 구분자** = 세미콜론 또는 **줄바꿈**이며, 이는 **세 레인 모두에 적용됩니다**(토큰 레인은 proc-macro의 span 줄 번호에서
  줄바꿈을 재구성하는데, 그 줄 번호가 소스 파일에 정렬되어 있으므로 진단도 같은 줄을 가리킵니다).
- **뒤 항목은 앞 항목을 참조할 수 있습니다**: 차원은 이름을 따라 전파됩니다(accel의 m/s²가 심볼 테이블에 합류).
  build.rs 레인은 생성 시점에 치환을 인라인합니다.
- **이름이 곧 계약입니다**: 수식이 `decl` 이름을 재사용하면 그 결과 차원이 해당 선언과 일치해야 하며
  (`a = F/m`은 괜찮고, `s : Pa; s = F/d`는 거부됩니다), 하나의 수식 집합이나 하나의 생성 디렉터리 안에서 중복된 수식 이름은 항상 거부됩니다.
- **연산자 연속 모델**: 연산자는 반드시 **줄 끝**에 있어야 합니다(`x +⏎ y` ✓). 다음 줄의 선행 `-`/`+`는 새 항목의 부호를 시작하며,
  줄이 이어진 뺄셈이 아닙니다 — 이것이 그 구분 결정입니다.
- LaTeX 표면의 암시적 곱셈(병치)은 **반드시 한 줄에 있어야 합니다**: 줄을 걸쳐 병치하면 다음 수식을 곱셈 항으로 삼켜 버립니다.

**행렬 여러 줄 작성**(행마다 물리적 한 줄, 열 간격은 자유이며 정렬이 필요 없습니다):

```text
[ 2*k, -k,    ...,   0 ;
  -k,  2*k,   -k,    ... ;
  ..., -k,    2*k,   -k ;
  0,   ...,   -k,    2*k ]
```

- 행 구분자 = `;` 또는 줄바꿈(혼용 가능, 끝에 붙여도 됨), 열 구분자 = 쉼표 또는 공백(1개 이상, 개수 무관).
- 셀 안의 줄임표 `...` / `⋯` / `…`는 "그 위치를 생략함"을 뜻합니다(가로/세로/대각 여부는 다시 쓸 때 추론됩니다).
- **앞에 공백 없이 쓴 `-`는 부호이고, 앞에 공백이 있으면 새 열이 시작됩니다**(MATLAB 의미론): `[k-1]`은 한 열, `[k -1]`은 두 열입니다.

## 복소수: 값 계층에서 코드 생성까지 끝까지 연결됨 (2026-11-23)

- **`j`는 예약된 허수 단위입니다**(항상 무차원이며, 선언하지 않고, **매개변수 목록에 절대 들어가지 않습니다**). `Z = R_s + j*X`를 바로 쓸 수 있습니다.
- 값 계층에는 정확히 두 가지 변형만 있습니다: `Value::Scalar(C)` / `Value::Matrix(Vec<Vec<C>>)`, 여기서 `C = {re, im}`.
  실수는 허수부가 0인 복소수이므로 ⇒ **복소 행렬, 전치, 곱셈, 덧셈과 뺄셈은 모두 공짜로 원소 단위로 성립합니다**.
  "실수 행렬 / 복소 행렬" 사분면 분할이 필요 없습니다.
- 초월 함수는 실수와 복소수가 하나의 테이블을 공유합니다: `exp ln sqrt sin cos tan sinh cosh tanh` +
  `abs arg conj re im`(마지막 네 개는 항상 실수축으로 되돌아옵니다). 복소 지수는 주 가지에서 `exp(w·ln z)`를 거칩니다.
- **`eval`은 복소값에서 명시적 오류를 보고합니다**(허수부를 조용히 버리지 않습니다). 복소값이 필요할 때는 언제나 `eval_value`를 쓰십시오.
- **코드 생성에는 별도의 복소 레인이 있습니다**: 수식에 `j`가 있으면 `-> (f64, f64)` = (실수, 허수)로 출력되며,
  블록 지역 헬퍼(`__c_mul` / `__c_sqrt` …) 중에서도 **실제로 쓰인 것만 출력됩니다**(그러지 않으면 clippy `-D warnings`가 빨개집니다).
  배치 진입점은 `out: &mut [(f64, f64)]`이며 EIS 주파수 스윕에 바로 쓸 수 있습니다.
  매크로 레인(`formula!` 등)도 같은 방식으로 분류합니다: `j`는 호출 지점에서 자유 변수로 **강등되지 않으며**,
  페더레이션된 `let` 체인 안에서 이미 복소인 바인딩은 올바르게 상속됩니다(`emit_block_complex_with`).
  복소 레인은 **해석적 도함수를 생성하지 않습니다**: `abs/arg/conj/re/im`은 복소 해석적이 아니므로 연쇄 법칙이 성립하지 않습니다.
- **생성된 코드와 값 계층이 점별로 일치해야 한다**는 것은 강한 제약입니다: `__c_powf`는 `C::pow_real`의 정수 분기를 그대로 따르고
  (음의 실수 밑의 정수 거듭제곱은 정확히 실수축에 안착해야 합니다), `__c_sqrt`는 값 계층과 마찬가지로 `hypot`를 써서 큰 크기에서의 오버플로를 피합니다.
  `__c_div`가 IEEE를 따르는 반면 값 계층은 오류를 내는 것은 의도된 것입니다 — 이들 각각은 픽스처의 연산자별 비교 테스트로 보호됩니다.
- 단위 문자열은 유리수 지수를 받습니다: `[V/A*s^(-1/2)]`(대괄호는 필수이며, 그렇지 않으면 지수의 `/`를
  단위 문자열의 나눗셈 기호와 구별할 수 없습니다). 나누어떨어지지 않는 지수(`m^(1/3)`)는 명시적으로 거부됩니다. 무차원량에는 `[1]`을 쓰십시오
  (이득 / 개수 / 몰분율은 모두 선언 가능해야 하며, "단위 생략"으로 몰래 들어와서는 안 됩니다).
- **`himari-fmt --diff <file>`**: `--- current / +++ canonical`
  통합 diff를 출력하는 읽기 전용 미리보기(변경 없음 → 출력 없음, 종료 0; 변경 있음 → 종료 1).
- **실수와 복소 사이의 의미론적 경계**(의도된 것이며 누락이 아닙니다): `1/0`은 예전에 `inf`를 냈지만 이제 **오류**입니다.
  `ln(0)`도 마찬가지이고, `(-2)^0.5`는 "결과가 복소수이므로 `eval_value`를 쓰십시오"를 보고합니다.
  생성된 코드는 대신 IEEE 의미론을 따릅니다(0으로 나누면 inf/NaN): 핫 패스에는 오류 경로가 없고,
  수식 계층이 정적으로 틀렸다고 증명할 수 있는 것은 dim/shape 게이트가 잡습니다.
- **`python3 scripts/fmt_check.py --fix`**: 표준형을 다시 배치하고 사이드카를 재생성하는 한 줄 명령입니다.

## 단위: SI 접두어, 변환, 무차원 군 (2026-11-23)

- **접두어를 분리하기 전에 전체 이름을 먼저 찾습니다**: `m`은 미터("밀리-아무것도"가 아닙니다), `mol`은 몰, `cd`는 칸델라,
  `daN`은 데카뉴턴(가장 긴 접두어가 이깁니다). `nF` / `GHz` / `mm^2` / `mV/mm` / `µF` / `Ω` 모두 동작합니다.
  유도 단위는 전자공학이 피할 수 없는 여섯 개를 포함합니다: `F` `Ω`(`ohm`도 가능) `S` `H` `Wb` `T`.
- **차원과 변환 계수는 따로 저장됩니다**: `parse_unit`은 차원만 주고, `parse_unit_spec`은 →SI 변환 계수를 추가로 줍니다.
  `convert(v, "nF", "F") = 1e-9 F`이며, 차원이 맞지 않으면 오류가 납니다. 질량 기본 단위는 **kg**입니다:
  `g = 1e-3 kg`, `mg = 1e-6 kg`, `Mg = 1000 kg` — 접두어는 그램부터 셉니다(회귀 테스트로 고정됨).
  **생성된 함수의 매개변수는 항상 SI 기본 단위입니다**. 선언의 접두어는 가독성에만 영향을 주며, 생성된 코드의 doc 주석이
  매개변수별 변환 계수를 명시합니다(실제 생성된 doc 주석에서 그대로 인용:
  `⚠ 参数 C_dl 声明为 µF：入参是 SI 基单位（1 µF = 0.000001 …）`).
- **CGPM 2022 접두어**가 테이블에 있습니다: `Q`(1e30), `R`(1e27), `r`(1e-27), `q`(1e-30) — 기존의
  `da … Y / d … y`와 함께.
- **정의가 정확한 비SI 단위** (`unit_base`가 각 계수를 담고 있어 `convert`가 차원적으로 정직하게 유지됩니다): `min`, `h`, `d`, `L`
  (`l`도 가능하며, `mL`은 `L`에 붙은 접두어로 분해됩니다), `deg`, `arcmin`, `arcsec`, `bar`, `atm`, `eV`, `Wh`, `tonne`, `Da`(`u`도 가능), `nmi`, `knot`, `ha`, `acre`.
- **오프셋 / 로그 단위는 명시적으로 거부됩니다**: `degC`(오프셋)와 `dBm`(비율)은 접두어 분리 전에 막히며,
  "알 수 없는 단위"가 아니라 "진짜 원인"을 보고합니다 — 이들을 K나 무차원으로 조용히 취급하면 **잘못된 값을 계산**합니다.
  **모호한 기호도 추측하지 않고 같은 방식으로 거부됩니다**: `cal` / `Cal`은 열화학 칼로리(4.184 J)와 IT 칼로리(4.1868 J)에서 다르므로 둘 다
  `J`를 쓰라는 안내와 함께 거부됩니다. `rpm`은 각도 축이 필요한데(1 rpm = 2π/60 rad/s) 이 시설은 `rad`를 무차원으로 취급하므로,
  `[Hz]` 선언과 함께 `2 * pi * f`를 쓰라는 안내와 함께 거부됩니다.
- **무차원 군(버킹엄 Π)**: `dimensionless_groups`는 **정확한 유리수**로 소거하며(`f64`는 오차가 누적됩니다),
  "변수 이름 + 차원"에서 기저의 무차원 조합을 직접 줍니다. 개수 = (변수 개수) − 계수(Π 정리를 단언으로 사용).
  고전적 검사: `{rho, v, L, mu}` → 1개 군 `rho·v·L·mu^-1`(레이놀즈 수).
  `dim_solve`는 같은 계의 비균일 사용입니다: `{kg, m/s²} → N`은 지수 `[1, 1]`을 주며,
  만들 수 없는 차원은 "만들 수 없다"와 함께 몇 개의 차원이 모자란지 보고합니다.

## 차원: 반정수 지수 (2026-11-23)

`Dim`은 내부적으로 **1/2** 단위로 저장하므로(`[i16;7]`이 실제 지수의 두 배를 담습니다), 분수 거듭제곱과 정수 거듭제곱이
같은 정수 산술을 거칩니다: `√s = s^(1/2)`, `f^(-1/2)`, `Ω·s^(-1/2)` 모두 합법이며, 표시에는
`s^(-7/2)`처럼 괄호 형태를 씁니다. 따라서 Warburg 임피던스는 기준 주파수 비차원화 없이
교과서 형태 `Z = σ·f^(-1/2)`로 돌아옵니다. `dim_check`의 거듭제곱 지수는 **먼저 상수를 폴딩하므로**,
자연스러운 표기 `f ^ (1/2)`가 `simplify`를 먼저 호출하지 않고도 게이트를 통과합니다.

## 함수 계열: 극값 / 클램프 / 행렬 연산자 (2026-11-23)

함수 인자 개수의 **유일한 진실 원천**은 `func_arity`(core에 있음)이며, 네 레인(인자 개수 검사 / 평가 / 차원 / 출력 / 다시 쓰기)이 모두
이를 참조합니다 — 예전에는 각 레인이 자기 `match`를 갖고 있었고, 그래서 "실수 레인에서 `arg`가 존재하지 않는 메서드로 출력된" 문제가 한 릴리스를 버텼습니다.

| 계열 | 함수 | 비고 |
| --- | --- | --- |
| 단항 스칼라 | `exp ln log sqrt sin cos tan sinh cosh tanh` | 실수와 복소가 같은 테이블 |
| 복소 | `abs arg conj re im` | `arg`는 무차원; 실수 레인에서 re/im/conj는 항등 |
| 극값/클램프 | `min(a,b)` `max(a,b)` `clamp(v,lo,hi)` | Rust와 같은 형태: `v.max(lo).min(hi)`; 세 인자는 같은 차원이어야 함 |
| 행렬 연산자 | `det` `trace` `adjoint` `inv` | **구체 행렬 리터럴만 받음**; `det`/`inv`는 4차/3차까지(2D와 3D 등매개변수 요소 모두에 충분), `adjoint` = 켤레 전치 |

`det`/`inv`는 **여인수 재귀**를 씁니다(`det` ≤ 4, `inv` ≤ 3): 2D 삼각형과 3D 사면체의 등매개변수 사상에 충분하며,
`J·J⁻¹ = I`와 `det(J)=1`에 대한 수치 검사가 있습니다. 4×4 역행렬은 16개의 3×3 여인수가
(≈100개 항) 필요해 생성 코드가 폭발하므로, 수치 라이브러리를 쓰라는 안내와 함께 명시적으로 거부됩니다. `det`/`trace`는 `diff`에서 **미분 전에 전개**됩니다 —
전개 결과는 평범한 미분 가능 수식이므로 FEM의 `area = det(J)/2`는 값과 해석적 도함수를 모두 갖습니다
(`∂area/∂x₂ = (y₃-y₁)/2`).
`min/max/clamp`의 구간 선택은 IR로 표현할 수 없으므로(비교 연산자가 없습니다) **도함수가 생성되지 않으며**,
생성된 코드의 주석 한 줄이 그 이유를 설명합니다(이제는 panic하지 않습니다). 극값과 클램프는 `f64::min/max`의 NaN 규칙을 따릅니다
(다른 피연산자를 반환할 수 있습니다). NaN 전파가 필요한 호출자는 경계에서 `is_finite`를 검사해야 합니다.

## 내장 형태 한눈에 보기

`identity` / `diag(d)` / `diag_v(d[i])` / `tridiag(a,b,c)` / `tridiag_v(b[i])` /
`bidiag_u(b,c)` / `bidiag_l(a,b)` / **`blockdiag2(p,q)` = diag(p·I₂, q·I₂)** /
**`banded(v, k)` = 반대역폭 k인 대칭 밴드 행렬**(k=2는 5×5부터만 모호하지 않으며, 4×4에서는 조밀 행렬로 퇴화합니다).

이 이름들은 **인식되는 IR 형태**를 서술하며, 수식에서 호출할 수 있는 함수가 아닙니다. 진입점은
줄임표를 쓰는 행렬 스케치이고, 인식되지 않는 것은 명시적으로 거부됩니다.

블록 대각 의미론에서 블록 안 = 스칼라 × 항등(대각에 p, 블록 내부의 비대각은 비어 있음), 블록 밖은 비어 있어야 합니다
(`0`과 `...`는 동등합니다). 전체 차원이 홀수이면 중심 셀은 오른쪽 아래 블록에 들어갑니다.

## 복소 레인 성능: 정직한 쪽 (2026-11-23 측정)

`bin/bench.rs`는 이제 네 레인을 측정합니다. 복소 레인인 Z_c(EIS 주파수 스윕)는 **손으로 쓴 코드보다 느립니다**. 기록된 그대로:

| 형태 | ns/점 | 손으로 쓴 것 대비 |
| --- | --- | --- |
| 손으로 쓴 특수화(`σ/√ω·e^{-jπ/4}`, 분기 없음, 벡터화 가능) | 2.3 | 1× |
| 같은 형태의 전사(생성 코드의 연산자 순서를 하나의 루프에 복사) | 2.9 | 1.3× |
| 생성 코드 · 스칼라 직접 호출 | 6.4 | 2.8× |
| 생성 코드 · 배치 진입점 | 12.8 | 5.5× |

내역: **일반 복소 √/÷는 손으로 쓴 특수화보다 약 2.2배 비쌉니다**(sqrt 1회 대 sqrt 3회 + 나눗셈 1회),
그리고 **배치 래퍼는 여기에 약 2.5배를 더합니다**(튜플 슬라이스 쓰기 + 분기 때문에 루프가 벡터화되지 않습니다).

이미 수행한 최적화(각각 실제로 격차를 좁혔습니다):

1. `__c_sqrt`를 극형식(atan2+cos+sin, 초월 함수 4개)에서 **대수적 닫힌 형태**로 바꿨습니다.
1. 순허수 고속 경로 `√(iy) = √(|y|/2)(1+sign·j)`(sqrt 1회 — EIS에서 일상적인 형태);
1. `__c_div`는 보통 크기에서 단순 형태를 씁니다(나눗셈 1회);
1. 복소 헬퍼를 **클로저**에서 블록 지역 `#[inline(always)] fn`로 옮겼습니다(15.5 → 11.9 ns/점).

**결론(숨기지 않고 README에 기록)**: 복소 레인은 "정확하게 계산하고 충분히 빠른" 용도에 적합하며,
손으로 쓴 특수화의 한계를 쫓을 가치는 없습니다. EIS 스윕의 진짜 핫 루프라면 특수화를 직접 작성하고
수식은 `.formula` 파일에 **진실 원천이자 차원 검사**로 남겨 두십시오. 실수 레인에는 이 문제가 없습니다(스칼라 1.11×, 손으로 쓴 것과 대등).

## 행렬 대수 (형태 + 평가 + 생성)

차원과 형태는 **서로 직교하는 두 검사 축**입니다: 차원은 물리적 의미를, 형태는 대수적 적법성을 지배합니다.

| 기능 | 동작 |
| --- | --- |
| `shape_of` | 구체 행렬 → `(rows, cols)`; 전치는 바뀜; 기호/패턴 행렬 → `None` (동적 추론 없음) |
| `shape_check` | 행렬 덧셈/뺄셈은 형태가 같아야 하고, 행렬 곱은 `left cols = right rows`가 필요하며, 들쭉날쭉한 행렬은 거부되고, 행렬 나눗셈은 명시적으로 거부됨 |
| `eval_value` | 스칼라/행렬의 통합 평가, 행렬 곱은 `C_ij = Σ_k A_ik·B_kj` |
| `flatten_matrix_value` | **정적으로 전개 가능한** 행렬 수식을 구체 행렬 IR로 폴딩(전치/덧셈/뺄셈/부호 반전/스칼라 브로드캐스트/행렬 곱) |
| 출력 | 폴딩된 행렬 → `vec![vec![…], …]` 상수 리터럴; 큰 행렬은 패턴 행렬 + 루프 레인을 거침 |

```text
[1, 2; 3, 4] * [5, 6; 7, 8]  →  [[19.0, 22.0], [43.0, 50.0]]
[1, 2, 3]'                   →  3×1 column vector (emitted as vec![vec![1.0], vec![2.0], vec![3.0]])
A * [1, 2]                   →  scalar broadcast (a bare symbol is a scalar: matrices only come from literals/pattern generators)
[1, 2, 3] * [1, 2, 3]        →  compile-time rejection: matrix multiply impossible: (1, 3) × (1, 3)
```

> **일반 런타임 `A,b`는 여전히 그렇게 선언해야 합니다**: 수량 이름이 `_matrix`/`_vector`로 끝나는
> (또는 `matrix`/`vector`와 같은) `decl` 이름은 행렬/벡터 매개변수가 되며, 아래 런타임 레인이 바로 그것을 씁니다. 그 밖의 모든
> 베어 기호는 스칼라입니다. 따라서 형태가 선언에 포함되지 않은 행렬에 대한 `A * x`는 여전히 리터럴, 정적으로 전개 가능한 수식,
> 또는 패턴 생성기로 표현합니다. 일반적인 대규모 `Ax=b`, 런타임 크기 추론, 또는 조건이 나쁜 계에는 수치 선형대수 라이브러리를 쓰십시오.

**음이 아닌 정수 행렬 거듭제곱**: `[a, b; c, d] ^ 2`는 생성기가 명시적 행렬 곱셈(0–8회)으로 폴딩하며,
`M ^ 0`은 같은 차수의 항등 행렬입니다(반환 타입은 여전히 행렬이며 스칼라 `1`이 아닙니다). 종단 간 수치 검사는
`matrix_power.formula`에 있습니다. 폴딩 실패(음수/분수 거듭제곱, 범위 초과, 비정방)는
`vec![…] * vec![…]` 같은 컴파일 사고 대신 `compile_error!`를 출력합니다. 값 계층(`himari-eval`)도 같은 형태에 같은 결과를 냅니다.

**두 개의 독립 구현이 일치해야 합니다**: 행렬 수식 코드 생성(`flatten_matrix_value` + 리터럴 출력)과
값 계층 평가(`eval_value`)는 따로 작성되므로, **차분 테스트**가 양쪽을 정렬된 상태로 유지합니다 —
폴딩된 리터럴을 평가한 결과는 전개되지 않은 수식을 셀 단위로 평가한 결과와 같아야 합니다(`mat-expr-fold`).

**줄임표 없는 행렬 스케치는 구체 행렬입니다**: 리터럴 레인을 거치며(상수는 폴딩되고 할당 루프가 없음),
생성기보다 낫습니다. 생성기 레인(`n`이 런타임 매개변수)을 쓰려면 줄임표를 써야 합니다.

## 런타임 행렬/벡터 레인 (2026-11-23)

위의 모든 것은 정적입니다: 형태가 수식 컴파일 시점에 알려져 있습니다. 런타임 레인은 **크기가 실행 시점에만 존재하는 매개변수**에 대한
별도의 답입니다 — 사용자 데이터를 소비하는 솔버, FEM 조립, `A`와 `b`를 값으로 받는 모든 것.

- **선언이 유일한 스위치입니다**: 수량이 `_matrix`/`_vector`로 끝나는(또는 `matrix`/`vector`와 같은) `decl`은
  행렬/벡터 매개변수가 됩니다 — `A : stiffness_matrix [N/m]`는 `&[Vec<f64>]`로, `b : load_vector [N]`은 `&[f64]`로 옵니다.
  참여하지 않은 이름은 스칼라로 남으므로 기존 수식은 영향받지 않습니다(`Decl::runtime_kind`).
- **생성된 함수는 실패할 수 있습니다**: `Result<_, himari::runtime::NumericError>`를 반환하며, 하나의 구조화된 오류 타입입니다
  (`InvalidInput` / `ShapeError` / `NonFiniteValue` / `SingularMatrix` / `IllConditioned` / `UnstableResidual` / `NoRealRoots`). 이 레인에는
  **조용한 NaN 계약이 없습니다**.
- **`solve(A,b)`**는 부분 피벗팅 LU이며, 어떤 답을 반환하기 전에 두 개의 독립 게이트를 통과합니다:
  **rcond 추정**(`1/(‖A‖∞·‖A⁻¹‖∞)`, `rcond ≥ f64::EPSILON·64·n` 요구)과 **상대 잔차 검사**
  (`≤ 1e-9`). 역행렬은 조건 추정을 위해서만 계산되며, `x`를 얻는 방법으로 쓰이지 않습니다. 특이 피벗,
  조건이 나쁜 행렬, 잔차가 큰 해는 하나의 "실패"가 아니라 세 가지 구별되는 오류입니다.
- **이 레인에서 또한 지원됩니다**: `inv`, `det`(리터럴 인자만 — 런타임 `det`은 차원에 정적 행렬 차수가 필요하므로 거부됩니다),
  `A*x`, `dot`, `norm`, 그리고 **1-기반** 인덱스의 `A(i, j)`(`[I,J]`; 범위 밖과 0은 panic이 아니라 오류입니다).
- **무엇을 출력하는가**: 본문은 생성된 함수 안의 스코프 내 `let` 체인에 대한 검사된 수식이고, 반환 타입은 값 종류를
  따릅니다(`Result<f64, _>`, `Result<Vec<f64>, _>`, `Result<Vec<Vec<f64>>, _>`). 런타임 레인 수식은 해석적 Jacobian을 **생성하지 않고**,
  `__f32` 변형도 **생성하지 않으며**, 배치 진입점도 **생성하지 않습니다**(그것들은 스칼라의 크기 지정 시그니처가 필요합니다).
- **답은 독립 참조와 대조됩니다**: `runtime_matrix.formula`는 `solve(A,b)`를 별도의 피벗 가우스 소거법과 검증하고,
  `A*x`를 `b`와, `A·inv(A)`를 항등 행렬 열과, 1-기반 인덱싱과, 피벗팅만이 올바르게 푸는 의도적으로 아주 작은 엡실론 계
  (`[[1e-17, 1], [1, 1]]`)를 대조하며 — 모두 2e-12/2e-15 허용 오차로 검증됩니다.
- **매크로 레인**: `formula_matlab!`은 런타임 수식도 받지만 **블록당 하나의 수식만** 받습니다(런타임 체인은 명시적 메시지와 함께
  build.rs 레인에 머뭅니다). 복소 런타임 행렬 매개변수는 당분간 거부됩니다.

## 코드 생성 품질 (2026-11-23)

- **정수 거듭제곱은 `powi`를 출력합니다**: `x^3` → `(x).powi(3)`(예전에는 존재하지 않는 내부 메서드를 출력해서
  어떤 `x^3`이든 생성된 코드 내부를 가리키는 오류와 함께 컴파일 실패했습니다). 픽스처에는 `x^3`에 대한 **컴파일 게이트**가 있습니다.
- **알 수 없는 함수는 컴파일 시점에 실패합니다**: 실수 레인의 함수는 화이트리스트입니다. `arg(x)`는 실수 위에서 무의미하므로
  `compile_error!`이고, `re/im/conj`는 실수 위에서 항등입니다(근사가 아니라 정확).
  다중 인자 호출은 파싱 시점에 거부됩니다(출력기가 `args[0]`만 보고 나머지를 조용히 버리는 것은 잘못된 값을 계산합니다).
- **시스템 Jacobian**: 각 `.formula` 파일은 추가로 `{filename}__jacobian(all params)`를 생성합니다.
  행 = **미분에 참여하는 실수 스칼라 수식**(행렬값 / 복소 / 미분 불가 항목은 건너뜀), 열 = 매개변수(선언 순서)이며,
  매개변수에 의존하지 않는 행은 해당 열 전체에서 **0**입니다. 이것이 음함수 솔버 / 뉴턴 반복 / FEM 조립이 필요로 하는 형태입니다.
- **비유한 상수는 단호히 실패합니다**: `inf` / `NaN`을 출력하면 불법 식별자가 되므로,
  생성 전에 출처를 밝히고 panic합니다(`contains_nan_expr`가 유일한 진실 원천).
- **거듭제곱 주위의 괄호**: `(x^2)^3`과 `x^(2^3)`은 두 표면 모두에서 괄호를 얻습니다 —
  `x ^ 2 ^ 3`은 `(x^2)^3`으로 다시 파싱되므로(x⁸ → x⁶, 즉 표준 포맷팅이 **수학을 바꿀** 수 있습니다).

## 포맷팅 (표준형)

`himari-fmt`: `cargo run -p himari-check --bin himari-fmt -- [--check|--write] <file>`.

- 여러 줄 decl(한 줄에 기호 하나); 한 줄에 수식 하나; **행렬 열 정렬**(각 열 = 가장 넓은 내용 + 공백 1칸 이상, 쉼표가 열 경계).
- 독립 주석 줄은 모두 파일 머리로 모입니다(순서 보존) — 주석은 사람을 위한 것이며 결코 IR에 들어가지 않습니다.
- `--check` = 드리프트 게이트(`just fmt-check` / CI에 연결됨); 표준형 출력은 왕복 멱등입니다.
- **표준형은 쉼표를 유지합니다**: 공백만으로 구분하면 다시 쓸 때 이항 뺄셈과 구별할 수 없으므로(`-k`가 뺄셈 항으로 삼켜집니다),
  쉼표가 모호하지 않은 경계입니다. 손으로 쉼표 없이 쓰는 것은 괜찮고, 포맷팅이 이를 되살립니다.

## 레인 (2026-11-23 사용자 결정)

| 레인 | 사용법 | 적합한 용도 |
| --- | --- | --- |
| **인라인 매크로** | `formula_matlab!{ decl { a : l [m]; b : l [m]; } a / b }` | 단순한 수식 |
| **문자열 매크로** | `formula_latex!{ r"decl { … } \frac{a}{b}" }` | 단순한 수식 (LaTeX 표면) |
| **외부 파일 매크로** | `formula_file!("formulas/bv.formula", matlab)` | 복잡한 수식 (방언을 명시해야 함) |
| **build.rs** | `packages/check/fixtures/three/` 참조 | 생성 코드 체크인 + 드리프트 게이트 (정식 레인) |

매크로 안의 `decl`은 차원 검사를 위한 기호 정보만 제공하며, **Rust 지역 변수를 만들지 않습니다**: 호출 지점의 `a/b`는
호출자가 이미 `let a = …; let b = …;`로 준비해 두어야 합니다. 완전히 컴파일되는 예는
`examples/common/src/main.rs`의 `inline_macro_example()`을 보십시오.

> ⚠️ 알려진 한계: 파일을 읽는 proc-macro는 **cargo가 추적하지 않습니다**(`tracked_path`는 아직 nightly입니다).
> 따라서 `.formula`를 편집한 뒤에는 `touch`를 해야 재빌드가 트리거됩니다. 프로덕션에서는 build.rs 레인(`rerun-if-changed`)을 쓰십시오.
> ⚠️ 패턴 행렬/전치의 **생성자 레인**은 파일 / build.rs에만 존재합니다(파일명과 생성기가 필요합니다).
> 인라인 매크로는 이것을 만나면 안내와 함께 명시적 오류를 보고하며, 결코 조용히 강등되지 않습니다.

## 표면 언어 (셋, 하나의 IR)

| | 논문 | LaTeX | MATLAB 스타일 |
| --- | --- | --- | --- |
| 그리스 문자 | `α·x` | `\alpha \cdot x` | `alpha*x` |
| 줄임표 | `⋯ …` | `\cdots \vdots \ddots` | `...` |
| 행렬 | `[a, ⋯, b; ⋮ ⋱ ⋮; c, ⋯, d]` | `\begin{bmatrix}…\end{bmatrix}` | `[a, ..., b; ...]` |
| 전치 | `A'`, `A′`, `A^T` | `A^T` | 왼쪽과 같음 |
| 차원 선언 | `decl { v : velocity [m/s]; }` | 왼쪽과 같음 | 왼쪽과 같음 |

규칙 (거부도 하나의 기능입니다):

- 모든 기호는 먼저 차원과 함께 선언되어야 합니다. 선언되지 않은 것 = 컴파일 오류, 글리프 추론 없음.
- `\sin^2 x`, `\left(\right)`, `$…$`, `x .* y` 같이 모호하거나 순전히 조판적인 표기는 즉시 거부됩니다.
- 암시적 곱셈은 LaTeX/논문 표면에서만 성립합니다(단일 문자 체계는 구조적으로 모호하지 않습니다). MATLAB 표면은 명시적 `*`를 요구합니다.
- 패턴 행렬은 증명 가능하게 올바른 세 가지 형태만 지원합니다: `identity(n)`, `diag(d, n)`,
  `tridiag(a, b, c, n)`. 인식되지 않는 것은 오류 + 그 세 가지 목록입니다.
- 소스는 손으로 쓸 수 있습니다(결합 부호 등). 그러나 **IR은 정규화되어야 합니다** — 결합 문자는 결코 IR에 들어가지 않습니다.

## 벡터 대수 / Horner / no_std (2026-11-23)

**`dot(a,b)` / `norm(v)`**: **구체 리터럴**에서만 전개됩니다(컴파일 시점에 형태를 압니다).
`dot`의 차원은 양쪽의 곱이고, `norm`은 원소와 같은 차원입니다. `dot([x,y],[x,y])`(x=3,y=4) → 25,
`norm` → 5. 형태가 맞지 않으면 즉시 거부됩니다.

**자동 Horner 변환**: 소스에서 **명시적 다항식**으로 쓴 `c₀ + c₁x + c₂x² + …`는 출력 전에
`(…((cₙx + cₙ₋₁)x + …) + c₀)`로 변환됩니다 — 곱셈 횟수가 `2n-1`에서 `n`으로 줄고, `x^n` 같은 큰 거듭제곱이 사라집니다
(수치적으로 더 안정적입니다). `a*x^3 + b*x` → `(a * x * x + b) * x`.
**간결 형태는 전개되지 않습니다**: `(u-1)^3`은 쓴 그대로 남습니다(전개하면 읽기만 어려워집니다). 도함수도
**Horner 이전의 원본**에서 계산합니다(Horner 형태를 미분하면 상쇄되는 곱의 연쇄가 나옵니다).

**`no_std` 레인**: `himari_buildhelper::generate_dir_libm`은 `core` + `libm`만 쓰는 코드를 생성합니다
(초월 함수 → `libm::exp` 등, 정수 거듭제곱 → `libm::pow`; `f64::powi`는 std의 것입니다).
이는 **생성된 코드**가 `no_std`에서 쓸 수 있다는 뜻이고, 2026-11-23부터 컴파일 타임 스택도 마찬가지입니다:
`himari`, `himari-latex`, `himari-matlab`은 기본 `std` 피처 뒤의 `no_std + alloc`입니다(`std`는 끄지 않으면 켜져 있습니다).
로더, buildhelper, 매크로, check 크레이트(파일 IO, proc-macro 호스트, 도구)는 `std`로 남고 피처를 명시적으로 켭니다.
생성된 코드는 **자체 libm 레인**을 유지하며, 이것이 베어메탈 소비자가 실제로 링크하는 대상입니다.
게이트: `#![no_std]` 픽스처 크레이트(`[lib] test = false`, 테스트 하네스가 std를 필요로 하므로)가
생성된 코드를 **컴파일하면서** 파서 체인도 std 없이 행사합니다(`himari_matlab::parse` → `dims_of_set` → `shapes_of_set` → `dim_check_runtime` → `format_set`).
**`cargo build`가 통과한다 = 생성된 코드와 프론트엔드가 몰래 std에 손을 뻗지 않는다.**
검증된 베어메탈 타깃: `riscv32imc-unknown-none-elf`(core만 — 원자 연산 불가), `thumbv7em-none-eabi`,
`x86_64-unknown-none`(파서 체인). 이 레인은 Jacobian(`alloc`이 필요함)과 f32 변형
(f32 초월 함수는 libm의 `*f` 계열이며, 우리는 반쪽 레인을 배포하지 않습니다)을 출력하지 않습니다. 편미분이 필요하면 수식별 `__d_*` 함수를 쓰십시오
(순수 스칼라, 할당 없음).

## 파일 간 수식 라이브러리: `use "..."` (2026-11-23)

```text
use "lib/atmosphere.formula"      % file header, may span several lines
decl { ... }
v_terminal = sqrt(2 * m * g / (rho * Cd * A))
```

- **파싱은 수집만 하고, IO는 로더의 몫입니다**: 프론트엔드는 순수 문자열 API로 남고(`FormulaSet.uses`),
  `himari-loader`가 파일 읽기, 재귀 인라인, 순환 감지, 충돌 해결을 담당합니다.
- 병합 의미론(단순하고 예측 가능): 참조된 decl/항목은 **먼저 배치됩니다** → 페더레이션이 평소처럼 동작합니다(뒤 항목이 앞 항목을 참조 가능).
  동일한 중복 decl은 중복 제거되고, 표기가 다르면 오류입니다. 중복 항목 이름은 항상 오류입니다(**"마지막 쓰기가 이긴다" 없음**).
  순환은 오류를 내며 순환 주변의 파일명 체인을 출력합니다.
- **라이브러리는 "호출"되는 것이 아니라 "치환"됩니다**: `rho`가 호출자 안으로 전개되면 매개변수 목록에는 `rho_0 / h / H`가 들어갑니다.
  이는 의도된 것입니다(숨은 상태 없음, 정적 미분 가능). 대가는 더 긴 매개변수 목록입니다.
- 디렉터리 관례: `generate_dir`은 **최상위** `*.formula`만 스캔하므로, `formulas/lib/*.formula`는
  자연히 라이브러리로만 존재하며 최상위 수식으로 두 번 생성되지 않습니다.
- **방언은 추측이 아니라 매크로에서 옵니다** (2026-11-24 사용자 결정, "매크로가 곧 방언"): 수식을 감싸는 매크로가
  어떤 문법이 그것을 읽을지 결정합니다.

  | 매크로 | 방언 |
  | --- | --- |
  | `formula!(…)` | **matex** (표준 표면; 진입 이름은 유지되고 의미론은 확정됨) |
  | `formula_latex!(…)` | LaTeX |
  | `formula_matlab!(…)` | matex (`formula!`와 동의어이며, 읽기에 더 자명함) |
  | `formula_file!("f.formula", latex)` | **필수** 두 번째 인자로 결정됨 |

  `formula_file!`은 방언 인자를 선택 사항으로 만들지 않습니다: 파일 내용은 매크로 이름에서 추론할 수 없고,
  매크로가 추측하게 하면 모호함을 다른 곳으로 숨길 뿐입니다.

  **이것이 단지 스타일 선호가 아닌 이유** — 실제의 조용한 잘못된 값을 없애 줍니다. `si`가 선언된 상태에서 `si * x`는:
  matex에서는 `si·x`, LaTeX에서는 `s·i·x`로 읽힙니다. 같은 파일, 같은 입력(s=3, i=5, x=2, si=100)으로 측정한 값:

  ```text
  old AUTO (try matex first, use if it succeeds)  →  200    without reporting any error
  explicit LaTeX                                  →  30
  ```

  둘은 거의 7배 차이 납니다. AUTO는 저자가 무엇을 의도했는지 알 방법이 없었습니다 — "추측"한 것은 어느 파서가 먼저 성공했는지일 뿐입니다.
  그래서 매크로 레인의 `Dialect` 열거형에는 `Auto` 변형이 **없습니다**: 타입 시스템이 추측이 돌아올 수 없음을 보장합니다.

## 빠른 시작: `examples/reentry` (최소 실행 가능 프로젝트)

```text
examples/reentry/
  formulas/entry.formula       % terminal velocity / dynamic pressure / drag (aerospace side)
  formulas/structures.formula  % static displacement = solve(k·x − F, x)
  build.rs                     % three lines: generate_dir("formulas", "src/generated.rs")
  src/main.rs                  % prints the table + physical invariant self-checks
  src/generated.rs             % the checked-in generated code (reviewable, covered by the drift gate)
```

`cargo run -p himari-example-reentry`는 속도→동압→항력 표를 출력하고 다음을 검증합니다:

- **물리적 불변량**: `drag(v_terminal) == m·g`(상대 차이 1.6e-16 — 이것은 적합이 아니라 정의입니다)
- **해석적 도함수 대 차분 몫**: `∂drag/∂v`가 두 경로에서 상대 차이 1.2e-8로 일치
- **기호 풀이**: `x_static`은 `solve(k·x − F, x)`에서 나오며, `∂x/∂F = 1/k`가 자동으로 성립
- **f32 변형**과 **라이브러리가 인라인된 수식의 시스템 Jacobian**이 모두 같은 생성 파일에 있음

이제 소비자는 `himari-buildhelper::generate_dir(dir, out)` 하나만 필요합니다 — build.rs 레인 전체
(파싱 / 페더레이션 / 차원 / 형태 / 도함수 / f32 / 배치 진입점 / Jacobian / 소스 LaTeX)가 하나의 함수로 접히므로,
모든 프로젝트가 더 이상 300줄을 복사하지 않습니다.

이 예제들은 **현재 지원되는 형태**가 실제로 `.formula`에서 실행 가능한 Rust로 간다는 것을 증명합니다. 그것들은
`solve`를 범용 수치 솔버로 내세우지 않으며, 정적 예제들은 런타임 행렬 매개변수를 필요로 하지 않습니다.
생성된 `src/generated.rs`는 체크인되어 있고 드리프트 게이트로 보호됩니다.

## 표준 레인: `himari-standards` (2026-11-23)

`packages/standards`는 몇 가지 **공개된 공학 표준**을 타입 지정 계산기로 바꿉니다. 모듈마다 조항 수준의 관계 하나씩이며, 각자

## 증명 레인: `himari-lean` (2026-11-23)

`packages/lean`은 Lean 4 **공동 프로세스**입니다: 자족적인 증명 의무를 생성해 stdin으로 진짜 `lean` 실행 파일에 넘기고
(`lean --stdin --json -T <heartbeats> -M <MB>`), 무슨 일이 있었는지를 구조화된 문서로 보고합니다. Lake 프로젝트도, 패키지 인덱스도,
네트워크도 없습니다. 생성된 파일에는 import가 없습니다.

- **동적 데이터는 오직 *이름 붙은 예제 정리 진술*의 리터럴 정수가 됩니다** — 데이터 정의, 공리, 식별자가 되지 않습니다.
- **`decide`로 커널 검사됨**: 의무는 `Int` 위에서 닫히고 `by decide`로 처리됩니다. `native_decide`, `#eval`,
  `implemented_by`, `extern`, `partial`, `sorry` 또는 사용자 공리는 출력되지 않으며, 테스트가 생성 텍스트를 그 목록에 대조해 단언합니다.
- **공리 게이트**: `#print axioms` 출력을 파싱하고 `propext`, `Classical.choice`, `Quot.sound`만 용인합니다. 읽을 수 없는 보고는
  위반이며, 결코 통과가 아닙니다. 보고의 부재는 깨끗한 보고의 증거가 아닙니다.
- **독립적 오라클**: 같은 행렬식이 Rust에서 *다른* 전개로 계산되므로 Lean이 유일한 증인이 되는 일은 없습니다.
- **`lean_missing`은 일급의 비성공입니다**: 툴체인이 없었고 **아무것도 검사되지 않았다**는 뜻입니다. 결코
  "검증됨"으로 렌더링되지 않고 결코 0으로 종료하지 않습니다. 상태와 종료 코드: `success` 0, `lean_missing` 3, `invalid_request` 4, `proof_failed` 5,
  `resource_exhausted` 6, `axiom_violation` 7, `oracle_mismatch` 8.

**실제 툴체인(Lean 4.36.0, 커밋 `611c117b`)으로 검증됨.** 이정표 의무는 커널에 수용되고 공리를 전혀 보고하지 않습니다:

```text
status = success            verified = true       exit = 0
lean_message: 'det3_example' does not depend on any axioms
oracle:       rust-i128-permutation det3([1,2,3,4,5,6,7,8,10]) = -3
```

부정 대조군은 같은 바이너리에서 설계대로 동작합니다: `expected = -306`을 단언하는 요청은 `oracle_mismatch`(종료 8)를 반환하고
검증됨으로 보고되지 않으며, 스텁 프로세스 스위트는 `proof_failed` / `axiom_violation` / `resource_exhausted` 경로를 다룹니다.

프로비저닝은 이 저장소 밖의 일이며 일회성으로 남습니다: `elan`을 설치하고, `leanprover/lean4:v4.36.0`을 고정한 뒤, `lean`을 `PATH`에 두거나
`HIMARI_LEAN_BIN`이 그것을 가리키게 하십시오. `just lean-verify`는 의무를 출력하고 실제 Lean 테스트를 실행합니다. **툴체인이 없으면 레인은
`lean_missing`(비성공)으로 강등되며 `--emit`은 여전히 검토 가능한 `.lean` 파일을 씁니다** — Lean의 부재는 결코 검증으로 보고되지 않습니다.

## 견고성과 적대적 입력 (2026-11-23)

- **깊이 제한 2048**: 모든 파싱 출구가 IR 깊이를 한 번 검사하며(`check_depth`), 제한을 넘으면
  어떤 하위 재귀가 스택 오버플로(SIGSEGV)를 내도록 두지 않고 "수식이 너무 깊게 중첩됨 (N levels > limit 2048)"을 보고합니다.
  pest 자체의 스택 제한도 발동하고 그 메시지도 평문으로 번역됩니다. **알려진 경계**: 긴 연쇄 `a + b + c + …`는
  IR에서 왼쪽 중첩이므로 깊이가 항 수와 같습니다. 따라서 한 수식의 항 수는 약 2048로 제한됩니다.
  별도의 결정적 괄호 중첩 보호 장치(256단계, `MAX_PARSE_NESTING`)가 파싱 전에 동작합니다. pest의
  선택적 `stack-guard` 피처를 쓸 수 없는 곳(`no_std`)에서도 성립해야 하기 때문입니다.
- **보이지 않는 문자는 항상 거부됩니다**: 제로 폭 공백 / 양방향 재정의 / 제로 폭 결합자 / BOM / NUL은 모두
  이름이 밝혀지고 파싱 전에 거부됩니다(`scan_source`) — 그것들은 수식이 "검토할 때 보이는 것과 실제로 다른" 것이 되게 할 수 있습니다.
- **합/적분 단계 제한 10^7**: `Σ(i,1,1e9)`가 "밤새 돈다"에서 오류 한 줄로 바뀝니다.
- **인자가 빠진 함수 호출**은 더 이상 `args[0]` 인덱싱으로 panic하지 않습니다: 세 레인(평가/출력/차원) 모두 이를 명시적으로 거부합니다.
- **구조화된 속성 테스트**(무작위 문자 난잡이가 아닙니다): 무작위 수식 600개가 각각 세 게이트를 통과합니다 — 표준형 다시 쓰기가
  **같은 트리**로 재파싱되고, LaTeX 다시 쓰기가 **같은 트리**로 재파싱되며, `simplify`가 **값을 보존**합니다.
  현재 셋 모두 비동등성 0입니다(`prop-roundtrip`). 1500개 항을 합하는 큰 입력도 100 ms 이내에 끝납니다.

## 단정밀도(f32) 레인 (2026-11-23)

모든 **실수 스칼라** 수식은 추가로 `{name}__f32(p: f32) -> f32`를 생성합니다 — 같은 수식,
같은 출력 규칙이며, 리터럴만 `f32` 접미사로 바뀝니다(`Fx::F32`, 출력기에 꿰인 단일 스위치).

게임 엔진 / 오디오 DSP / 실시간 SDR이 직접 이득을 봅니다.

복소 수식과 행렬값 수식은 f32 변형을 **생성하지 않습니다**: 복소 레인의 `(f64, f64)` 튜플과
행렬의 `Vec<Vec<f64>>`는 단정밀도에서 다른 타입 계약입니다. 그것은 나중에 올 수 있습니다(우리는 반쪽 레인을 배포하지 않습니다).

## LaTeX 표면: 여러 글자 이름에는 `\mathrm`이 필요합니다 (2026-11-23)

LaTeX 수식 모드에서 베어 `sigma`는 **다섯 개 변수의 곱 s·i·g·m·a**이므로(암시적 곱셈),
이 방언의 여러 글자 이름은 `\mathrm{sigma_0}`처럼 써야 하며, 다시 쓰기도 같은 방식으로 출력합니다.
그리스 문자 이름(`sigma`, `omega`…)은 아래첨자를 유지한 채 **실제 글리프** `\sigma`로 다시 씁니다
(`\sigma_0`). 구현은 예전에 부분 문자열 교체였기 때문에 `alphabet`이 `\alphabet`이 되고
`betamax`가 `b\etamax`가 되었으며, `sigma`는 다섯 개 이탤릭 글자로 렌더링되었습니다 — 한 번에 세 곳(호버 / 사이드카 / 문서 진실 원천)에서 틀렸습니다. 수정되었습니다(`latex_var`).

## 오류: 하나의 enum, 아홉 개 언어

crate 의 모든 실패는 하나의 enum `himari::Error` 입니다. 문자열 모음이 아니라, 각 실패가
**데이터를 지닌** 변형이므로 세 가지를 동시에 얻습니다.

- **안정적인 코드** — `err.code()` 는 kebab-case 식별자(`dimension-mismatch`, `undeclared-symbol`,
  `no-real-roots` 등)를 돌려줍니다. 테스트와 호출자는 코드를 검증하므로 문구를 바꾸거나 번역해도
  깨지지 않습니다.
- **언어별 렌더링** — `err.render(locale)` 과 `Display`(영어)가
  [i18n.rs](packages/himari/src/i18n.rs) 의 카탈로그에서 문장을 만듭니다. CLI 와 LSP 경계에서는
  `HIMARI_LANG` / `LC_ALL` / `LANG` 으로 선택하며, 아홉 언어는 조직 표준을 따릅니다
  (`en`, `zh-Hans`, `zh-Hant`, `ja`, `ko`, `fr`, `es`, `ru`, `ar`).
- **`anyhow` 호환** — `Error` 는 `core::error::Error`(`std` 에서는 `std::error::Error`)를 구현하고
  `Send + Sync + 'static` 이므로 래퍼가 필요 없습니다:

```rust
  use anyhow::Context as _;

  fn run() -> anyhow::Result<f64> {
      let dim = himari::parse_unit("N/m")?; // `?` converts automatically
      let e = himari::Error::NoRealRoots { discriminant: -4.0 };
      let err = anyhow::Error::from(e).context("solving the loop equation");
      let root = err.downcast_ref::<himari::Error>().expect("root cause kept");
      assert_eq!(root.code(), "no-real-roots");
      assert_eq!(dim, himari::parse_unit("kg/s^2")?);
      Ok(1.0)
  }

  fn main() {
      assert_eq!(run().unwrap(), 1.0);
  }
```

`tests/anyhow_compat.rs` 가 이 모두를 고정합니다: `?` 전파, `Send + Sync + 'static` 경계,
`anyhow::Context` 를 거친 뒤에도 `downcast_ref::<himari::Error>()` 로 코드를 되찾는 것, 그리고
"같은 오류가 아홉 언어에서 서로 다르게 렌더링되지만 코드는 항상 동일"하다는 규칙.

아직 카탈로그에 없는 메시지는 `Error::Message(String)` 에 남습니다. 어떤 언어에서도 그대로 출력되므로
단계적 이전이 **타입으로** 드러납니다(번역된 척하지 않습니다). 이 부채는 **산문이 아니라 게이트**로 잽니다: `python3 scripts/staging_budget.py` 는 워크스페이스의 모든 생산 트리(`packages/`, `examples/`, `tools/`)의 미카탈로그 생산자(`Error::from(`, `Error::Message(`, 프런트엔드의 `FrontError::plain("…")` / `plain(format!(…))` / `FrontError::new(…, "…")`)를 테스트와 카탈로그 자체를 제외하고 세며, 기록된 상한(현재 175)을 넘으면 실패합니다. 게이트는 AST 순회(`tools/staging-budget`, `syn` 기반)이므로 줄 배치·공백·주석에 의존하지 않으며, `matches!(e, Error::Message(m) if …)` 같은 **패턴**이 생성으로 오판되지 않습니다. 상한은 내려가기만 하며 이는 강제됩니다: CI 는 `--against-git` 으로 게이트를 실행해 `HEAD` 의 `tools/staging-budget/src/ceiling.txt` 를 읽고, 작업 트리의 상한이 더 높으면 실패합니다. 38개 변형 전부는 `catalogue_completeness_tests` 가 고정합니다——각 변형을 구성하고 9개 언어로 렌더링합니다(비어 있지 않음, `{n}` 누출 없음). LSP 퀵픽스 *제목*은 여전히 중국어입니다; 진단은 현지화되어 있습니다.

```text
python3 scripts/staging_budget.py                # counts + ceiling
python3 scripts/staging_budget.py --against-git  # also: the ceiling may only go down vs HEAD
```

### 편집기 통합 (LSP)

`himari-lsp`는 손으로 작성한 LSP 서비스입니다(프로토콜 계층은 순수 함수, 단위 테스트 + 종단 간 stdio 테스트):

| 기능 | 설명 |
| --- | --- |
| 진단 | `didOpen`/`didChange` 후 `publishDiagnostics` 푸시 (미선언 기호, 차원 불일치, 문법 오류) |
| 완성 | 파일의 `decl` 이름 + 수식 이름 + 단항 함수 테이블 (`det/inv/solve/roots/...`) |
| **빠른 수정** | `textDocument/codeAction`: 미선언 기호 → ① 가장 가까운 선언 이름으로 고쳐 쓰기 ② decl 블록에 줄 추가; 잘못 쓴 함수 이름 → 레지스트리의 이름 |
| 동기화 | **증분 동기화**(`textDocumentSync: 2`, 범위로 잘라 냄); 전체 변경도 받으므로 옛 클라이언트가 깨지지 않음 |

빠른 수정은 이름이 **정확히 한 번** 나타날 때만 교체를 제안합니다(여러 번 나타나면 "선언 추가"만 제안하고,
어떤 발생인지 결코 추측하지 않습니다). 범위를 벗어난 값은 변경을 버리는 대신 항상 **클램프**됩니다(하나를 버리면
버퍼가 편집기와 영구히 어긋납니다).

### 수식 라이브러리 내용 잠금: 라이브러리가 바뀌면 말해야 한다

`use "lib/…"`는 라이브러리 파일을 **인라인**하므로, 라이브러리가 바뀌면 하위 생성 코드도 함께 바뀝니다 — 가장 놓치기 쉬운
종류의 회귀입니다. `--lock`은 참조된 모든 파일의 지문을 `<entry>.lock`에 쓰고, 그때부터 **매 로드마다 잠금이 검증됩니다**:

```text
$ himari-fmt --lock formulas/entry.formula
已写入 formulas/entry.formula.lock（4 行）

$ himari-eval formulas/entry.formula         # someone quietly changed the library
himari-eval: 公式库与锁文件不一致（formulas/entry.formula.lock）：
  内容变了（声明版本 1.4.2 → 2.0.0）：lib/atmosphere.formula
              复核改动后运行 `himari-fmt --lock <入口>` 重新生成锁。
```

(CLI 출력은 그대로 인용했습니다: 도구는 여전히 중국어로 출력합니다. 영어로는: 라이브러리와 잠금 파일이 불일치합니다 —
`lib/atmosphere.formula`가 선언 버전 1.4.2 → 2.0.0으로 바뀌었습니다 — 변경을 검토한 뒤
`himari-fmt --lock <entry>`를 다시 실행하십시오.)

- **sha256 내용 해시**(semver 범위가 아님): "인라인된 소스"라는 의존 형태에서는 내용 해시가
  더 강한 보장입니다 — 어떤 변경이든 잡히고, 버전 해석 정책도, 프리릴리스 규칙도 필요 없습니다.
- **평문, 결정적, 경로는 엔트리 디렉터리 기준**: git에 넣을 수 있고, diff가 읽히며, 기계 간에 비교할 수 있습니다.
- **닫힌 게이트**: `scripts/fmt_check.py`는 `.lock`이 있는 파일에 `--lock-check`를 실행합니다
  (`--fix`에서는 자동으로 다시 잠급니다) — 낡은 잠금은 누가 파일을 로드하기를 기다리지 않고 게이트에서 빨개집니다.
- **옵트인**: `.lock`이 없으면 아무것도 검증되지 않습니다(기존 저장소에 영향 없음). 잠금이 생기면 **새 참조도 실패합니다**
  (화이트리스트 의미론). 받아들이려면 다시 잠그십시오.
- **읽을 수 없는 잠금도 실패입니다**: UTF-8이 아니거나(편집기가 UTF-16으로 저장), 권한이 부족하거나, 디렉터리 경로인 경우
  모두 강한 오류입니다 — 이것들은 결코 "잠금 없음"으로 취급될 수 없습니다. 그러면 보호가 조용히 꺼집니다.
- **`--fix`는 세 단계입니다**(먼저 모두 포맷 → 그다음 모두 다시 잠금 → 마지막으로 모든 사이드카 재생성):
  사이드카는 로드할 때 잠금을 검증하므로 잠금이 먼저 최종이어야 합니다. 둘 다 참조된 라이브러리의 최종 내용에도 의존하므로,
  하나의 루프에 섞으면 낡은 산출물이 남습니다.
- `%! version: 1.2.0`은 사람이 읽는 칸일 뿐입니다(잠겨 있고 버전 변경이 보고됩니다). 의미론적 보장은 해시에 있습니다.
- semver 범위를 쓰지 않는 이유: 그러면 해석/고정/프리릴리스 정책 전체가 필요해지는데, 이 저장소의 의존 형태는
  "인라인된 소스"입니다. "마이너 드리프트를 허용"을 표현하려면 다시 잠그는 것이 더 직접적인 진술입니다.

### 방언 지시자: 파일 레인의 "매크로가 곧 방언" 대응물

파일에는 감쌀 매크로가 없으므로 대응 규칙은 다음과 같습니다: **기본은 matex; LaTeX는 명시적으로 선언.** 두 레인은 하나의 원칙을 공유합니다 —
추측하지 않고, 작성자(파서가 아니라)가 의미론을 결정합니다.

```text
%! dialect: latex
decl {
    s : d;
    i : d;
    si : d;
    x : d;
}
q = si * x        % LaTeX semantics: s·i·x (not the declared si·x)
```

- `%! dialect: latex`(또는 `tex`)와 `%! dialect: matex`(또는 `matlab`)를 지원합니다.
- **지시자 없음 = matex**. 예전에는 여기에 AUTO 폴백이 있었습니다(matex 파싱이 실패하고 소스에 `\`가 있으면 LaTeX 시도).
  그것이 바로 위의 조용한 200 대 30 잘못된 값을 만들었고 — 제거되었습니다.
- 방언 지시자 없는 LaTeX 전용 표기 → 기본 matex로 파싱 → **오류**(결코 조용히 잘못된 값이 아님).
  오류는 출구를 제시하지만(`%! dialect: latex` 작성) **당신 대신 추측하지는 않습니다**.
- **첫 번째 비주석 줄 이전**에만 효력이 있습니다(본문 주석 안의 `%!`는 방언을 바꾸지 않습니다).
- 인식되지 않는 값은 오류입니다.
- 지시자가 있으면 오류도 그 방언으로 보고됩니다: LaTeX 지시자 아래의 문법 오류는 LaTeX 오류입니다.
- 정확히 한 곳(`himari_loader::parse_source`)에 구현되어 있으므로 build.rs 레인, `himari-fmt`,
  `himari-eval`, LSP 진단이 모두 일치합니다. (LSP 진단은 `HIMARI_LANG` 이 고른 언어로 렌더링됩니다. "오류" 절을 참조하십시오.)

### LaTeX 표면의 나눗셈 (한때 없었음)

`a / b`와 `a \div b`는 이제 진짜 나눗셈이며 `\frac{a}{b}`와 동의어이고, 곱셈과 같은 우선순위이며 왼쪽 결합입니다.
예전에는 LaTeX 표면에 **나눗셈 연산자가 전혀 없었습니다** — `\frac{a}{b}`만 받아들여졌고 `a / b`는 문법 오류였습니다.
그것은 아이를 물과 함께 버리는 셈이었습니다: `/`는 나눗셈을 쓰는 가장 평범한 방법이고 그것을 거부할 이유가 없었습니다.
(위의 AUTO 폴백은 사실 이 결함을 덮고 있었습니다: `a / b`가 "우연히 동작하는" 것처럼 만들면서 조용한 잘못된 값을 함께 데려왔습니다.
결함을 고치면 폴백이 존재할 이유가 없습니다.)

## 기호 선형 풀이 `solve` (2026-11-23)

단일 변수 형태 `solve(equation, variable)`는 `equation = 0`을 `variable = -b/a`로 풉니다(방정식은 그 변수에 대해 **선형**이어야 합니다).

```text
ES_ss = solve(k_on * E * S - (k_off + k_cat) * ES, ES)
      → ES_ss = k_on·E·S/(k_off + k_cat)          % Michaelis–Menten steady state
```

- 해는 **여전히 IR입니다**: 그래서 차원 검사, 평가, 코드 생성, 해석적 도함수, Jacobian을 유지합니다 —
  두 번째 메커니즘이 필요 없습니다. `ES_ss`의 편미분과 Jacobian 행은 자동으로 나옵니다.
- **매개변수 목록 = 출력된 수식이 실제로 쓰는 변수**: 풀어낸 `ES`는 `ES_ss`의 매개변수에 나타나지 않습니다
  ("요구하지만 넘겨야 하는" 문제가 고쳐졌습니다). 사이드카 / 호버 / 완성도 같은 매개변수 목록을 읽습니다.
- **비선형은 명시적으로 거부됩니다**: `x·x`, `1/x`, `x^2`, `sin(x)`는 **파싱 출구에서** 오류를 내고 관련된 종류를 밝힙니다.
  수치 근사도, 의심스러운 답도 없습니다. 화학 정상 상태를 잘못 구하는 대가는 글자 몇 개를 더 쓰는 것보다 훨씬 큽니다.

### 계 형태 `solve([equations…], [unknowns…])`

두 인자가 모두 리스트이면 **선형 계** 레인으로 들어가고, 해는 **열 벡터**입니다(행렬 수식 값 레인,
`Vec<Vec<f64>>` 반환):

```text
x = solve([(k1 + k2) * x1 - k2 * x2 - F1,
           -k2 * x1 + (k2 + k3) * x2 - F2], [x1, x2])
  → x = 2×1 column vector, dimension [m]           % two-mass spring statics
```

- **기호 소거**: 가우스–조르당 소거가 **수식 링** 위에서 동작합니다(계수는 숫자가 아니라 IR 하위 수식이며),
  매 단계마다 표준형으로 단순화됩니다. 풀린 각 성분은 여전히 IR이고 평소처럼 차원/평가/출력을 거칩니다.
  **그러나 계의 해는 행렬값입니다**: 행렬값 수식은 해석적 도함수를 생성하지 않고(원소별 편미분은 행렬이 아니고 Jacobian이 행렬입니다),
  f32 변형도 생성하지 않습니다 — 이는 행렬값 레인의 기존 한계이며 `solve` 특유의 것이 아닙니다.
- **형태 관례**: 방정식과 미지수 리스트는 행 우선으로 **평탄화**되므로 `[e1, e2]`와 `[e1; e2]`는 동등합니다 —
  사용자가 방향을 기억할 필요가 없습니다. 미지수 리스트의 항목은 베어 변수 이름이어야 합니다.
- **미지수는 차원이 선언되어야 합니다**: 그것이 주는 것은 **결과의 차원 검사**(스프링 예제는 `m = N/(N/m)`를 풉니다)와
  방정식 자체의 **균질성** 검사입니다(`x1 − F1`, m에 N을 더하는 것, 은 파싱 시점에 거부됩니다).
  풀린 미지수는 매개변수 목록에 들어가지 않습니다(생성된 함수는 실제 매개변수만 받습니다).
- **거부도 하나의 기능입니다**: 미결정(최대 계수가 아님), 불일치(소거 후 `0 = nonzero`), 비선형(미지수가 곱셈의 양쪽에 /
  분모나 지수에 / 함수 인자 안에 나타남)은 **모두 파싱 출구에서 보고됩니다**.
  차원 관련 거부는 `dims_of_set` / 생성 단계에서 일어납니다(파서 자체는 차원 검사를 하지 않습니다).
  중복 방정식은 "폴딩 가능한 의미"로 제거됩니다: 기호 계수를 가진 중복 행이 0으로 폴딩되지 않으면 보수적으로
  불일치로 보고합니다 — 잘못된 해를 반환하느니 거부하는 편이 낫습니다.
- **피벗 비소멸과 수치 경계**: 단일 변수 `solve`와 같은 관례로, 0임을 증명할 수 없는 것은
  비영으로 취급합니다(`a ≠ 0`을 신뢰합니다). 소거는 컴파일 시점에 수식 순서로 일어나며 **런타임에 |피벗|로 행을 재정렬하지 않습니다**.
  극단적 스케일에서는 닫힌 형태가 상쇄되고, 특이 매개변수는 값 계층에서 0으로 나누기를 보고하고 생성 코드에서는 IEEE에 따라
  `inf/NaN`을 냅니다 — 그것은 예외가 아닙니다. 조건이 나쁜 계, 또는 피벗팅 전략이 필요한 계는 수치 라이브러리로 가야 합니다.
- **경계 (네 가지, 모두 파싱 출구에서 또는 컴파일 타임 오류로 거부됩니다)**:

  1. **행렬값인** 계수나 상수항(`solve(M*x - b, x)`, `solve([M*x - b], [x])`) → `inv(A) * b`를 가리키는
     안내와 함께 명시적으로 거부됩니다 — 그렇지 않으면 스칼라 레인이 `vec!` 나눗셈을 생성해 컴파일되지 않습니다.
  1. **방정식은 서로 다른 차원을 가질 수 있습니다**(N 단위의 힘 평형에 m 단위의 기하학적 제약을 더한 것은 합법적인 계입니다). 그러나 각 방정식은
     스스로 균질해야 하고, 해의 모든 성분은 **하나의 차원**을 공유해야 합니다(차원이 섞인 미지수 — 전류와
     저항을 동시에 푸는 것 — 는 아직 지원되지 않습니다. 그것은 행렬값 레인의 한계입니다).
  1. 복소 레인(`j` 포함)은 **값 계층**과 **출력 계층**에서 동작합니다(2026-11-23 완료). 복소 열 벡터는
     `Vec<Vec<(f64, f64)>>`로 출력되며, 각 원소는 (실수, 허수)입니다. 따라서 AC 회로 절점 해석과 EIS 스타일의 "복소 방정식 계"가
     코드로 직접 생성될 수 있습니다.
  1. **중복 행의 영 검사는 충분 조건입니다**: 동류항 결합으로 증명할 수 있는 영(`k−k`, `k·a−a·k`, `x·x²−x³`)은
     인식됩니다. 영임을 증명할 수 없는 복소 항등식은 비영 계수로 취급합니다(보수적 — 미결정/불일치를 잘못 보고할 수는
     있지만, 잘못된 해를 반환하지는 않습니다).

### 다항식 근 `roots(poly, x)`

`solve`는 선형 닫힌 형태를 주고, `roots`는 **다항식의 모든 근**을 줍니다(열 벡터로):

```text
roots_quad = roots(a * x ^ 2 + b * x + c, x)
% q = −(b + sign(b)·√(b²−4ac))/2; large root = q/a, small root = c/q
% Return order still matches the original formula (−b−√Δ first); it does not depend on sorting the roots by size.
```

- **1–2차만**: 1차는 `solve`와 같은 수학이고, 2차는 닫힌 형태의 근 공식입니다.
  **3차 이상은 실제 차수를 보고하며 명시적으로 거부됩니다** — 카르다노/페라리는 부동소수점에서 조건이 몹시 나쁘고,
  이 저장소는 "정확해 보이는" 근사를 내놓지 않습니다. 3차 이상의 근은 먼저 계수를 수치적으로 구한 뒤
  수치 라이브러리를 쓰십시오.
- **중근은 중복도만큼 반복됩니다**(`x² − 2x + 1`은 1을 두 개 줍니다) — 대수학 기본정리와 일치합니다.
  영근에 대한 `q=0` 대체는 `-b/(2a)`이며 `0/0`을 거치지 않습니다.
- **이차 공식의 상쇄 회피**: `(−b±√Δ)/(2a)`를 직접 쓰면 `b²≫4ac`일 때 작은 근을 잃습니다
  (`x²−10⁸x+1`이 한때 `10⁻⁸`을 약 `7.45×10⁻⁹`으로 계산했습니다). 이제 안정적인 `q/a`와 `c/q`를 쓰며, 생성 코드에서 작은 근의
  상대 오차 허용선은 `1e-12`입니다. 두 부호 방향과 복소 레인 모두 회귀 테스트가 있습니다.
- **차원은 자동으로 나옵니다**: 방정식은 차원적으로 균질해야 하고, 균질성은 곧 "근의 차원 = 변수의
  차원"을 함의하므로 별도의 차원 유도가 필요 없습니다(계약 테스트가 이 추론을 보호합니다).
- **실수 레인에서 음의 판별식**: 생성 코드는 NaN이 아니라 **타입 지정 오류**를 반환합니다 — 실수 이차 `roots` 진입점은 이제
  `Result<_, himari::runtime::NumericError>`를 반환하고 음의 판별식은 `NumericError::NoRealRoots { discriminant }`입니다. 더 이상 조용한
  NaN 계약이 없으므로 `is_nan`/`is_finite` 검사가 이 경우를 감지하는 방법이 아닙니다. 컴파일 시점에
  음수임이 증명되는 상수 판별식은 여전히 즉시 거부됩니다. `eval_value`는 일반 복소 값 계층이며 **여전히 같은 수식에 대해 복소 레인에서
  복소 근을 반환합니다**. 복소 레인에는 명시적 `j`가 필요합니다.
- **상쇄되는 고차항은 제거됩니다**: `x³ − x³ + x − 1`은 1차로 취급됩니다("다항식에 x³가 나타나므로 거부"가 아닙니다).
- **비다항식은 명시적으로 거부됩니다**: 함수 인자 안의 `x`, 분모의 `x`, 비정수 거듭제곱의 `x` — 각각 이유를 함께 밝힙니다.
- **행렬값 계수**는 거부됩니다(`solve`와 같은 관례이며, 그렇지 않으면 스칼라 레인이 `vec!` 나눗셈을 생성합니다).

### 계수 벡터 `poly_coeffs(poly, x)`

`roots`의 여집합입니다: **계수**를(저차에서 고차로) 주며 `1×k` 행 벡터를 반환합니다.

```text
coeffs = poly_coeffs(2 * s ^ 2 - 3 * s + 1, s)   → [[1, −3, 2]]
```

- **변수는 무차원이어야 합니다**. 균질 다항식의 k차 계수의 차원은 `dim(poly)/dim(x)^k`여서 서로 다릅니다.
  그러나 행렬은 **하나의 차원을 가진 원소**를 요구합니다 — 따라서 차원이 있는 변수의 계수를 취하는 것은 그 형태로는 대수적으로 불가능합니다.
  이 검사는 진단 단계에서 그것을 직접 설명하고 출구를 제시합니다(특성량으로 나누거나 `roots`를 쓰기). 하위에서
  "행렬 원소 차원이 다름"을 보고하게 두지 않습니다.
- 고차 영 계수는 제거됩니다(`x³ − x³ − 2x + 1`은 1차). 영 다항식은 거부됩니다.
- 비다항식(`sin(x)`, `1/x`, 비정수 거듭제곱)은 거부됩니다.
- `roots`와 같은 `poly_coeffs` 추출기를 공유합니다 — 계수 의미론의 정의 하나, 사용자 둘.

### 3차를 넘는 근: `himari-eval --roots`

언어에서 3차 이상을 거부하는 것은 강제된 트레이드오프이지만, **수치적** 근 찾기는 어떤 차수에도 동작하므로 도구 계층에 있습니다:

```text
$ himari-eval cubic.formula --roots
cubic = 1, 2, 3  [1] (degree 3, 3 roots)
cplx  = -1, 0.5-0.8660254037844387j, 0.5+0.8660254037844386j  [1] (degree 3, 3 roots)
```

- **Durand–Kerner 반복** (복소 산술을 위해 core의 `C` 재사용, 서드파티 수치 라이브러리 없음): 초기값은
  `0.4 + 0.9j`의 거듭제곱이고, 반지름은 **근 크기의 기하평균** `|c₀/cₙ|^(1/n)`입니다(퇴화한 경우에만
  코시 한계 `1+max|cᵢ|`로 대체). 최대 1000회 반복; DK 기준은 `|Δz| ≤ 1e-10·radius`(근의 크기 기준이며
  1 기준이 아님)이며, 뒤이어 **뉴턴 다듬기 60단계**(상대 정지 기준 `1e-15·|z|`).
- **비수렴은 오류**이며, 아직 수렴하지 않은 근사를 결과로 반환하지 않습니다. 반복 중 `inf`/`NaN`도 즉시 오류입니다
  (`f64::max`는 NaN에 대해 다른 쪽을 반환하므로, 한때 NaN 단계가 "수렴"처럼 보여 NaN 20개를 반환했습니다).
- **잔차 수용**: 반복 후 상대 후방 오차 `|p(z)| / Σ|aₖ|·|z|ᵏ`가 충분히 작아야 하며(임계값 1e-8),
  그렇지 않으면 오류입니다 — DK는 근으로의 수렴을 보장하지 않으며, 기준은 반복 자체와 독립적이어야 합니다.
  분모는 **반드시 `k=n` 항을 포함해야 합니다**: 그것이 없으면 작은 `|z|`에서 분모가 상수 `|a_n|`로 퇴화하고,
  `x²−1e-100`이 4e25배 틀린 채로 통과할 것입니다(실제 회귀).
- **뉴턴 다듬기**(상대 기준): 단근은 기계 정밀도에 도달합니다. **중근은 선형으로만 수렴**하므로 `x²−2x+1` 같은 것은
  상대 오차가 `1e-9` 수준이며 오류를 내지 않습니다 — 그것은 알고리즘의 성질이지 버그가 아닙니다. 중근을
  단근으로 취급하지 마십시오.
- **차수 제한 16**(`poly_coeffs`의 다항식 전개 한도이며, `numeric_roots` 자체는 최대 64까지 지원합니다).
- 반복 전 **모닉 정규화**(최고차 계수로 나누기)로 크기 오버플로를 피합니다. 차수 한도 64; `inf`/`NaN` 계수는 거부됩니다.
- **노이즈 영처리는 허수부만 지우며, 기준은 상대적입니다**: 실근은 `1e-16` 규모의 허수 잔여를 지니는데 이는
  반복 산출물입니다. 기준은 `|im| ≤ 1e-12·|z|`입니다. **실수부는 결코 건드리지 않습니다**(`x²−1e-50`의 근은 ±1e-25입니다).
  그리고 **절대 임계값도 소용없습니다** — 크기가 1e-12 아래인 복소근에서는 허수부가 근의 정보 전부이며,
  (`x³−1e-60`이 그 기준 때문에 한때 세 개의 실근으로 뭉개졌고, 상대 오차 0.87이었는데 오류가 나지 않았습니다).
- 계수는 `--set`이 준 매개변수에서 숫자로 평가되어야 합니다. 변수를 생략하면 "수식에서 선언된 유일한 기호"로
  추론되며, 후보가 여러 개면 `--var`가 필요합니다.
- 출력에는 차수와 근 개수가 실립니다. 복소근은 `a+bj`로 씁니다.

## 복소 행렬과 복소 방정식 계 (2026-11-23)

복소성은 스칼라에만 있는 것이 아닙니다: 행렬 원소와 해 벡터도 복소일 수 있고, **값 계층과 출력 계층이 일치합니다**.
생성된 함수의 반환 타입은 `Vec<Vec<(f64, f64)>>`입니다(원소 = (실수, 허수)):

```rust
// I = solve([Z*I1 - V, Z*I1 - R*I2], [I1, I2]) with Z = R + jωL
pub fn I(R: f64, w: f64, L: f64, V: f64) -> Vec<Vec<(f64, f64)>> { … }
```

- 전형적인 용도는 **AC 회로 절점 해석**과 EIS 모델링입니다: 미지수는 복소 전류/전위입니다.
- 전치는 **단순 전치**입니다(켤레 없음) — 켤레는 별도의 `conj` 연산자이므로 혼동하지 마십시오.
- `adjoint`는 켤레 전치이며, 컴파일 시점에 형태가 알려진 리터럴만 전개할 수 있습니다.
- 복소 레인에서 `det/trace/adjoint/inv/solve/roots/dot/norm`도 **마찬가지로** 출력 전에 IR 수준에서 전개됩니다(역사적 비대칭:
  실수 레인은 전개했지만 복소 레인은 곧장 `compile_error!`로 갔습니다).
- 여전히 지원되지 않음: 복소 수식의 **no_std/libm 레인**(클로저가 std에 의존합니다), 복소 수식의 **해석적 도함수**
  (`abs/arg/conj/re/im`은 복소 해석적이 아니며, 그것은 비르팅거 미적분이 필요합니다), 그리고 복소 수식의 **f32 변형**.

## WGSL(GPU) 레인: 부분집합 + 검증 경계 (2026-11-23)

`himari-fmt --wgsl <file.formula>`는 실수 스칼라 수식을 f32 커널로 출력합니다:

```wgsl
// Generated by himari (f32 scalar lane; really compiled and validated by naga)
fn q(rho: f32, v: f32) -> f32 {
    return 0.5f * rho * (v * v);
}
```

**지원 부분집합(의도적으로 작습니다)**: `+ - * /`, `sqrt`, `exp`/`log`(이 저장소의 `ln`) `sin cos tan
sinh cosh tanh abs min max clamp`, 더불어 2/3 거듭제곱, 제곱근, -1 거듭제곱.
**명시적으로 거부됨**: 복소(`j`), 행렬, `det/inv/solve`, Σ/∫, 기호 연산자, 기타 거듭제곱,
WGSL 예약어와 충돌하는 기호 — 각각 이유와 함께(컴파일되지 않는 커널은 출력하지 않습니다).

**검증은 두 계층입니다**(2026-11-24부터 WGSL 레인에 **컴파일러 수준** 증거가 있습니다):

1. **실제 컴파일 게이트**(권위): `cargo test -p himari-check --features wgsl-compile`이
   픽스처의 모든 출력 커널을 **naga**(wgpu의 셰이더 컴파일러, WGSL 명세의 권위 있는 구현 중 하나)에 넘겨
   실제 파싱 + 실제 검증을 합니다. naga는 순수 CPU 개발 의존성이며 **GPU가 필요 없고**, 런타임 의존성 트리에 결코 들어가지 않습니다.
1. **정적 게이트**(빠른 선별, `wgsl::validate_wgsl`): 괄호 균형, `-> f32` 시그니처, 정확히 하나의
   `return`, `f`를 지닌 부동소수 리터럴, `^`/`**` 없음, 비유한 상수 없음. 그 가치는 "naga가 없는 환경에서 거친 오류를 잡고
   + 이 레인에 더 가까운 오류 메시지"이며, **정확성의 증명이 아닙니다**.

**실제 컴파일 게이트가 필수인 이유 — 구체적 교훈**: 이 WGSL 레인의 모든 커널은 예전에 **유효하지 않았습니다**.
WGSL에는 식 본문 함수가 없고 본문은 `return expr;`이어야 하는데, 출력기는 항상 베어 수식을 출력했습니다.
더 나쁘게는 정적 게이트가 **`return`을 금지**했습니다 — 그 규칙은 명세의 그 부분을 모른 채 작성되어
오해를 "규칙"으로 바꾼 것이었습니다. 정적 게이트의 구조적 사각지대는 "놓친다"가 아니라 "**무엇을 놓쳤는지 모르고,
올바른 코드를 틀렸다고 판정할 수도 있다**"입니다. 첫 naga 실행이 그 부류 전체를 드러냈습니다.
또 바로잡은 믿음: `return 2.5;`는 naga에서 **합법**입니다(추상 부동소수는 문맥에 따라 f32로 안착합니다) — 따라서 "부동소수는 `f`를
달아야 한다"는 이 레인의 스타일 관례이지 WGSL 명세가 아닙니다.

**검증 경계(정직하게 진술)**: naga는 **문법과 타입**만 검증합니다. "커널이 실제 GPU에서 올바른 숫자를 계산하는가"는 여전히
미검증입니다 — 그것은 wgpu 런타임 + GPU가 필요합니다(node-3에 RTX 5880이 있으며, 연결 대기 중).
또한 tint(Chrome/Dawn의 구현)와 naga는 일부 경계 규칙에서 다릅니다. 이 저장소는 naga에 대해서만 책임집니다.

## 분야별 레인 선택 (표 하나)

| 시나리오 | 권장 레인 | 비고 |
| --- | --- | --- |
| 대규모 과학 HPC / 수치 라이브러리 | `.formula` + build.rs, 실수 스칼라 | 손으로 쓴 것과 대등(1.0×); 고정 길이 배치 변형이 경계 검사를 없앰 |
| 게임 엔진 / 오디오 DSP | 동일 + **`{name}__f32`** | 측정된 SIMD 이득 1.44×; `clamp/min/max`로 클램프 |
| 실시간 SDR | 실수 또는 복소 레인 + 배치 | 합성곱/채널 행렬을 리터럴로 (상수는 폴딩됨) |
| EIS / 전기화학 | 복소 레인 (`j` + `(f64,f64)`) | 위상은 물리적 약속입니다; 스윕에는 배치를 쓰고, **핫 루프는 직접 작성** |
| FEM / 유한요소 | 행렬 연산자 `det/trace/inv` + Jacobian | `det`는 4차까지, `inv`는 3차까지; 그 이상은 수치 라이브러리로 |
| 런타임 크기 선형 계 | 런타임 레인 (`_matrix`/`_vector` decl) | `solve(A,b)`가 검사됨(rcond + 잔차); `Result` 반환 |
| 차원 탐색 | `himari-eval --groups` | 버킹엄 Π 군: 레이놀즈 수를 손으로 유도할 필요 없음 |

> 일부 중국어 텍스트도 반대편에 남아 있습니다: 생성 코드의 doc 주석과 진단 문자열은 이 레인의 메시지가
> 현재 중국어로 쓰여 있기 때문입니다(위에 인용한 doc 주석을 보십시오). 이들은 한 줄 문자열 리터럴입니다.

**캐럿이 붙은 오류**, **잘못 쓴 함수 이름에 대한 제안**(`closest_func`, 편집 거리 ≤ 2),
**보이지 않는 문자 거부**, **깊이/단계 제한** — 이것들은 장식이 아니라 "동료가 감히 이걸 쓰게 하려면" 필요한 기준선입니다.

## 상태

`dev` 브랜치에서 반복 개발 중입니다(로컬 저장소이며 원격에 푸시되지 않았습니다). crates.io / docs.rs 배지는 예약된 진입점이며,
**아직 아무것도 게시되지 않았습니다**. 정식 크레이트의 `publish = false`가 수동 검토 잠금이고, 예제와 픽스처도 게시 불가로 남습니다.
내부 의존성은 이미 로컬 경로와 함께 `version = "0.1"`을 달고 있으며, 검토가 해제되면 위상 순서대로 게시되어야 합니다:
`himari → himari-latex / himari-matlab → himari-loader → himari-buildhelper → himari-macros`.
`himari-check` 도구 릴리스는 따로 결정됩니다. `himari-standards`와 `himari-lean`은 워크스페이스의 새 `publish = false` 크레이트이며,
각각 `himari-macros`와 `himari-loader`에 의존하므로 그 게시 순서를 바꾸지 않습니다.
로드맵과 트레이드오프의 이력: `_reports/math-formula-20261122/` (REPORT / SPIKE-S0 / SYMBOLS-AND-PAPER).

## 검증

```bash
cargo test --workspace --offline
cargo test -p himari-check --features wgsl-compile --test wgsl_compile --offline
cargo run -p himari-check --release --offline
python3 scripts/fmt_check.py

```

게이트는 핵심 대수, 실제 생성 코드 컴파일과 수치 불변량, 독립적으로 작성된 소비자 예제, WGSL의 실제 naga 컴파일,
그리고 표준형/사이드카/잠금과 생성 코드 드리프트를 다룹니다. 정확한 테스트 개수는 현재 `cargo test --workspace` 출력이 말하는 대로이며,
성능 숫자는 이 저장소의 bench 환경만 서술하며 크로스 플랫폼 보장이 아닙니다.

## 주장하지 않는 것

이것들은 범위 한계이지 거의 다 된 할 일 목록이 아닙니다. "주장하지 않음"이라고 쓰인 곳에서는 "주장하지 않음"이라고 말하십시오.

- **기호 레인에 런타임 피벗팅이 없습니다**: 기호 `solve`는 수식 순서로 소거하며 `a ≠ 0`을 신뢰하고,
  피벗 크기로 행을 재정렬하지 않습니다. 조건이 나쁘거나 피벗팅에 민감한 계는 런타임 레인(위의 `solve(A,b)`)이나 수치 라이브러리의 몫입니다.
- **패턴 행렬은 파일 레인으로만**: 패턴 행렬의 생성자 레인은 파일명과 생성기가 필요하므로, 인라인 매크로는 안내와 함께
  이를 거부합니다. 임의의 패턴 행렬을 자동으로 전개하는 기능은 없습니다(연구급 — 내장 형태 밖의 것은 지원 목록과 함께
  명시적으로 거부됩니다).
- **WGSL 수치 검증은 아직 대기 중입니다**: naga는 문법과 타입을 증명할 뿐, 커널이 GPU에서 올바른 숫자를 계산한다는 것을 증명하지 않습니다. 여기서 GPU 실행은 이루어지지 않았습니다.
- **Lean 검증은 성공하지 못했습니다**: 이 호스트에는 툴체인이 설치되어 있지 않아 스텁 프로세스 테스트만 돌았습니다. Lean이
  생성된 증명 의무를 수용한다는 주장은 없습니다.
- **`publish = false`는 사람 검토 게이트입니다**: 사람 검토가 해제할 때까지 크레이트는 의도적으로 게시 불가이며, 상태를 보십시오.
- **`no_std` 범위**: `himari`, `himari-latex`, `himari-matlab`은 `no_std + alloc`이고, 로더/buildhelper/매크로/check 크레이트는 아닙니다.
  생성 코드는 자체 libm 레인을 유지하며, 복소 수식은 `no_std` 레인의 일부가 아닙니다.
- **복소 해석적 도함수 없음, 복소나 행렬값 수식의 f32 변형 없음, 행렬값 수식의 해석적 도함수 없음.**
- **`roots`는 언어에서 1–2차만 다룹니다**; 더 높은 차수는 `himari-eval --roots`로 수치적으로만 가능합니다.
- 일반 LaTeX(매크로/카테고리 코드/조판) — 의미론이 결정 불가능하며, 조판은 렌더링 계층의 몫입니다.
- 글리프에서 의미론을 추론하지 않으며, MATLAB 표면의 `xy` 곱셈도 없습니다. `\sin^2 x` 없음, `.*` 없음, `$…$` 없음(모호하거나 순전히
  조판적인 표기: 파싱과 렌더링은 다른 일이고 하나의 파서가 둘 다 해서는 안 됩니다).
- 실시간/안전 필수 경로에 런타임 JIT 없음. AGPL 의존성은 결코 없음(evalexpr ≥12와 그 친구들은 제외됩니다).
- **`himari-standards`** 모듈은 조항 수준 계산기이며 **적합성 주장이 아닙니다**: 시험편 형상, 힘 수준 선택,
  유지 시간, 불확도 예산, 표준 자체의 보고 규칙을 모델링하지 않으며, 범용 단위 라이브러리도 아닙니다.
- **`himari-lean`** 레인은 하나의 작은 닫힌 정수 의무(3×3 행렬식 예제)를 증명하며, 범용 정리 증명기가 아니고, 그 공리
  게이트는 Lean 자체 출력에 대한 파서이지 건전성 논증이 아닙니다.
