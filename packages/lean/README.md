# `himari-lean`

A Lean 4 co-process for himari: generate a self-contained proof obligation,
hand it to a real `lean` executable, and cross-check the answer with an
independent Rust oracle.

```text
lean --stdin --json -T <heartbeats> -M <MB>
```

No Lake project, no package index, no network. The generated file has no
imports and needs nothing beyond the toolchain's own library.

## Milestone request

```json
{ "theorem": "det3", "values": [1, 2, 3, 4, 5, 6, 7, 8, 10] }
```

Matrix entries may also be decimal strings (`"1"`, `"-2"`). The optional fields
are `literals` (nine integers overriding what the statement mentions),
`expected` (the determinant the caller believes is correct), and the budgets
`heartbeats` / `memory_mb` / `timeout_secs`. Unknown fields are refused rather
than ignored.

## Generated source

```lean
/-
  Self-contained proof obligation generated by himari-lean.
  No imports, no axioms, no `native_decide`: the goal is closed and
  discharged by the kernel through `by decide`.
-/

/-- Determinant of the 3x3 integer matrix `[[a, b, c], [d, e, f], [g, h, i]]`,
computed with the Sarrus expansion. -/
def det3 (a b c d e f g h i : Int) : Int :=
  a * e * i + b * f * g + c * d * h - c * e * g - b * d * i - a * f * h

/-- Worked example: the determinant of a specific integer matrix. -/
theorem det3_example : det3 1 2 3 4 5 6 7 8 10 = -3 := by decide

#print axioms det3_example
```

Dynamic data enters at exactly one place: the integer literals of the named
example theorem statement. They are re-rendered from `i64` values, never copied
from the request text. The source contains no `native_decide`, `#eval`,
`sorry`, `axiom`, `implemented_by`, `extern`, `partial` or attribute syntax;
the only occurrence of the word `axiom` is the `#print axioms` command itself.

> **The milestone matrix has determinant -3, not -306.** `-306` is the value for
> matrices with a 9 in the last position, which is singular for the first two
> rows. Both figures are pinned by tests so the generator, the oracle and the CLI
> cannot drift apart on it.

## Statuses

| status | meaning | exit |
| --- | --- | --- |
| `success` | kernel accepted it, axioms clean, oracle agrees | 0 |
| `lean_missing` | no usable toolchain — **nothing was checked** | 3 |
| `invalid_request` | malformed, out of scope, or a forbidden token | 4 |
| `proof_failed` | Lean ran and refused the theorem | 5 |
| `resource_exhausted` | a heartbeat / memory / wall-clock guard bounded it out | 6 |
| `axiom_violation` | axioms outside `propext` / `Classical.choice` / `Quot.sound` | 7 |
| `oracle_mismatch` | the request's `expected` disagrees with the Rust oracle | 8 |

Only `success` is verified, and only `success` exits 0. `lean_missing` is a
first-class non-success: it is reported loudly, never downgraded to a pass, and
never confused with `proof_failed`.

An unreadable `#print axioms` line is an `axiom_violation`, not a pass: the
absence of a report is not evidence of a clean one.

## Checking the obligation without this tool getting a toolchain

`himari-lean --emit <path>` writes the generated obligation to a file, byte-identical to what
the co-process feeds to `lean` over stdin. That path works with **no** Lean installed: the run
still reports `lean_missing` (a non-success), but the file is written, so anyone with a
toolchain can check it directly:

```bash
himari-lean --input request.json --emit det3.lean
lean det3.lean          # silent on success; the emitted file ends with the axiom query
```

Pinned and **actually verified**: **Lean 4.36.0**
(`leanprover/lean4:v4.36.0`, Linux x86_64 archive ≈ 580 MB compressed). Provisioning is a
one-off: install `elan`, pin `leanprover/lean4:v4.36.0`, then put `lean` on `PATH` or point
`HIMARI_LEAN_BIN` at it. With that in place `cargo test -p himari-lean --test cli_real_lean --
--ignored` actually checks the obligation; without it the test reports the missing toolchain.

Measured result with the pinned binary (4.36.0, commit `611c117b`):

```text
status = success   verified = true   exit = 0
lean: 'det3_example' does not depend on any axioms
```

The same binary yields `oracle_mismatch` (exit 8) for a request that asserts a wrong
`expected` value, so the gate is not vacuous.

`just lean-verify` does both steps and is expected to fail the ignored test on a host without
Lean — that failure is the honest state, not a gate regression.

## CLI

```text
himari-lean [--input <path>] [--print-source]
```

Reads the request from `--input` or stdin, writes the result as JSON on stdout,
and puts the generated source on stderr when `--print-source` is given. The
regression suite uses an unadvertised `--no-verify` switch to force the missing
state on any machine.

## Tests

```sh
CARGO_HOME=/tmp/himari-cargohome \
CARGO_TARGET_DIR=/mnt/work/sandbox-targets/himari-lean \
cargo test -p himari-lean
```

Unit tests cover request intake and its deny-list, the oracle, source
generation, the axiom parser and the status model. Integration tests cover the
missing-toolchain state, input plumbing, and the subprocess contract using a
**stub** `lean` that records argv and stdin.

The stub tests prove the pipe is wired correctly; they prove nothing about Lean.
